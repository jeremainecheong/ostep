Classes and objects: initialization order, exactly as specified

Most "why did that print 0?" questions in Java are answered by two numbered procedures in JLS chapter 12: when and how a class is initialized, and the five steps of constructing an instance. Add the rules for fields, methods, overriding, hiding and access, and you can predict every trace. This lesson takes the procedures verbatim and lets you step through them.

Primary sources: JLS §12.4 Initialization of Classes and Interfaces (§12.4.1 When Initialization Occurs, §12.4.2 Detailed Initialization Procedure, examples 12.4.1-1/2/3), §12.5 Creation of New Class Instances (examples 12.5-1, 12.5-2), ch 8 (§8.3 fields, §8.4.8 inheritance/overriding/hiding, §8.8 constructors, §8.1.3 inner classes). Quoted rules were read from the SE 21 text.

What you'll be able to do

    When a class is initialized (§12.4.1)

    A class or interface T is initialized immediately before the first occurrence of: (1) an instance of T is created; (2) a static method declared by T is invoked; (3) a static field declared by T is assigned; (4) a static field declared by T is used and it is not a constant variable. Also by certain reflective calls. Under no other circumstance. Superclasses are initialized first; superinterfaces only if they declare default methods; initializing an interface does not initialize its superinterfaces; a static field reference initializes only the class that declares it.

    The spec's own examples: with class Two extends Super and an unused class One, new Two() prints Super Two false — One is never initialized. Sub.taxi where taxi is declared in Super prints only 1729: Sub's static initializer never runs. J.i for a constant i in interface I does not initialize I (constants are inlined); K.j initializes J but neither I nor K.

    The procedure (§12.4.2) uses a per-class initialization lock and four states (verified-and-prepared, in progress by thread T, initialized, erroneous). A recursive request by the same thread returns immediately (so a static initializer can see a not-yet-initialized field of its own class); another thread waits; an erroneous class throws NoClassDefFoundError forever after. Steps: constant variables first; then the superclass and default-method superinterfaces recursively; then the static initializers and static field initializers in textual order as one block. An exception that is not an Error is wrapped in ExceptionInInitializerError, and the class is marked erroneous.

    Creating an instance (§12.5)

    Memory is allocated for all instance fields, including those of every superclass (or OutOfMemoryError), and all fields are set to default values. Then the constructor runs by this five-step procedure:

    1. Bind the arguments to the parameters.
    2. If the constructor begins with this(...), evaluate those arguments and run that constructor recursively with these five steps, then go to step 5.
    3. Otherwise (unless the class is Object) run the explicit or implicit super(...) recursively.
    4. Execute the instance initializers and instance variable initializers of this class, in textual order.
    5. Execute the rest of the constructor body.
    Dynamic dispatch is not altered during construction. "If methods are invoked that are overridden in subclasses in the object being initialized, then these overriding methods are used, even before the new object is completely initialized." Example 12.5-2 prints 0 then 3: the superclass constructor calls an overridden method that reads a subclass field before step 4 has assigned it.

    Step through a full trace

    class Super {
    static { System.out.print("Super-static "); }
    { System.out.print("Super-init "); }
    Super() { System.out.print("Super() "); show(); }
    void show() { System.out.print("Super.show "); }
}
class Sub extends Super {
    static int s = log("Sub-static-field ");
    static { System.out.print("Sub-static "); }
    int x = log("Sub-field ") ;
    { System.out.print("Sub-init "); }
    Sub() { super(); System.out.print("Sub() "); }
    @Override void show() { System.out.print("Sub.show(x=" + x + ") "); }
    static int log(String s) { System.out.print(s); return 7; }
    public static void main(String[] a) { new Sub(); new Sub(); }
}

    Members: fields, methods, overriding, hiding

    • Overriding (§8.4.8.1) applies to instance methods with an override-equivalent signature; the return type may be a subtype (covariant); access may not be reduced; checked exceptions may not be broadened; @Override asks the compiler to verify. Dispatch is on the run-time class of the receiver (§15.12.4).
    • Hiding applies to static methods and to fields: chosen by the static type of the expression. A subclass field with the same name hides, not overrides; ((Super) sub).x reads the superclass field.
    • Overload resolution (§15.12.2) happens at compile time in phases: first without boxing/varargs, then with boxing, then with varargs; the most specific method wins, ambiguity is an error. print(null) with overloads for String and Object picks String (more specific).
    • Access (§6.6): private (top-level class body, including nested classes), package-private (default), protected (package + subclasses, with the "through a subclass reference" restriction), public; modules add exports/opens on top.
    • Constructors are not inherited; the default constructor exists only when none is declared; super(...)/this(...) must be the first statement in 21 (JEP 447 relaxes this later); a class whose only constructors are private can't be subclassed outside its body.
    • Nested classes (§8.1.3): static nested classes are plain; inner classes capture an enclosing instance (Outer.this); local and anonymous classes capture effectively final locals; since Java 11 (JEP 181 nestmates) private members are accessible across the nest without synthetic accessors.
    class A { String name = "A"; static String who() { return "A"; } String me() { return "A"; } }
class B extends A { String name = "B"; static String who() { return "B"; } @Override String me() { return "B"; } }
A ab = new B();
System.out.println(ab.name + " " + ab.who() + " " + ab.me());   // A A B — fields and statics: static type; instance methods: dynamic
void f(Object o) { System.out.print("Object "); }   void f(String s) { System.out.print("String "); }
f(null);                                            // String — most specific applicable overload
void g(int x) {}  void g(long x) {}  void g(Integer x) {}  void g(int... xs) {}
g(1);                                               // g(int): phase 1 finds it before boxing/varargs are considered

    Object: the root's contract

    equals must be reflexive, symmetric, transitive, consistent, and false for null; equal objects must have equal hashCode; toString is for humans; getClass is final; wait/notify belong to the monitor (lesson 7); finalize is deprecated for removal and, per JLS §12.6 in SE 21, an implementation may disable finalization — use Cleaner or try-with-resources. Records (next lesson) generate equals/hashCode/toString from state; HashMap relies on the contract (lesson 12 shows its hashing).
