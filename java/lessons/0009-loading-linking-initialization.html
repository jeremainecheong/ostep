JVMS 21 Chapter 5 Loading, Linking, and Initializing · JLS §12.4 Initialization of Classes and Interfaces

From bytes to a live class: loading, linking, initialization

A class file becomes a usable class in three phases the JVMS specifies precisely — loading (find bytes, create the class in the method area, via a class loader), linking (verify, prepare, resolve symbolic references, lazily), and initialization (run <clinit> exactly once, under a per-class lock, superclass first). Class loaders make a class's identity <name, defining loader>, which is what enables plugins, hot-swapping frameworks and modules — and what produces "ClassCastException: X cannot be cast to X".

Primary source: JVMS §5, fetched in full — §5.3 creation and loading (bootstrap vs user-defined loaders, defining vs initiating loaders, loading constraints, derivation steps), §5.4 linking (verification, preparation, resolution, access control, method overriding/selection), §5.5 initialization (triggers and the 12-step procedure), §5.7 termination. What you'll be able to do

    Loading: class loaders and identity

    Creation of class C named N is triggered by some class D whose constant pool references N (or by reflection). For a non-array class the JVM asks a class loader to locate the bytes: the bootstrap loader (built into the JVM; ClassNotFoundException → NoClassDefFoundError) or a user-defined loader, an instance of a ClassLoader subclass whose loadClass(N) either loads C directly — obtains bytes and calls defineClass — or delegates to another loader. The loader that calls defineClass is C's defining loader; every loader on the delegation path that the JVM asked is an initiating loader. Array classes have no bytes; the JVM creates them, with the component type's defining loader.

    Identity. After creation a class is determined by the pair <binary name, defining loader>, and its run-time package by <package name, defining loader>. Two loaders that each define com.x.Foo from the same bytes produce two distinct classes; instances of one cannot be cast to the other. Loading constraints (§5.3.4) make this safe: when class C (loader L1) references a field/method of D (loader L2), every type name T in the descriptor must denote the same class through L1 and L2 (TL1 = TL2); a violation is a LinkageError. Well-behaved loaders return the same Class for the same name every time.

    Derivation (§5.3.5): the JVM parses the bytes (ClassFormatError; UnsupportedClassVersionError; NoClassDefFoundError if this_class ≠ N), resolves the superclass (ClassCircularityError if C is its own ancestor; IncompatibleClassChangeError if the superclass is an interface or final, if C is not among a sealed superclass's PermittedSubclasses, or if C overrides a final method), resolves superinterfaces, then marks L as defining loader and records L as initiating. Modules (§5.3.6): every class is in exactly one run-time package and thus one run-time module; unnamed modules read everything and export everything; access control is by module, not by loader. Since JDK 9 the platform loaders are bootstrap → platform → application (system), delegating parent-first by default.

    Delegation walk

    Linking: verify, prepare, resolve

    Verification (§5.4.1) checks the structural constraints of §4.9/4.10 (the StackMapTable type-checker from lesson 8); failure is a VerifyError, remembered so later attempts fail the same way. Preparation (§5.4.2) creates static fields with default values (no code runs — explicit initializers belong to initialization) and imposes loader constraints for overriding methods. Resolution (§5.4.3) turns symbolic references into concrete ones for new, getfield, invoke*, checkcast, ldc…; the spec allows lazy (per use) or eager strategies, and HotSpot is lazy: the first execution of an instruction resolves its constant-pool entry, and the result — or the error — is memoized (an IllegalAccessError stays even if the package is later exported dynamically). Field lookup: C, then superinterfaces recursively, then the superclass. Method lookup: C, then superclasses, then the maximally-specific superinterface methods (private and static interface methods are ignored); one non-abstract match wins, otherwise the choice is arbitrary. invokedynamic call sites are resolved per instruction by running the bootstrap method once (lesson 10). Then access control (§5.4.4): public + same module, or public + read/exported; package-private in the same run-time package; protected for subclasses; private for nestmates (NestHost/NestMembers — inner classes no longer need synthetic accessors).

    Three properties hold whatever the strategy: a class is completely loaded before it is linked; completely verified and prepared before it is initialized; and link errors are thrown where the program actually uses the class.

    Not triggers (JLS §12.4.1): reading a constant variable (inlined at compile time), referencing a static field declared in a superclass through a subclass name (only the declaring class initializes), array creation new C[10], C.class literals, and Class.forName(name, false, loader).

    The initialization procedure (§5.5), as a state machine

    Two consequences worth memorizing. Because <clinit> runs under the class's initialization lock and a second thread blocks until it completes, the lazy holder idiom (static class Holder { static final X INSTANCE = new X(); }) is a correct, lock-free-after-the-first-time singleton. And because recursive requests from the initializing thread return immediately, a static initializer that (through another class) reads its own not-yet-assigned static field sees the default value — the source of "static field is null" mysteries in class-initialization cycles. If <clinit> throws, the class is marked erroneous: the first caller gets ExceptionInInitializerError, every later one NoClassDefFoundError.
