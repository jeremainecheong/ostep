Records, sealed hierarchies, and interfaces: modelling data as data

Java 16–17 added the two halves of algebraic data types: records (product types — "a transparent carrier for a fixed set of values") and sealed classes/interfaces (sum types — a closed set of permitted subtypes). Together with pattern matching (lesson 5) they let the compiler check that a switch covers every case. Interfaces, meanwhile, grew default, static and private methods, so this lesson also settles how the JLS resolves conflicting inherited defaults.

Primary sources: JLS §8.10 Record Classes and the java.lang.Record class documentation (quoted from the JDK 21u source), §8.1.1.2 sealed classes / JEP 409, ch 9 (§9.4.1 inheritance and overriding in interfaces, §9.4.3 interface method body, §9.8 functional interfaces), JEP 395 (records).

What you'll be able to do

    Records (§8.10)

    From the Record javadoc: "A record class is a shallowly immutable, transparent carrier for a fixed set of values, called the record components." Mandated members: a canonical constructor with the same descriptor as the record header and at least the record's accessibility; a private final field per component; a public accessor per component (x(), not getX()); and equals, hashCode, toString derived from all component fields. Invariant: new R(r.c1(), …, r.cn()).equals(r) must hold.
    • A record is implicitly final, extends java.lang.Record, cannot declare instance fields beyond its components or instance initializers, may declare static members, nested types, and may implement interfaces. It may be generic and local (local records are implicitly static).
    • The compact canonical constructor record Range(int lo, int hi) { Range { if (lo > hi) throw …; } } has no parameter list; parameters are assigned to the fields after its body, so it can validate and normalize (reassign parameters) but cannot assign fields directly. Explicit accessors exist for defensive copies of mutable components.
    • Component annotations propagate to field/accessor/parameter according to their targets. Serialization uses the canonical constructor. Records are ideal switch subjects via record patterns (lesson 5: case Range(int lo, int hi)).
    record Point(int x, int y) {
    Point {                                    // compact canonical constructor: validation/normalization
        if (x < 0 || y < 0) throw new IllegalArgumentException("negative");
    }
    Point(int v) { this(v, v); }               // extra constructors must delegate to the canonical one
    double dist() { return Math.hypot(x, y); } // instance methods may use the fields
    static Point ORIGIN = new Point(0, 0);     // static members allowed; instance fields are not
}
var p = new Point(3, 4);
p.x(); p.equals(new Point(3, 4)); p.toString();   // 3, true, "Point[x=3, y=4]"
record Pair<A, B>(A first, B second) {}             // generic record

    Sealed classes and interfaces (§8.1.1.2, §9.1.1.4)

    A sealed class or interface lists its direct subtypes with permits (omittable when they are in the same compilation unit). Every permitted subtype must be in the same module (or the same package in the unnamed module), must directly extend the sealed type, and must itself be final, sealed (continuing the closed hierarchy) or non-sealed (reopening it). Records and enums are implicitly final, so they are natural leaves. Reflection exposes Class.isSealed()/getPermittedSubclasses(). The payoff is exhaustiveness: a switch over a sealed type without a default is checked to cover all permitted subtypes, and adding a subtype produces compile errors where cases are missing (lesson 5).

    Is this hierarchy legal?

    sealed interface Shape permits Circle, Square, Polygon {}
record Circle(double r) implements Shape {}            // record ⇒ implicitly final
final class Square implements Shape { … }
non-sealed class Polygon implements Shape { … }        // anyone may extend Polygon
double area(Shape s) {
    return switch (s) {                                  // exhaustive: no default needed
        case Circle c  -> Math.PI * c.r() * c.r();
        case Square q  -> q.side() * q.side();
        case Polygon p -> p.computeArea();
    };
}

    Interfaces in 21 (ch 9)

    • Members are implicitly public; fields are implicitly public static final constants; abstract methods have no body; since Java 8 default methods (§9.4.3) supply an implementation inherited by implementing classes, static methods belong to the interface only; since Java 9 private (and private static) methods share code between defaults. Interfaces cannot have instance state or constructors.
    • Resolution of conflicting defaults (§8.4.8.4, §9.4.1.3): (1) a method from a class always wins over any interface default ("class wins"); (2) among interfaces, a more specific interface (a subinterface) wins over the one it overrides; (3) if two unrelated interfaces supply the same default, the class must override it — and may call a chosen one with I.super.m(). An abstract method in one interface and a default in another also forces an override.
    • Functional interfaces (§9.8): exactly one abstract method (methods of Object don't count); @FunctionalInterface asks the compiler to check; the target of lambdas (lesson 6). Marker interfaces (Serializable) have no methods at all.
    • Interface initialization (lesson 2) happens only when a field that is not a constant is used, or a static method is invoked — and, for a class, when the interface declares default methods.
    interface Walker { default String move() { return "walk"; } }
interface Swimmer { default String move() { return "swim"; } }
class Duck implements Walker, Swimmer {
    @Override public String move() { return Walker.super.move() + "+" + Swimmer.super.move(); }  // required: unrelated defaults conflict
}
class Base { public String move() { return "base"; } }
class Robot extends Base implements Walker {}   // no conflict: the class method wins over the interface default → "base"

    Enums (§8.9)

    An enum is a class with a fixed set of instances created during class initialization (in declaration order), implicitly final unless constants have bodies, with values(), valueOf, ordinal(), name(), and compareTo by ordinal. Constructors are private; enums may have fields, methods, and implement interfaces (sealed ones too); they are the safe singleton idiom and serialize by name. EnumMap/EnumSet are bit-vector-backed. JEP 441 lets case labels use qualified constants (case Suit.HEARTS) even when the selector's static type is a sealed supertype.
