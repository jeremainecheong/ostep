What Java 21 adds, feature by feature

JDK 21 is the LTS release after 17 and ships fifteen JEPs: three that finish multi-release efforts (virtual threads, record patterns, pattern matching for switch), a collections fix twenty years overdue (sequenced collections), a new GC mode, a security API, two deprecation warnings, and six previews/incubators that show where the language is heading. This lesson is the map; the language JEPs get worked examples and an exhaustiveness checker.

Primary sources: the JDK 21 GA announcement on jdk-dev (list of 15 JEPs) and Oracle's Significant Changes in JDK 21; JEP 441 (full text fetched — dominance, exhaustiveness, null, guards); JEP 440; java.util.SequencedCollection source (JEP 431); JEPs 444/439/446/453 as covered in lessons 12–15.

    Record patterns (JEP 440)

    A record pattern Point(int x, int y) matches a value that is an instance of the record and binds the components by calling the accessors — it is deconstruction, the inverse of the canonical constructor. Patterns nest: Line(Point(var x1, var y1), Point(var x2, var y2)). var infers component types; generic records infer type arguments (Box(String s) matches Box<String>). A record pattern never matches null (unlike a type pattern in a total position), and a null component still matches a nested var/type pattern only if the type pattern is unconditional for that component. If an accessor throws, matching completes abruptly with MatchException (from JEP 441's error rules). Exhaustiveness handles nesting recursively: a switch over Pair<S> where S is sealed with A and B needs Pair(A a, A b), Pair(A a, B b), Pair(B a, A b), Pair(B a, B b) — or a wildcard-ish Pair(A a, S b) + Pair(B a, S b).

    Pattern matching for switch (JEP 441)

    // selector may be any reference type (or int/char/short/byte)
static String describe(Object o) {
    return switch (o) {
        case null            -> "null";                        // without it: NullPointerException
        case Integer i when i > 0 -> "positive int " + i;      // guarded label
        case Integer i       -> "int " + i;                    // unguarded after guarded
        case String s        -> "string of length " + s.length();
        case Point(int x, int y) -> "point " + x + "," + y;    // record pattern
        case int[] a         -> "ints x" + a.length;
        default              -> o.toString();                  // one match-all only
    };
}
sealed interface Shape permits Circle, Square {}
record Circle(double r) implements Shape {}
record Square(double s) implements Shape {}
static double area(Shape s) {                                   // exhaustive without default:
    return switch (s) {                                         // permits clause = type coverage
        case Circle c -> Math.PI * c.r() * c.r();
        case Square q -> q.s() * q.s();
    };                                                          // compiler adds a throwing default
}

    Dominance & exhaustiveness checker

    Order the labels for a switch over Object o; the checker applies JEP 441's rules.

      The rules, from the JEP. (1) Labels are tried in order; the first applicable one wins. (2) A label dominated by an earlier one is a compile error: case CharSequence cs before case String s; an unguarded pattern before the same guarded pattern; a pattern before a constant of its type (case Integer i before case 42). Guards are not analysed (undecidable) except a constant true. Hence the natural order: constants → guarded patterns → unguarded patterns. (3) At most one match-all label (default, or a pattern unconditional for the selector type). (4) Exhaustiveness is required for switch expressions and for switch statements that use patterns or null or a non-legacy selector type; type coverage uses sealed permits and generic refinement; legacy switch statements compile unchanged. Prefer exhaustive switches without default so adding a permitted subtype breaks the build instead of failing at run time; the compiler inserts a synthetic default that throws MatchException for separately-compiled drift. (5) null: only case null (or case null, default) matches null; default alone does not. (6) Pattern variables are flow-scoped; falling through a pattern label is an error, and a label cannot bind several patterns. (7) Enum switch expressions now throw MatchException (not IncompatibleClassChangeError) when no constant matches at run time.

      Before 21 there was no type expressing "has an encounter order": List had get(size()-1), Deque getLast(), LinkedHashSet nothing, and no uniform way to iterate backwards. The default implementations in SequencedCollection are built on iterator() and reversed() (e.g. getLast() is reversed().iterator().next()), so custom collections get them for free once they implement reversed(). Watch for conflicts: a class that already had getFirst() with a different return type won't compile against 21 (the famous Vector/JavaFX ObservableList incidents).

      Reading the trajectory

      Three themes tie the release together. Data-oriented programming: records (16) + sealed types (17) + record patterns and pattern switch (21) let you model data as algebraic types and process it with exhaustive, compiler-checked switches instead of visitors. Project Loom: virtual threads (final) with structured concurrency and scoped values (preview) restore blocking, thread-per-request code as the scalable default. Project Panama: the FFM API and Vector API continue toward JNI-free native interop and SIMD. Plus "integrity by default" (JEP 451 is the first step toward requiring explicit opt-in for agents, following the encapsulation work of JDK 9–17).
