HotSpot: from bytecode to machine code, and back

The JVMS ends by saying that translating bytecode into native code "just in time" is the implementor's business. HotSpot's business is a tiered pipeline: a template interpreter starts everything, counters find hot methods and loops, the C1 compiler produces quick code with profiling, and C2 produces aggressively speculative code that can be deoptimized back to the interpreter when a speculation fails. This lesson gives the tiers, the thresholds and transitions straight from the source, and the optimizations that make "write clean code and let the JIT handle it" mostly true.

Primary sources: HotSpot JDK 21u sources read for this lesson — compilerDefinitions.hpp (CompLevel enum), compilationPolicy.cpp (the state-transition comment, quoted below), compiler_globals.hpp (Tier3/Tier4 thresholds), c2_globals.hpp/c2_globals_x86.hpp (inlining limits), safepoint.hpp, deoptimization.hpp; JVMS §2.13. Diagnostics mentioned: -XX:+PrintCompilation, -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining, JFR.

What you'll be able to do

    The tiers

    0 · interpreterCompLevel_none. Template interpreter: a machine-code stub per bytecode, generated at startup. Profiles invocation and back-edge counts.
    1 · C1 simpleCompLevel_simple: C1 without profiling — for trivial methods, or when C2 can't compile something.
    2 · C1 limited profileInvocation and back-edge counters only; a holding pattern when C2 is busy.
    3 · C1 full profileCounters + MethodData (MDO): type profiles at call sites, branch frequencies, null-check outcomes — the input C2 needs.
    4 · C2 / JVMCICompLevel_full_optimization: the server compiler (or Graal via JVMCI): speculative, inlining-heavy, escape-analysing.
    Transitions (from compilationPolicy.cpp): (a) 0 → 3 → 4, the common path; profiling may start at 0 and finish at 3. (b) 0 → 2 → 3 → 4 when the load on C2 is too high, so the method runs at level 2 without over-profiling while it waits. (c) 0 → (3→2) → 4 when the C1 queue is long enough that profiling fully happens at level 0, so the in-queue request is downgraded to 2. (d) 0 → 3 → 1 or 0 → 2 → 1 for methods found trivial (or that C2 cannot compile). (e) 0 → 4 directly after a deoptimization that needs no reprofiling, or if C1 fails. And "state 0 can be reached from any other state via deoptimization", so loops are possible.

    Thresholds (compiler_globals.hpp defaults): tier 3 is requested when invocations exceed Tier3InvocationThreshold = 200, or invocations > Tier3MinInvocationThreshold 100 and invocations + back-edges exceed Tier3CompileThreshold = 2000; tier 4 when invocations exceed Tier4InvocationThreshold = 5000, or > 600 with invocations + back-edges > Tier4CompileThreshold = 15000. Loops compile separately by on-stack replacement (OSR) when back-edge counts pass Tier3BackEdgeThreshold 60000 / Tier4BackEdgeThreshold 40000: the running interpreter frame is replaced mid-loop by a compiled one. The thresholds scale with compiler-queue load (Tier?LoadFeedback). Compilation runs on background compiler threads; the method keeps executing at its current level until the new code is installed in the code cache.

    Deoptimization and safepoints

    Compiled code embeds assumptions: "this branch is never taken", "this call site sees only ArrayList", "no subclass of Shape exists". When one fails — the branch is taken, a new class is loaded, a profile changes — the JVM deoptimizes (deoptimization.hpp): it reconstructs the interpreter frames the compiled frame had folded together (using the debug info recorded at every safepoint in the compiled code, including scalar-replaced objects it must re-materialize) and continues in the interpreter at level 0, usually recompiling later with better profiles. Deoptimization happens only at safepoints: points where the JVM knows the exact state of every thread's frames and which references live where. Compiled code polls for a pending safepoint at method returns and loop back-edges; the VMThread's SafepointSynchronize::begin() "rolls all JavaThreads forward" to their next poll and waits (safepoint.hpp) — the same mechanism stop-the-world GC pauses use, and why a long-running counted loop without a poll can delay a pause (time-to-safepoint). Since JDK 10, thread-local handshakes let the VM run an operation on one thread without stopping all of them; JDK 21's ZGC relies on that.

    Practical rules that follow. Keep hot methods small so they inline; keep call sites monomorphic where it matters (one concrete type per site); prefer final/private helpers; avoid megamorphic interface calls in inner loops; don't fear short-lived objects (escape analysis and the young generation handle them); always warm up before measuring (JMH); read -XX:+PrintCompilation lines: % = OSR, s = synchronized, ! = has exception handlers, n = native, level in the 4th column, "made not entrant" = deoptimized.
