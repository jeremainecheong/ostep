Class files and bytecode: the contract between javac and the JVM

Everything the JVM knows about your program arrives as a .class file: a big-endian binary with a magic number, a constant pool that acts as the symbol table, and per-method bytecode for a stack machine with one-byte opcodes. This lesson reads one from the first byte to the last instruction, explains why the instruction set is deliberately non-orthogonal, and sets up lesson 9 (how those bytes become a running class) and lesson 10 (how invocation works).

Primary sources: JVMS §4 (ClassFile structure, constant pool, descriptors, attributes, verification), §2.11 (fetched: one-byte opcodes, type-support table, computational types), §6; HotSpot classFileParser.cpp (magic, versions, preview rule) and bytecodes.hpp (opcode numbers). Tool: javap -v -p.

    u2 minor, u2 major
    Java 21 = major 65 (45 = JDK 1.0.2; 52 = 8; 61 = 17). Legal: 45–55 any minor; ≥ 56 with minor 0; or major = current with minor 65535 for preview class files, which need --enable-preview (rule quoted from classFileParser.cpp).
    constant_pool
    1-indexed table of tagged entries: Utf8, Integer/Float/Long/Double (the 8-byte ones take two slots — a documented "poor design choice"), Class, String, Fieldref/Methodref/InterfaceMethodref (→ Class + NameAndType), NameAndType, MethodHandle, MethodType, Dynamic, InvokeDynamic, Module, Package. Everything symbolic — names, descriptors, referenced classes — lives here and is resolved lazily (lesson 9).
    u2 access_flags
    ACC_PUBLIC 0x0001, FINAL 0x0010, SUPER 0x0020, INTERFACE 0x0200, ABSTRACT 0x0400, SYNTHETIC 0x1000, ANNOTATION 0x2000, ENUM 0x4000, MODULE 0x8000
    this_class, super_class, interfaces[]
    constant-pool indices; super_class is 0 only for Object; interfaces always have Object as superclass
    fields[], methods[]
    each: access flags, name index, descriptor index, attributes. Field descriptors: I J Z B C S F D, Lpkg/Name;, [ prefix per dimension. Method descriptors: (IJLjava/lang/String;)V
    attributes[]
    Code (max_stack, max_locals, code[], exception_table, then nested StackMapTable, LineNumberTable, LocalVariableTable), ConstantValue (static finals — lesson 9's step 6), Exceptions, Signature (generics survive erasure here), BootstrapMethods (§4.7.23, for invokedynamic/condy), InnerClasses, NestHost/NestMembers (§4.7.28–29, private access between nestmates since JDK 11), Record, PermittedSubclasses (§4.7.31), SourceFile, RuntimeVisibleAnnotations, MethodParameters, Module…

    Bytecode: a stack machine with one-byte opcodes

    §2.11: an instruction is a one-byte opcode followed by zero or more operands (big-endian when multi-byte). The stream is byte-aligned except tableswitch/lookupswitch, padded to 4 bytes. The interpreter loop is literally "fetch opcode at pc; fetch operands; execute; repeat". One byte limits the set to 256 opcodes — HotSpot's bytecodes.hpp numbers 202 of them (nop 0x00 … jsr_w 0xc9, plus breakpoint 0xca) and reuses the rest for internal fast variants it rewrites at run time. The set is intentionally not orthogonal: type letters i l f d a (and b s c only for array access and pushes); boolean, byte, char, short are loaded sign/zero-extended and computed as int. Computational-type categories: 1 (int, float, reference, returnAddress) vs 2 (long, double — two operand-stack units and two local slots).

    Each frame has a local variable array (parameters first; slot 0 is this for instance methods) and an operand stack, both sized at compile time in the Code attribute. Families: loads/stores (iload_2, astore, ldc, bipush, iconst_1), arithmetic (iadd, ldiv — the only integer ops that throw are div/rem by zero; floats never throw), conversions (i2l widening, d2i narrowing with saturation), object/array (new, newarray, getfield, putstatic, arraylength, checkcast, instanceof), stack management (dup, pop2, swap), control (if_icmpge, goto, tableswitch for dense cases, lookupswitch for sparse), invocation (invokevirtual, invokeinterface, invokespecial, invokestatic, invokedynamic — lesson 10), returns (ireturn… return), athrow, monitorenter/monitorexit. Comparisons of long/float/double first produce an int via lcmp/fcmpl/dcmpg (the l/g variants decide what NaN yields), then an int branch.

    Exceptions, verification, and what javac hides

    Exception handling is a table per Code attribute: (start_pc, end_pc, handler_pc, catch_type); when an exception is thrown, the JVM scans the current method's table in order for a range containing the faulting pc whose type matches, else pops the frame and rethrows in the caller (§2.10). finally blocks are duplicated by javac into each path plus a catch-all handler — there is no "finally" bytecode. Since Java 7 (jsr/ret are no longer used by javac), verification (§4.10) is by type-checking against the StackMapTable: the compiler records the types of locals and stack at every branch target, so the verifier can check each basic block in one pass without inferring types by fixpoint. The verifier guarantees stack discipline, type-safe locals, that <init> is called exactly once on a new object, and that protected access rules hold. Other javac artifacts: <init> constructors and one <clinit> per class (§2.9), synthetic bridge methods for generics (lesson 4), lambda$main$0 private methods plus invokedynamic for lambdas, string concatenation via invokedynamic to StringConcatFactory, switch on strings via hashCode + lookupswitch, pattern switches via invokedynamic to SwitchBootstraps.typeSwitch, and enum switches via a synthetic $SwitchMap$ array.
