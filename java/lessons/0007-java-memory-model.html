The Java memory model: what a read is allowed to see

Chapter 17 does not say how threads are scheduled. It says which values a read of shared memory may return when other threads write it — and it answers with one relation, happens-before. If two conflicting accesses aren't ordered by it, the program has a data race and the compiler, the JIT and the CPU are all free to reorder in ways that look paradoxical. If they are ordered, the program behaves as if sequentially consistent. Everything else in Java concurrency — synchronized, volatile, final, start/join, java.util.concurrent — is a way to create those edges.

What you'll be able to do

    Monitors, wait sets, and what sleep doesn't do

    §17.1 Every object has a monitor; only one thread holds it at a time; a thread may lock it several times (reentrant) and each unlock reverses one lock. synchronized (obj) locks the computed object's monitor and unlocks on any completion; a synchronized instance method locks this, a static one locks the Class object. Deadlock is neither prevented nor detected. §17.2 Every object also has a wait set. wait() requires holding the lock (else IllegalMonitorStateException), releases all n locks, sleeps until notify/notifyAll/interrupt/timeout — or a spurious wake-up, which the spec explicitly permits ("although not encouraged") and which is why wait must sit in a loop re-checking the condition — then re-acquires n locks. notify picks an arbitrary waiter; notifications cannot be lost to interrupts. §17.3 Thread.sleep and yield have no synchronization semantics: the spec's own example, while (!this.done) Thread.sleep(1000); with a non-volatile done, may loop forever because the compiler may read the field once and cache it.

    Actions, program order, synchronization order

    The model reasons about inter-thread actions: normal reads/writes of shared variables (instance fields, static fields, array elements — never locals, parameters or exception parameters), synchronization actions (volatile read/write, lock, unlock, thread start/termination detection, the synthetic first/last actions of a thread), external actions, and thread-divergence actions. Two accesses to the same variable conflict if at least one is a write. Each thread's actions have a program order; all synchronization actions of an execution have a total synchronization order consistent with each program order.

    synchronizes-with (§17.4.4) — the release/acquire pairs: an unlock of monitor m → every subsequent lock of m; a volatile write of v → every subsequent read of v; the action that starts a thread → its first action; the default-value write of every variable → the first action of every thread; the final action of T1 → any action that detects T1 terminated (join, isAlive); an interrupt → the point where it is detected. happens-before (§17.4.5) = program order ∪ synchronizes-with ∪ (constructor end → finalizer start), closed transitively. A data race is a pair of conflicting accesses not ordered by happens-before. A program is correctly synchronized iff all sequentially consistent executions are race-free — and then every execution appears sequentially consistent (§17.4.3/17.4.5).

    Happens-before explorer: which outcomes can a reader observe?

      

      A read r of v may see a write w if r does not happen-before w and no other write w' to v lies between them in happens-before. Note what this does not say: with no edges at all, a read may see a write that comes later in the execution order (Table 17.4.5-A, both reads seeing 0) — "happens-before consistency" alone would even allow values out of thin air (Table 17.4.8-A), which the causality requirements of §17.4.8 forbid by insisting an execution be built up from committed actions that never depend on a data race. A happens-before edge also does not force real-time ordering: reorderings are legal as long as no observation can tell.
      


      The derived rules you actually use
      

      • An unlock happens-before every subsequent lock of the same monitor — so everything the holder wrote is visible to the next holder. Lock.lock()/unlock() must provide the same effects (javadoc).
      • A volatile write happens-before every subsequent read of that field — and by transitivity everything the writer did before the write is visible to the reader after the read. This is the "flag" idiom; it costs nothing on the reader beyond a fresh load, but it does not make count++ atomic (read-modify-write is three actions; use AtomicInteger or a lock).
      • start() happens-before every action of the started thread; every action of a thread happens-before another thread's successful return from join() on it.
      • Default initialization happens-before everything — a field is never garbage, only stale.
      • Data races cannot corrupt array lengths, checked casts or virtual dispatch (§17.4.5): the JVM's own metadata is safe; only your variables are stale.
      • Word tearing is forbidden (§17.6): adjacent bytes of a byte[] written by different threads must not interfere. But a non-volatile long/double write may be split into two 32-bit halves (§17.7); volatile 64-bit values and all references are atomic.
      


      final fields: immutability without synchronization
      

      §17.5 gives final fields stronger semantics than happens-before alone. A freeze occurs when the constructor that writes the field exits. If a thread sees a reference to the object only after the constructor finished — even via a data race — it is guaranteed to see the correct value of the final fields, and versions of objects reachable through them at least as up to date as at the freeze. The usage model: set finals in the constructor and don't let this escape before the constructor returns. The spec's example: with final int x = 3; int y = 4; assigned in the constructor and f = new FinalFieldExample() in one thread, a reader that sees f != null is guaranteed f.x == 3 but may see f.y == 0. This is what makes String safe to share across a race (its fields are final; otherwise a racy reader could see a zero offset and compare "/tmp/usr".substring(4) equal to "/tmp"). Caveats: reflection can rewrite finals (a new freeze after each write, and reads may be reordered); finals initialized to constant expressions are inlined; System.in/out/err are "write-protected", treated as normal fields.
