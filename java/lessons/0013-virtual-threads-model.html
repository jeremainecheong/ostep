JEP 444 Virtual Threads (JDK 21, final) · java.lang.Thread API · Executors.newVirtualThreadPerTaskExecutor

Virtual threads: thread-per-request that scales

JEP 444's argument is economic. A server's throughput is bounded by how many requests it can have in flight, each request wants a thread for its whole duration, and OS threads are too expensive to have in the hundreds of thousands — so developers abandoned the readable thread-per-request style for asynchronous pipelines. Virtual threads are java.lang.Thread instances that the JDK, not the OS, schedules: cheap enough to never pool, plentiful enough to have a million, and — crucially — invisible to existing code that just calls blocking APIs. This lesson is JEP 444's model and its rules; the next opens the implementation.

Primary source: JEP 444, fetched in full (Ron Pressler & Alan Bateman): motivation (Little's Law), the 10,000-task example, "do not pool", scheduling (FIFO ForkJoinPool, carriers), pinning, memory/GC, API changes, observability. Also the Java 21 core-libs guide.

What you'll be able to do

    Why: Little's Law

    JEP 444: scalability is governed by Little's Law — for a given request latency, the number of requests being processed concurrently must grow in proportion to throughput. The JEP's numbers: 50 ms latency at 200 requests/s needs 10 concurrent requests; 2000 requests/s needs 100. Thread-per-request means threads must grow with throughput, but platform threads are wrappers around OS threads and "the number of threads often becomes the limiting factor long before other resources, such as CPU or network connections, are exhausted." Pooling avoids thread creation cost but does not raise the total.

    Little's Law: concurrency = throughput × latency

    The asynchronous alternative — return the thread to a pool while waiting for I/O, compose stages with callbacks or CompletableFuture — achieves the scaling but, the JEP argues, at a high price: it forsakes loops and try/catch, stack traces lose context, debuggers can't step through a request, profilers can't attribute cost, because the application's unit of concurrency (the pipeline) is no longer the platform's (the thread).

    What a virtual thread is

    A virtual thread is an instance of java.lang.Thread that is not tied to a particular OS thread; a platform thread is one implemented the traditional way as a thin wrapper around an OS thread. Virtual threads are user-mode threads with M:N scheduling (Java's 1990s green threads were M:1, platform threads are 1:1). When code in a virtual thread calls a blocking operation in the java.* API, the runtime performs a non-blocking OS call and suspends the virtual thread until it can resume; the OS thread it was using is freed for other virtual threads. To Java code, "virtual threads are simply threads that are cheap to create and almost infinitely plentiful."

    The JEP's example

    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000).forEach(i -> {
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1));
            return i;
        });
    });
}  // executor.close() waits for all tasks

    10,000 virtual threads sleeping one second run on "perhaps as few as one" OS thread and finish in about a second (~10,000 tasks/s). Executors.newCachedThreadPool() would try to create 10,000 OS threads and may crash; newFixedThreadPool(200) would take 50 seconds (~200 tasks/s). Change 10,000 to 1,000,000 and virtual threads still work: about a million tasks per second after warm-up.

    When they help — and don't

    Virtual threads improve throughput when (1) the number of concurrent tasks is high — more than a few thousand — and (2) the workload is not CPU-bound. "Virtual threads are not faster threads — they do not run code any faster than platform threads. They exist to provide scale (higher throughput), not speed (lower latency)." If each task computed for a second instead of sleeping, adding threads beyond the core count would help nobody.

    They are also not a data-parallelism construct: parallel streams remain the tool for processing large data sets in parallel (a non-goal of the JEP).

    The rules

    • Never pool virtual threads. Create one per task; most will be short-lived with shallow stacks. Pools exist to share expensive resources; virtual threads aren't expensive.
    • Don't use pools to limit concurrency to a resource that handles, say, 20 requests; use a Semaphore (or other constructs designed for it).
    • Be wary of ThreadLocal caching. A thread-local holding an expensive resource (a DB connection) made sense to share across tasks on a pooled thread; with a virtual thread per task it means one resource per task. Virtual threads do support thread-locals (a change from the previews), but with a million threads the memory adds up; -Djdk.traceVirtualThreadLocals=true prints where they are set. Scoped values (lesson 15) are often the better fit.
    • Blocking is fine — that's the point. Most blocking JDK operations unmount the virtual thread: sockets, BlockingQueue.take(), locks and LockSupport.park, Thread.sleep, Future.get.
    • Two exceptions capture the carrier: OS-level limits (many filesystem operations) and JDK-level ones (Object.wait()). The scheduler compensates by temporarily adding platform threads, up to jdk.virtualThreadScheduler.maxPoolSize.
    • Pinning: inside a synchronized block or method, or a native method/foreign function, a virtual thread cannot unmount; blocking there blocks the carrier and the scheduler does not compensate. Fix frequent, long-blocking cases by switching to ReentrantLock; infrequent or in-memory-only synchronized is fine. Diagnostics: the JFR event jdk.VirtualThreadPinned (enabled by default, 20 ms threshold) and -Djdk.tracePinnedThreads=full|short. (The JEP says the synchronized limitation may be lifted in a future release.)

    Scheduling and carriers

    The JDK's scheduler is a work-stealing ForkJoinPool in FIFO mode, distinct from the common pool (which runs parallel streams in LIFO mode). Its parallelism defaults to the number of available processors (jdk.virtualThreadScheduler.parallelism). The platform thread a virtual thread runs on is its carrier; the scheduler mounts a virtual thread on a carrier, and the thread unmounts when it blocks, after which the carrier takes another. There is no affinity and no time-sharing: a virtual thread is not preempted for using CPU, and it may resume on a different carrier. From Java code the carrier is invisible: Thread.currentThread() is the virtual thread; stack traces, thread dumps and thread-locals of the carrier and the virtual thread are separate. From native code both share one OS thread, so JNI may see different OS thread ids across calls. Virtual threads are not cooperative — code never yields explicitly — and must not assume how or when they are assigned to carriers.

    Memory, GC, observability

    A virtual thread's stack lives in the heap as stack chunk objects that grow and shrink; that is what makes a million threads affordable. They are not GC roots, so G1 and friends don't scan them in a stop-the-world pause. One current limitation: G1 doesn't support humongous stack chunks, so a stack reaching half a region (as small as 512 KB) may StackOverflowError. Overall the JEP expects heap and GC costs comparable to asynchronous code, since a million tasks need a million objects either way. Tooling: debuggers step through virtual threads; JFR attributes events correctly (new events VirtualThreadStart/End off by default, VirtualThreadPinned, VirtualThreadSubmitFailed); the new thread dump jcmd <pid> Thread.dump_to_file -format=json groups threads without pausing the application; ThreadMXBean and JVM TI's GetAllThreads cover platform threads only. And one flag to avoid: -XX:+PreserveFramePointer "has a drastic negative impact on virtual thread performance."
