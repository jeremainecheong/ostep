Generics: compile-time types, erased at run time

Java generics give you type-checked collections without changing the JVM: type parameters exist in the compiler and in Signature attributes, but erasure (§4.6) replaces them with their bounds in bytecode. That single design decision explains why List<String> is not a List<Object> (invariance), why wildcards exist (PECS), why new T[] and instanceof List<String> are illegal, why bridge methods appear in javap, and why an unchecked cast can produce a ClassCastException far from where it was written.

Primary sources: JLS §4.5 (parameterized types, §4.5.1 wildcards), §4.6 Type Erasure, §4.10 Subtyping, §8.4.8.3 (bridge methods), ch 18 Type Inference. "PECS" is Joshua Bloch's mnemonic for §4.10.2's wildcard subtyping.

What you'll be able to do

    Invariance and the reason for it

    §4.10.2: C<S> is a subtype of C<T> only if S and T are the same type (or via wildcards). List<String> is not a List<Object>: if it were, List<Object> o = strings; o.add(1); would put an Integer into a list of Strings, and unlike arrays there is no run-time check to catch it (erasure). Arrays are covariant and pay with ArrayStoreException; generics are invariant and pay nothing at run time.
    List<String> strings = new ArrayList<>();
List<Object> objects = strings;            // compile error: incompatible types
Object[] arr = new String[1];               // allowed (covariant arrays)
arr[0] = 1;                                 // ArrayStoreException at run time
List<? extends Number> nums = List.of(1, 2.5);   // wildcards restore useful subtyping
Number n = nums.get(0);                     // reading is fine: everything is at least a Number
// nums.add(3);                             // error: the capture type could be List<Double>

    Wildcards and PECS

    Producer → ? extends T

    A List<? extends Number> produces Numbers: get returns Number; add accepts only null, because the actual element type is unknown (could be Integer or Double). Use it for parameters you only read from: double sum(Collection<? extends Number> c).

    Consumer → ? super T

    A List<? super Integer> consumes Integers: add(Integer) is safe because the actual type is Integer or a supertype; get returns only Object. Use it for parameters you write to: void fill(List<? super Integer> sink). Comparators are consumers: Comparator<? super T>.

    ? alone (unbounded) means "some type": read as Object, write nothing — the right type for methods that don't care about the element type (void printAll(List<?> l)). A type parameter instead of a wildcard is needed when two positions must agree (<T> void copy(List<? super T> dst, List<? extends T> src) — Collections.copy's signature). Capture conversion (§5.1.10) gives each wildcard a fresh type variable so the compiler can reason about it; a "capture#1 of ?" error message is this mechanism showing through.

    Erasure (§4.6) and what it costs

    The erasure of a parameterized type is its raw type; of a type variable, the erasure of its leftmost bound (Object if none). Consequences, all from that rule:

    • new T(), new T[n], T.class, instanceof List<String>, catch (T e), static fields of type T — all illegal: T is not there at run time. List<String>.class does not exist; List.class does. Workarounds: pass a Class<T> token, Array.newInstance, or accept an unchecked cast.
    • Unchecked warnings mark the places where the compiler cannot prove safety (raw types, casts to a parameterized type). The ClassCastException then surfaces at the call site where the compiler inserted a checkcast — heap pollution: @SafeVarargs documents that a varargs method of type T... (erased to Object[]) does not store into the array.
    • Overloading on erasure is illegal: void f(List<String>) and void f(List<Integer>) have the same erased signature.
    • Bridge methods (§8.4.8.3): when a subclass overrides a generic method with a specialized signature, the compiler emits a synthetic method with the erased signature that casts and delegates, so overriding still works after erasure. javap shows it flagged synthetic bridge.
    • Reflection keeps the generic signatures in the Signature attribute (Method.getGenericReturnType), which is how frameworks like Jackson read List<String> from a field declaration — but never from a value.
    // source
class Box<T extends Comparable<T>> {
    T value;
    T get() { return value; }
    void set(T v) { value = v; }
}
class IntBox extends Box<Integer> {
    @Override void set(Integer v) { value = v * 2; }
}
    // after erasure (what the JVM sees)
class Box {
    Comparable value;              // leftmost bound
    Comparable get() { return value; }
    void set(Comparable v) { value = v; }
}
class IntBox extends Box {
    void set(Integer v) { value = v * 2; }
    /* synthetic bridge */ void set(Comparable v) { set((Integer) v); }
}

    Bounds, inference, and idioms

    • Bounds: <T extends Number & Comparable<T>> — a class bound first, then interfaces; erasure uses the leftmost. Recursive bound: <T extends Comparable<? super T>> T max(Collection<? extends T>) — the real signature of Collections.max, allowing subclasses whose superclass is the comparable one.
    • Inference (ch 18): the diamond new ArrayList<>(), generic method arguments, and lambdas are typed by inference from the target type — "poly expressions" (§15.2). List.of() in List<String> l = List.of(); infers String. Explicit witnesses Collections.<String>emptyList() exist for the rare ambiguous case.
    • Raw types exist for migration only; using one turns off checking for the whole expression. List vs List<?>: the wildcard is checked, raw is not.
    • Generic class vs generic method: a static method cannot use the class's type parameter (there is no instance) and declares its own <T>. Optional<T>, Comparator<T>, Function<T,R> are the everyday generic APIs; primitives are boxed (List<int> is illegal until Valhalla), hence IntStream/ToIntFunction specializations.
