Structured concurrency and scoped values: giving threads a shape

Once threads are cheap, the next problem is organizing them. ExecutorService lets a subtask outlive the method that started it, leak when the parent fails, and keep running after its result is no longer wanted. Structured concurrency (preview in 21) confines the lifetime of a group of subtasks to a syntax block, exactly as a sequential operation is confined, so failure, cancellation and observability follow the block structure. Scoped values (also preview) are the matching way to pass context down a call tree — and across those subtasks — without ThreadLocal.

Primary sources: the JDK 21u class documentation of StructuredTaskScope (basic operation, policies ShutdownOnSuccess/ShutdownOnFailure, extending via handleComplete, tree structure) and ScopedValue (bindings per thread, rebinding, inheritance), read from the sources; JEP 453 summary (StructuredTaskScope::fork returns Subtask, not Future, as of 21; incubated as JEP 428/437 in 19/20; still previewing through JDK 25+). Both require --enable-preview in 21.

What you'll be able to do

    The problem with unstructured concurrency

    With executor.submit the parent gets a Future and the subtask is on its own: if the parent throws, the subtask leaks; if one subtask fails, its siblings keep working uselessly unless you hand-cancel each; if the parent is interrupted, nothing propagates. Thread dumps show a flat list. The API doesn't express that these tasks belong together. Structured concurrency's principle (from the class docs): "the lifetime of a concurrent operation is confined by a syntax block, just like that of a sequential operation in structured programming."

    StructuredTaskScope

    // JDK 21 (--enable-preview): the class docs' basic pattern
try (var scope = new StructuredTaskScope<Object>()) {
    Subtask<String>  s1 = scope.fork(task1);   // starts a thread (virtual by default) per subtask
    Subtask<Integer> s2 = scope.fork(task2);
    scope.join();                              // wait for all subtasks (or shutdown)
    ... s1.get(), s2.get(), or s1.state() ...   // SUCCESS / FAILED / UNAVAILABLE
}                                               // close(): owner only; waits for any leftovers; StructureViolation if misused
    The contract (from the source's javadoc). The thread that creates the scope is its owner. Only the owner may fork, join, shutdown and close (WrongThreadException otherwise — subtasks may also fork, nesting scopes). join() must be called before reading results: close() throws IllegalStateException after closing if the owner never joined. shutdown() interrupts unfinished subtasks and prevents new forks; it is how a policy stops work that is no longer needed. close() is meant for try-with-resources; forking after close() fails. Scopes form a tree by nesting (a subtask that opens a scope makes it a child), which powers scoped-value inheritance, confinement checks ("threads contained in the task scope"), and the structured thread dump.

    Policies: what happens when subtasks finish

    ShutdownOnFailure captures the first exception and shuts the scope down — interrupting siblings and waking the owner — for the "all results required" case; after join(), throwIfFailed() rethrows (wrapped in ExecutionException, or mapped by a function). ShutdownOnSuccess captures the first successful result and shuts down the rest — "any result will do"; result() returns it or throws if every subtask failed. Both are StructuredTaskScope subclasses overriding handleComplete(Subtask), the hook you override for your own policy (the docs' CollectingScope example queues successful subtasks and guards its accessor with ensureOwnerAndJoined()). joinUntil(Instant) throws TimeoutException; the usual recipe then calls shutdown().

    // invoke-all with fail-fast, from the class docs
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<String>  user  = scope.fork(() -> findUser());
    Subtask<Integer> order = scope.fork(() -> fetchOrder());
    scope.join().throwIfFailed();                     // first failure cancels the other and propagates
    return new Response(user.get(), order.get());
}
// invoke-any
try (var scope = new StructuredTaskScope.ShutdownOnSuccess<String>()) {
    scope.fork(() -> fetch(left)); scope.fork(() -> fetch(right));
    scope.join();
    return scope.result(e -> new WebApplicationException(e));   // both failed → exception with causes
}

    Scoped values

    A ScopedValue is "an implicit method parameter": bound to a value for the dynamic scope of a method call — the call and everything it transitively calls — and unbound when the call completes, normally or abruptly. Compared to ThreadLocal: no set() (immutable binding), automatic unbinding (no remove() leaks), bounded lifetime, and cheap to inherit into child threads because there is nothing to copy — child threads created in a StructuredTaskScope see the parent's bindings. The docs stress the value should be immutable or synchronized, since several threads may read it.

    API (JDK 21)Meaning

    ScopedValue.runWhere(K, v, Runnable)run with K bound to v
    callWhere / getWheresame, returning a result (Callable / Supplier)
    ScopedValue.where(K, v).where(K2, v2).run(…)bind several keys via a Carrier

    Status and outlook

    In JDK 21 both are preview APIs (@PreviewFeature: javac --enable-preview --release 21, java --enable-preview); the class-file minor version 65535 (lesson 8) marks the result. JEP 453's one change from the incubator: fork returns Subtask rather than Future, removing the temptation to call cancel/get outside the structure. The API kept previewing after 21 (JEP 462, 480, 499, 505 — the last replacing public constructors with static factories and introducing Joiner), so expect names to differ in later JDKs; the principles — owner, join before results, shutdown-based cancellation, tree structure — are stable.
