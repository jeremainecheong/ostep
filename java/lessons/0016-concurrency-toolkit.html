The concurrency toolkit: monitors, locks, executors — and how to choose

Java gives you two lock families (intrinsic monitors and java.util.concurrent.locks), one synchronizer framework underneath most of the second (AQS), a handful of executor shapes, and — since 21 — virtual threads that change which shape to pick. This closing lesson of the concurrency track lays out the pieces with their exact semantics, then gives a decision procedure that respects both the memory model (lesson 7) and pinning (lessons 13–14).

Primary sources: JLS §17.1–17.3 (monitors, wait sets, sleep/yield — fetched); JDK 21u javadoc in the sources for AbstractQueuedSynchronizer ("first-in-first-out wait queues… a single atomic int value to represent state"), ReentrantLock (fairness), LockSupport (permits: at most one, don't accumulate; virtual-thread aware per JEP 444), ForkJoinPool (work stealing, asyncMode, common pool, ManagedBlocker), Executors; objectMonitor.hpp for inflation.

What you'll be able to do

    Intrinsic monitors

    synchronized uses the object's monitor (JLS §17.1): reentrant, released on any exit, no fairness, no timeout, no interruptible acquire. In HotSpot (lesson 12) an uncontended acquire is a CAS on the mark word; contention or wait() inflates to an ObjectMonitor with an entry list and a wait set. wait/notify/notifyAll (§17.2) implement condition waiting: call only while holding the lock, loop on the condition, prefer notifyAll unless every waiter is interchangeable. In JDK 21 a virtual thread blocking inside synchronized or in Object.wait() pins its carrier (the latter with compensation) — the main reason to prefer ReentrantLock around slow operations.

    AbstractQueuedSynchronizer. The framework beneath ReentrantLock, Semaphore, CountDownLatch, ReentrantReadWriteLock and the pre-JDK-8 FutureTask: a single atomic int state (getState/setState/compareAndSetState) whose meaning the subclass defines via tryAcquire/tryRelease (exclusive) and tryAcquireShared/tryReleaseShared, plus a FIFO wait queue (a CLH-lock variant) of blocked threads parked with LockSupport.park. For ReentrantLock, state = hold count and the owner is tracked in the AbstractOwnableSynchronizer superclass; for Semaphore, state = permits; for CountDownLatch, state = count. LockSupport is the primitive: each thread has at most one permit; park() consumes it or blocks (may return spuriously), unpark(t) makes it available — and since JEP 444 parking a virtual thread unmounts it. Write your own lock by extending AQS; never with wait/notify spin loops.

    Executors and pools

    Executors.newFixedThreadPool(n) (n platform threads, unbounded queue), newCachedThreadPool() (unbounded threads, 60 s idle timeout — the JEP's crash example at 10,000 tasks), newSingleThreadExecutor(), newScheduledThreadPool(n), newWorkStealingPool() (a ForkJoinPool), and JDK 21's newThreadPerTaskExecutor(factory)/newVirtualThreadPerTaskExecutor() (a ThreadPerTaskExecutor: no queue, no pool, a new thread per task; ExecutorService is AutoCloseable since 19 and close() waits). Behind the classic ones is ThreadPoolExecutor: core size, maximum size, keep-alive, a work queue and a RejectedExecutionHandler; threads beyond core are created only when the queue is full, so an unbounded queue never grows the pool — the classic surprise. ForkJoinPool is different: work-stealing per-worker deques (LIFO for fork/join recursion, FIFO in asyncMode for event-style tasks), a commonPool() sized to processors − 1 that runs parallel streams and CompletableFuture defaults, and ManagedBlocker to add compensation threads when a worker blocks — the same mechanism the virtual-thread scheduler uses. CompletableFuture composes asynchronous stages; with virtual threads it remains useful for fan-out/fan-in, but JEP 444's point is that plain blocking code in a virtual thread is now the simpler option.

    Decision procedure

    Correctness checklist (from the memory model)

    • Every shared mutable field is guarded by one policy — a lock, volatile, an atomic, or confinement — and the policy is documented (@GuardedBy in comments).
    • volatile gives visibility and ordering, not atomicity of compound actions; count++ needs AtomicInteger/LongAdder or a lock.
    • Immutable objects (final fields, no this escape) are free to share; prefer records.
    • Publish safely: through a lock, a volatile, a concurrent collection, or thread start/join; never via a plain field with a data race (except immutable objects).
    • Hold locks briefly; never call unknown code (listeners) while holding one; acquire multiple locks in a fixed global order.
    • Use ConcurrentHashMap.compute* and friends for atomic map updates instead of check-then-act.
    • Prefer higher-level constructs (executors, latches, queues) to raw threads and wait/notify; prefer ReentrantLock to synchronized around I/O when virtual threads are in play.
