Execution: the five invoke instructions and the frame they create

Every method call in Java compiles to one of five instructions, and the choice encodes what the language guaranteed at compile time: static dispatch, virtual dispatch, interface dispatch, special (constructor/super/private) dispatch, or — since Java 7 — a call whose target is decided at run time by a bootstrap method. Understanding invokedynamic explains how lambdas, string concatenation and pattern switches are compiled without new bytecodes.

What you'll be able to do

    Threads, stacks, frames

    Per thread (§2.5): a pc register (address of the current instruction; undefined inside native methods), a JVM stack of frames (which may be heap-allocated and non-contiguous — the spec deliberately allows this, and it is what makes virtual-thread stack chunks legal), and optionally a native method stack. Shared: the heap (all objects and arrays; GC-managed) and the method area (per-class structures, run-time constant pools, method code; logically part of the heap — HotSpot calls it Metaspace since JDK 8). Exhaustion: StackOverflowError for stacks, OutOfMemoryError for everything. A frame (§2.6) is created per invocation and destroyed on completion, normal or abrupt; it holds the local variable array, the operand stack, and a reference to its class's run-time constant pool for dynamic linking — symbolic references in the code are translated to concrete ones lazily, which is why changing a callee's class rarely breaks callers. Only one frame per thread is current; on normal completion the return value is pushed onto the invoker's operand stack; on abrupt completion nothing is returned and the exception propagates to the invoker's handlers.

A package-private method with the same signature in another package therefore does not override — a favourite interview trap that is really a run-time-package rule.

    invokedynamic and bootstrap methods
    

    An invokedynamic instruction references a CONSTANT_InvokeDynamic entry: a bootstrap method handle (from the BootstrapMethods attribute), a name, a method descriptor, and static arguments. On first execution (§5.4.3.6) the JVM builds the argument array [Lookup, name, MethodType, staticArgs…], invokes the bootstrap via invokeWithArguments, and validates the result: a non-null CallSite whose type matches the descriptor, else BootstrapMethodError. Resolution is per instruction (another instruction sharing the same constant-pool entry bootstraps separately), memoized, and if several threads race, one result wins. Afterwards each execution simply invokes the CallSite's target method handle — a ConstantCallSite is as fast as a direct call after JIT inlining. Bootstrap invocation initializes the bootstrap method's class (a REF_invokeStatic handle).
    

    Life of a lambda: Runnable r = () -> System.out.println(x);
    

    Why this design? Compiling a lambda to an inner class would fix the strategy forever in class files; invokedynamic defers it to the JDK's LambdaMetafactory, which today spins a hidden class per lambda site and could change tomorrow without recompiling. The same trick powers StringConcatFactory (JEP 280, Java 9: "a" + b becomes one invokedynamic whose bootstrap builds an optimal concatenation recipe), ObjectMethods (records' equals/hashCode/toString), and SwitchBootstraps.typeSwitch/enumSwitch (pattern matching for switch, JEP 441). Method handles (§5.4.3.5) are the currency: nine kinds mirror bytecode behaviours (getField, getStatic, putField, putStatic, invokeVirtual, invokeStatic, invokeSpecial, newInvokeSpecial, invokeInterface), resolved with the same access checks as the equivalent bytecode; MethodHandle.invokeExact has exactly the stack effect of that bytecode. Dynamically-computed constants (CONSTANT_Dynamic, JDK 11) use the same bootstrap mechanism for ldc.
