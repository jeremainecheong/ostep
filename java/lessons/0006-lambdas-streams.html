Lambdas, method references, and streams

A lambda is not an anonymous class in disguise: the JLS makes it a poly expression whose type comes from the context, and the JVM compiles it through invokedynamic with no class file (lesson 10). Streams build on lambdas to describe data pipelines that are lazy until a terminal operation runs. This lesson is about the rules that make both predictable: target typing, effectively final capture, the stream pipeline model, and where parallel streams help.

Primary sources: JLS §15.27 Lambda Expressions (§15.27.2 body, §15.27.3 type, §15.27.4 run-time evaluation), §15.13 Method References, §9.8, the java.util.stream package summary (laziness, non-interference, statelessness, ordering, parallelism) and java.util.function.

What you'll be able to do

    Lambdas as specified

    • Target typing (§15.27.3): a lambda has no type of its own; it is compatible with a functional interface (§9.8: exactly one abstract method) inferred from the assignment, argument, return or cast context. Runnable r = () -> {}; and Callable<Void> c = () -> null; differ only by target. Overloads that accept different functional interfaces can be ambiguous; an explicit cast or typed parameters disambiguate.
    • Body rules (§15.27.2): parameters may be typed, inferred, or var (to attach annotations); local variables of the enclosing scope may be used only if effectively final — never reassigned — so captured values are copies, not shared variables; the body's this is the enclosing instance (unlike anonymous classes); lambda parameters may not shadow enclosing locals.
    • Run-time evaluation (§15.27.4): "either a new instance of a class with the properties below is allocated and initialized, or an existing instance … is referenced" — the identity of the object is unspecified. In practice javac desugars the body to a private synthetic method and emits invokedynamic bound to LambdaMetafactory, which spins a hidden class at first use; a non-capturing lambda evaluates to a single cached instance.
    • Exceptions: a lambda can throw checked exceptions only if its functional interface's method declares them — hence the ubiquitous wrapping in UncheckedIOException or custom ThrowingFunction interfaces.

    Method references (§15.13)

    Four forms, each equivalent to a lambda with the same target type: Type::staticMethod (Integer::parseInt ≡ s -> Integer.parseInt(s)); expr::instanceMethod — bound receiver, evaluated once when the reference is created (System.out::println); Type::instanceMethod — unbound, the first parameter becomes the receiver (String::length ≡ s -> s.length()); Type::new / int[]::new constructors. Resolution follows the overload rules with the functional interface's parameter types; Integer::compare vs Integer::compareTo both typecheck as Comparator<Integer> (static two-arg vs unbound one-arg).

    Streams: the pipeline model

    From the package summary: a stream pipeline is a source, zero or more intermediate operations (which are lazy and return a new stream), and one terminal operation that triggers execution and consumes the stream. Streams are not data structures, are single-use, and process elements one at a time through the whole pipeline — not stage by stage. Behavioural parameters must be non-interfering (don't modify the source) and, for predictable results, stateless; side effects are discouraged; some operations (sorted, distinct) are stateful and may buffer.

    Watch elements flow one at a time

    List.of(1, 2, 3, 4, 5, 6).stream()
    .filter(n -> { log("filter " + n); return n % 2 == 0; })
    .map(n -> { log("map " + n); return n * 10; })
    .limit(2)                       // short-circuits
    .forEach(n -> log("consume " + n));
    • Sources: Collection.stream(), Stream.of, Arrays.stream, IntStream.range, Stream.iterate/generate (infinite; needs limit/takeWhile), Files.lines, String.chars, Random.ints.
    • Intermediate: filter map flatMap mapMulti(16) distinct sorted peek limit skip takeWhile dropWhile boxed mapToInt. Terminal: forEach collect reduce count sum min max anyMatch allMatch noneMatch findFirst findAny toList(16) toArray iterator. Short-circuiting ones (limit, findFirst, anyMatch) can finish infinite streams.
    • Collectors: toList (mutable, vs Stream.toList() unmodifiable), toSet, toMap(k, v, merge) (throws on duplicate keys without a merge function), groupingBy(classifier, downstream), partitioningBy, joining, counting, summingInt, teeing (12). reduce(identity, accumulator, combiner) must be associative for parallel correctness.
    • Ordering: an ordered stream (List, arrays, sorted) preserves encounter order through operations like map and into ordered collectors; HashSet sources are unordered; unordered() can speed up parallel distinct/limit; forEachOrdered vs forEach.
    • Parallel: parallelStream()/parallel() splits the source with a Spliterator and runs on the common ForkJoinPool (LIFO work-stealing, parallelism = cores − 1 by default; the virtual-thread scheduler in lesson 14 is a separate FIFO pool). Worth it only for large, cheaply splittable sources (ArrayList, arrays, ranges) with CPU-heavy, stateless, non-interfering operations; LinkedList, iterate, and I/O-bound work parallelize badly. Correctness needs associative reductions and thread-safe collectors (collect's three-argument form handles the merging).
    record Emp(String name, String dept, double salary) {}
Map<String, Double> avgByDept = emps.stream()
    .collect(Collectors.groupingBy(Emp::dept, TreeMap::new, Collectors.averagingDouble(Emp::salary)));
Optional<Emp> top = emps.stream().max(Comparator.comparingDouble(Emp::salary));
List<String> names = emps.stream().filter(e -> e.salary() > 50_000).map(Emp::name).sorted().toList();
int total = IntStream.rangeClosed(1, 100).filter(i -> i % 3 == 0).sum();       // no boxing
String csv = Stream.of("a", "b", "c").collect(Collectors.joining(",", "[", "]"));   // "[a,b,c]"
long evens = Stream.iterate(0, i -> i + 2).takeWhile(i -> i < 20).count();        // infinite source, bounded

    Optional

    Optional<T> is a value container for "may be absent" return values — the API notes it is not meant for fields or parameters. Prefer map/flatMap/filter/orElse/orElseGet/orElseThrow/ifPresentOrElse over isPresent + get; orElse(expensive()) always evaluates its argument, orElseGet doesn't. Primitive variants OptionalInt etc. avoid boxing.
