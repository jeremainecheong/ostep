Expressions, exceptions, and the new switch

Three things the JLS pins down that other languages leave loose: the exact left-to-right evaluation order of every expression, the checked/unchecked exception discipline with try's precise semantics, and — since Java 21 — switch as a full pattern-matching construct with type patterns, record patterns, guards, null handling, dominance rules and compile-time exhaustiveness. This lesson uses JEP 441's own examples, fetched from the JEP text.

Primary sources: JLS ch 15 (§15.7 Evaluation Order, §15.7.1 left operand first, §15.7.4 argument lists), §14.20 try, ch 11 Exceptions (§11.1.1 kinds, §11.2 compile-time checking), JEP 441 and JEP 440 (text read from the JDK bug tracker mirror).

What you'll be able to do

    Evaluation order (§15.7)

    "The Java programming language guarantees that the operands of operators appear to be evaluated in a specific evaluation order, namely, from left to right." The left operand is fully evaluated before any part of the right (§15.7.1) — including saving its value before a side effect on the right changes the variable: i = 2; j = (i = 3) * i; gives 9, and a[i] = i = 3 uses the old i for the index (§15.26.1 evaluates the array reference and index first). Arguments are evaluated left to right, all of them, before the invocation (§15.7.4). Operands are evaluated before the operation (§15.7.2) — so x / 0 evaluates x before throwing. Only &&, ||, ?: and switch skip operands.
    int i = 2;
int j = (i = 3) * i;             // 9: left operand assigns 3, then right reads 3
int k = i + (i = 10);            // 13: left operand's value 3 was saved before the assignment
int[] a = {0, 0, 0};
int n = 1; a[n] = n = 2;         // a[1] = 2: index evaluated before the right-hand side
String s = null;
System.out.println(s + "!" + 1 / 0);   // ArithmeticException: operands left to right, then the operator

    Exceptions (ch 11) and try (§14.20)

    CheckedThrowable minus RuntimeException and Error subclasses (§11.1.1). A method must declare them in throws or catch them (§11.2); the compiler verifies. For recoverable conditions the caller can be expected to handle (IOException).
    Unchecked: RuntimeExceptionProgramming errors and precondition violations: NullPointerException (with helpful messages since 14), IllegalArgumentException, ClassCastException, IndexOutOfBounds, ArithmeticException, MatchException (21).
    Unchecked: ErrorSerious problems the program should not catch: OutOfMemoryError, StackOverflowError, LinkageError family (lesson 9), AssertionError.
    • try/catch/finally (§14.20): catch clauses are tried in order and a clause catching a superclass may not precede one catching its subclass (unreachable → compile error, the same "dominance" idea as pattern switch). Multi-catch catch (A | B e) makes e implicitly final. finally runs whenever the try block or a catch completes, normally or abruptly; a return/throw in finally overrides the try's completion (§14.20.2 — the reason for the "return in finally" warning).
    • try-with-resources (§14.20.3): resources (AutoCloseable, effectively final variables allowed since 9) are closed in reverse order of initialization, even on exceptions; an exception from close() during exception propagation is attached as a suppressed exception (getSuppressed()), while the primary one propagates. Translation: nested try/finally per resource.
    • Precise rethrow (§11.2.2): catch (Exception e) { throw e; } may declare only the checked types the try body can throw, if e is effectively final. Exceptions chain with a cause; stack traces are captured at construction (fillInStackTrace), which is the cost of using exceptions for control flow.

    Pattern matching for switch (JEP 441) and record patterns (JEP 440)

    Java 21 finalizes the feature previewed since 17. Selector: any reference type, or char/byte/short/int (no long/float/double/boolean yet). Case labels: constants, case null (optionally case null, default), and patterns — type patterns Integer i, record patterns Point(int x, var y) (nested arbitrarily, JEP 440), optionally with a guard when expr. Rules from the JEP:

    • First applicable label wins, top to bottom. A label dominated by an earlier one is a compile error: case CharSequence cs before case String s; an unguarded pattern dominates the same guarded pattern; a pattern label dominates constants of its type (case Integer i before case 42). Recommended order: constants → guarded patterns → unguarded patterns. Only one match-all (default or an unconditional pattern).
    • Exhaustiveness is required for every switch expression, and for switch statements that use patterns or null labels or a non-legacy selector type. Sealed hierarchies and enums count as covered without default — the JEP argues an exhaustive switch without a match-all clause is better, because a new subtype then fails compilation instead of running silently. The compiler adds a synthetic default that throws MatchException for separately-compiled drift; enum switch expressions now throw MatchException rather than IncompatibleClassChangeError.
    • null: case null matches null; without it the switch throws NullPointerException as before — default does not match null.
    • Scope of pattern variables is flow-sensitive: the guard and the rule body; falling through into a label that declares a pattern variable is a compile error, so case A a, B b is not allowed. A guard that throws, or a record accessor that throws inside a pattern, makes the switch throw (MatchException for the accessor case).

    Which label applies? (from JEP 441's examples)

    static String test(Object obj) {
    return switch (obj) {
        case null            -> "null!";
        case -1, 1           -> "special int";
        case Integer i
             when i > 0      -> "positive int";
        case Integer i       -> "other int";
        case String s
             when s.isEmpty()-> "empty string";
        case String s        -> "string";
        case CharSequence cs -> "char sequence";
        default              -> "something else";
    };
}
    sealed interface Shape permits Circle, Rect {}
record Circle(double r) implements Shape {}
record Rect(Point tl, Point br) implements Shape {}
record Point(int x, int y) {}
double area(Shape s) {
    return switch (s) {                                            // exhaustive via permits — no default
        case Circle(double r) when r == 0 -> 0;                    // record pattern + guard
        case Circle(var r)               -> Math.PI * r * r;       // var in a record pattern
        case Rect(Point(var x1, var y1), Point(var x2, var y2)) -> Math.abs((x2 - x1) * (y2 - y1));   // nested
    };
}

    Switch details worth knowing

    Arrow form (case X ->) never falls through; the colon form does, and pattern labels forbid fall-through into them. A switch expression must complete with a value via -> expr, a block with yield, or throw. Enum constants may be written qualified (case Suit.HEARTS) and the selector may be a supertype of the enum (JEP 441). String switches compare with equals after hashing (compiled to hashCode lookupswitch + equals); pattern switches compile to invokedynamic on SwitchBootstraps.typeSwitch (lesson 10).
