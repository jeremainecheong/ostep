Inside a virtual thread: a continuation, a state machine, a scheduler

Strip away the API and a virtual thread is three things: a Continuation that can be run, yielded and resumed (its frames copied between the carrier's stack and heap stack chunks by HotSpot's freeze/thaw code); a small state machine in VirtualThread.java that decides when to yield and what to do if it can't; and a ForkJoinPool whose worker threads are the carriers. Everything in lesson 13 — mount/unmount, pinning, compensation, parking — is a path through these three.

Primary sources: read directly from the JDK 21u tree — VirtualThread.java (state constants and transition comment, createDefaultScheduler, runContinuation, mount/unmount, park/parkNanos/parkOnCarrierThread), Continuation.java (run, yield, Pinned, onPinned), CarrierThread.java, and the design comment at the top of continuationFreezeThaw.cpp (budgets, fast/slow paths, stack layout). Names and numbers below are the source's.

What you'll be able to do

    The scheduler, as constructed

    // VirtualThread.createDefaultScheduler() — JDK 21
ForkJoinWorkerThreadFactory factory = pool -> new CarrierThread(pool);   // CarrierThread extends ForkJoinWorkerThread
parallelism = jdk.virtualThreadScheduler.parallelism ?? Runtime.getRuntime().availableProcessors();
maxPoolSize = jdk.virtualThreadScheduler.maxPoolSize ?? max(parallelism, 256);
minRunnable = jdk.virtualThreadScheduler.minRunnable ?? max(parallelism / 2, 1);
boolean asyncMode = true;                                                 // FIFO
new ForkJoinPool(parallelism, factory, handler, asyncMode, 0, maxPoolSize, minRunnable, pool -> true, 30, SECONDS);

    So: carriers are ForkJoinWorkerThreads; FIFO ("asyncMode") so the oldest runnable virtual thread goes first; the pool may grow beyond parallelism up to maxPoolSize (default ≥ 256) for compensation when a carrier is captured (e.g. file I/O uses ForkJoinPool.managedBlock); idle carriers die after 30 s. A separate ScheduledThreadPoolExecutor ("unparker", jdk.unparker.maxPoolSize) implements timed parking by scheduling an unpark. Submitting a virtual thread means submitting its runContinuation task: from a carrier it goes to the worker's local queue, otherwise to an external submission queue.

    The state machine

    States from VirtualThread.java (values are the source's)

    The transition comment in the source, verbatim in structure: NEW → STARTED (start, schedule to run) → RUNNING (first run) → TERMINATED. RUNNING → PARKING (park); PARKING → PARKED when cont.yield succeeds (unmounted), or → PINNED when it fails ("parked indefinitely on carrier"); PARKED → UNPARKED (unmounted but runnable) → RUNNING; PINNED → RUNNING on the same carrier. The TIMED_ variants mirror this for parkNanos. RUNNING → YIELDING → YIELDED (yield succeeded; will be rescheduled) or back to RUNNING. A SUSPENDED bit (1 << 8) is OR'd in by debuggers. The state field is volatile and read by the VM.

    Mount, run, unmount: runContinuation()

    The carrier's task. runContinuation() throws WrongThreadException if called from a virtual thread. It CASes the state from STARTED/UNPARKED/YIELDED to RUNNING (consuming the park permit when coming from UNPARKED), calls mount() — record the carrier, transfer the interrupt status, and carrier.setCurrentThread(this), which is what makes Thread.currentThread() answer with the virtual thread — then cont.run(). When run() returns, the continuation either finished or yielded: unmount() restores carrier.setCurrentThread(carrier), clears the carrier reference and interrupt, and then afterDone() or afterYield() decides the next state (PARKED/YIELDED, or immediately resubmit if an unpark raced in).

    Parking: park() returns at once if a permit is available or the thread is interrupted; otherwise it sets PARKING and calls yieldContinuation() → Continuation.yield(VTHREAD_SCOPE). If the yield succeeds, control returns to runContinuation on the carrier — the virtual thread's frames are now in the heap. If it fails (pinned), the state goes back to RUNNING and parkOnCarrierThread() blocks the carrier with Unsafe.park, emitting the VirtualThreadPinnedEvent (the JFR event from lesson 13). parkNanos first schedules an unpark on the unparker pool and cancels it afterwards. Unparking CASes PARKED → UNPARKED and submits runContinuation again; for a PINNED thread it simply unparks the carrier.

    Continuations and freeze/thaw

    jdk.internal.vm.Continuation (internal API; the language never exposes it) wraps a Runnable in a ContinuationScope. run() enters it (enterSpecial), yield(scope) suspends the innermost continuation of that scope; isDone(); and the Pinned enum names the reasons a yield can fail: NATIVE (a native frame on the stack), MONITOR (a monitor held — synchronized), CRITICAL_SECTION. onPinned defaults to throwing IllegalStateException("Pinned: …"); VirtualThread overrides it to return false from the yield so park() can fall back to parking the carrier.

    Freeze: copying frames into a stack chunk

    The HotSpot side (continuationFreezeThaw.cpp) is "very latency-critical and very hot": freeze runs on every I/O, every j.u.c lock acquisition, every queue take, and thaw possibly several times per blocking call because the return barrier thaws frames lazily as the code returns into them. The budget is ~100–150 ns per operation. The fast path applies when all frames are compiled and the chunk needs no GC barriers: frames are simply memcpy'd into the chunk (or out of it) and the bottom-most frame is patched (its return address becomes the return barrier). The slow path handles interpreted frames (internal pointers must be made relative in the chunk and absolute again on thaw) and GC barriers. The stack layout: carrier frames, then Continuation.run, then the enterSpecial frame holding a ContinuationEntry (argsize, the continuation and chunk oops, a parent entry), then the continuation's frames down to the yield stub; freeze copies everything below the entry. Stack chunks are ordinary heap objects (jdk.internal.vm.StackChunk), which is why the stacks can grow, are not GC roots, and why the G1 humongous limitation exists.

    Why this design

    JEP 444's alternatives section explains the choices: async/await coroutines were rejected because they would split the world into thread APIs and coroutine APIs and require rewriting tooling; a brand-new user-mode-thread class was prototyped but foundered on Thread.currentThread() being used pervasively (lock ownership, thread-locals) — so virtual threads had to be Threads, and the carrier's currentThread had to be switched on mount. Delimited continuations were the enabling primitive precisely because they let existing blocking code suspend without being rewritten.
