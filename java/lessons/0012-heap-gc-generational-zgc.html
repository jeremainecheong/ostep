Objects on the heap, and the collectors that manage them

The JVMS mandates only that there is a shared heap reclaimed by a garbage collector; HotSpot decides the rest. Every object begins with a two-word header whose bit layout is documented in markWord.hpp; the heap is divided among collectors you choose by flag, defaulting to G1 on a server-class machine; and JDK 21 ships the first Generational ZGC, a concurrent collector whose pauses stay under a millisecond by putting metadata into the pointers themselves. This lesson goes from the header bits to the barrier design of JEP 439.

Primary sources: HotSpot JDK 21u markWord.hpp (the bit-format comment), oop.hpp (header fields), objectMonitor.hpp, gcConfig.cpp + os.cpp (default GC and server-class rule); JVMS §2.5.3; JEP 439 Generational ZGC (full text fetched: goals, colored pointers, load/store barriers, remembered-set bitmaps, dense regions); JEP 444 for stack chunks; java.lang.ref sources.

What you'll be able to do

    The object header

    oop.hpp: an object is a markWord _mark followed by _metadata — a Klass* or, with compressed class pointers (default), a 32-bit narrowKlass; then the fields, laid out by the JVM (not in declaration order; 8-byte alignment; arrays add a length). The 64-bit mark word (markWord.hpp): unused:25 | hash:31 | unused:1 | age:4 | unused:1 | lock:2. The identity hash is generated lazily on the first hashCode()/identityHashCode call and stored here (which is why hashing an object then locking it forces monitor inflation); age counts survived young collections for tenuring; the two lock bits encode the states below.

    Allocation and the generational hypothesis

    Allocation is a pointer bump inside a thread-local allocation buffer (TLAB), so new is cheap; large objects go straight to old/humongous space. All HotSpot collectors except non-generational ZGC are generational: most objects die young, so the young generation (eden + survivor spaces, or young regions) is collected often and cheaply by copying live objects and bumping their age; survivors are tenured into the old generation after enough collections. Old-generation collection needs to know which old objects point at young ones without scanning the whole old generation — a remembered set, maintained by a write barrier on every reference store (card table in Serial/Parallel/G1: one byte per 512-byte card dirtied on a store; G1 also needs a memory fence there, as JEP 439 notes). Roots are the thread stacks, static fields, JNI handles… except that, per JEP 444, virtual-thread stacks live in heap stack chunk objects and are not roots.

    Region-based young collection (G1 / Generational ZGC style)

    green = young (eden/survivor), yellow = old, red = humongous, grey = free. Allocate fills young regions; a young collection copies survivors and frees the rest.

    The collectors in JDK 21

    CollectorFlagCharacter
    Serial-XX:+UseSerialGCSingle-threaded, stop-the-world; the default on non-server-class machines (fewer than 2 processors or less than 2 GB, os.cpp); smallest footprint (containers, CLIs).
    Parallel-XX:+UseParallelGCMulti-threaded stop-the-world young and old; maximizes throughput, tolerates long pauses (batch jobs).
    G1-XX:+UseG1GCDefault on server-class machines (gcConfig.cpp: select_gc_ergonomically). Heap split into equal regions; concurrent marking of the old generation, incremental evacuation choosing the regions with the most garbage first ("garbage first"), pause-time goal (-XX:MaxGCPauseMillis, default 200 ms); humongous objects (≥ half a region) get their own regions — the reason a virtual thread's stack chunk reaching half a region may StackOverflowError (JEP 444).
    ZGC (non-generational)-XX:+UseZGCConcurrent everything (marking, relocation, reference processing); pauses in microseconds independent of heap size; heaps from hundreds of MB to many TB; but collects all objects every cycle, so it needs headroom to outrun allocation.
    Generational ZGC (JEP 439)-XX:+UseZGC -XX:+ZGenerationalNew in 21; young and old generations collected independently and concurrently; pauses < 1 ms; no tuning of generation sizes, thread counts or tenuring. (Default ZGC mode in 23 via JEP 474; non-generational removed in 24, JEP 490.)
    Shenandoah-XX:+UseShenandoahGCConcurrent compacting collector from Red Hat, in some distributions.

    Inside Generational ZGC

    Colored pointers (JEP 439). A reference stored in a heap field is a 64-bit colored pointer: the object address in the high bits plus metadata bits in the low bits saying what is currently known about it (marked? address correct? remembered?). References in registers and on stacks are colorless. The conversion happens in barriers: the load barrier, injected where a reference field is loaded, strips the color and, if the object was relocated, updates the stale pointer (one shift instruction on x64 both tests "good color" and strips it); the new store barrier, injected where a reference field is written, colors the new value, records the field in the remembered set (old→young pointers), and reports the overwritten value for SATB marking. Both have a JIT-inlined fast path, a medium path (a store-barrier buffer) and a C++ slow path, and act at most once per field between marking phases; global phase values are patched into the code as immediates.

    Removing the old multi-mapped memory trick lets ZGC add metadata bits without shrinking the maximum heap (it was capped at 16 TB) and stops reported heap usage tripling.

    Other design points from the JEP: the remembered set is double-buffered bitmaps per old region, precise to the field, swapped atomically at each young-collection start so mutators never wait and no fence is needed (unlike card tables); young collections are two-pass — mark fully, then relocate — so no to-space must be pre-reserved and relocation can even compact in place, which lets ZGC run with smaller heaps; dense regions are aged in place instead of copied; large objects can be allocated in the young generation; old-generation marking finds young→old references by running a young collection alongside; an explicit System.gc() first promotes everything so weak references and class unloading behave as expected. The JEP's Cassandra example: a quarter of the heap and four times the throughput of non-generational ZGC, with pauses under 1 ms.

    References, finalization, cleaners

    java.lang.ref: soft references are cleared under memory pressure (caches), weak references as soon as no strong reference remains (WeakHashMap, canonicalizing maps), phantom references are enqueued after the object is finalizable and are the basis of Cleaner, the replacement for finalize() (deprecated for removal since JDK 18, JEP 421) — finalizers run on a dedicated thread, at an unknown time, can resurrect objects and slow allocation. Use try-with-resources for deterministic cleanup and Cleaner as a safety net.
