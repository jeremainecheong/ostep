Language Reference §5 The import system

The import system: a cache, a list of finders, and a spec

import x is two operations: find the module and bind the result to a name. Everything in between is public machinery — sys.modules as the cache, sys.meta_path as the list of finders, a module spec describing what was found, and a loader that creates and executes the module. Knowing this order explains circular imports, why __init__.py matters (and when it doesn't), and how -m, relative imports and .pyc files behave.

What you'll be able to do

    Modules and packages

    There is only one kind of module object. A package is a module with a __path__ attribute; it can contain submodules. A regular package is a directory with __init__.py, which is executed when the package is imported (importing parent.one executes parent/__init__.py then parent/one/__init__.py). A namespace package (PEP 420) has no __init__.py: it is a composite of portions that may live in different directories (or zip files), its __path__ is a custom iterable recomputed on demand, and a subdirectory without __init__.py inside a regular package is treated as one. Importing a submodule always imports its parents first; a failure anywhere is ModuleNotFoundError.

    The search, in order

    1. sys.modules — the cache, checked first; a hit returns immediately. Deleting an entry forces a fresh search next time (but existing references keep the old object). Setting sys.modules['x'] = None makes importing x raise ModuleNotFoundError. 2. sys.meta_path — a list of meta path finders, each asked find_spec(name, path, target) in turn; path is None for top-level imports and parent.__path__ for submodules. The defaults: the built-in importer, the frozen importer, and the path based finder. A finder returns a ModuleSpec or None ("not mine"); if all return None, ModuleNotFoundError. 3. Loading — the spec's loader creates and executes the module.

    Walk import parent.one with a cold cache

    # the reference's approximation of loading (§5.4)
module = None
if spec.loader is not None and hasattr(spec.loader, 'create_module'):
    module = spec.loader.create_module(spec)      # may return None → default ModuleType
if module is None:
    module = ModuleType(spec.name)
_init_module_attrs(spec, module)                  # __name__, __loader__, __package__, __spec__, __path__, __file__, __cached__
if spec.loader is None: raise ImportError         # unsupported
if spec.origin is None and spec.submodule_search_locations is not None:
    sys.modules[spec.name] = module               # namespace package: nothing to execute
elif not hasattr(spec.loader, 'exec_module'):
    module = spec.loader.load_module(spec.name)   # legacy loaders
else:
    sys.modules[spec.name] = module               # inserted BEFORE executing
    try:
        spec.loader.exec_module(module)
    except BaseException:
        try: del sys.modules[spec.name]           # failed import leaves no trace
        except KeyError: pass
        raise
return sys.modules[spec.name]

    Two consequences the reference draws out. The module sits in sys.modules before its code runs, so a module that (directly or indirectly) imports itself gets the partially initialized object instead of recursing — which is exactly how circular imports "work" and why from a import name can fail with ImportError: cannot import name while import a succeeds. And a failed import removes the entry, so a retry re-executes the module. After loading, the submodule is also bound as an attribute of its parent package.

    The path based finder

    The default third finder searches an import path: sys.path for top-level modules, parent.__path__ for submodules. For each path entry it consults sys.path_importer_cache, and on a miss calls each hook in sys.path_hooks to obtain a path entry finder for that kind of entry (directories → FileFinder; zip files → zipimport). Path entry finders know how to find .py source, .pyc bytecode and extension modules (.so/.pyd). Bytecode is cached in __pycache__/name.cpython-313.pyc (PEP 3147); by default the cache is validated by the source's mtime and size stored in the .pyc header, or optionally by a hash of the source (PEP 552, "checked"/"unchecked" hash-based pycs). The whole finder is pluggable: put your own finder on sys.meta_path or your own hook on sys.path_hooks.

    Relative imports and __main__

    Relative imports

    from . import x, from ..pkg import y: leading dots count parent packages, resolved against __package__ (or __spec__.parent). Only the from form is allowed. Running a file directly makes it __main__ with __package__ empty, so relative imports fail with "attempted relative import with no known parent package" — run it as python -m pkg.mod instead.

    __main__.__spec__

    With -m, __main__.__spec__ is the spec of the module actually run and __package__ is set, so relative imports work. For the interactive prompt, -c, stdin, or a file/directory path, __spec__ is None — even if the file could technically have been imported.

    Module attributes and importlib

    Import-related attributes set from the spec: __name__, __spec__ (name, loader, origin, submodule_search_locations, cached, parent), __loader__, __package__, __path__ (packages only), __file__/__cached__ (optional). importlib.import_module() is the programmatic import; importlib.reload() re-executes a module in place; importlib.util.find_spec() locates without loading; importlib.invalidate_caches() after creating files at runtime. A module's __getattr__/__dir__ (PEP 562) customize attribute access at module level — used for lazy submodule loading and deprecations.
