Everything is an object: identity, type, value

The Python Language Reference opens its data model with one sentence that explains half of the language's behaviour: every object has an identity, a type and a value. Names are not objects; they refer to objects. Get this model exactly right and mutability, aliasing, is vs ==, and hashing all follow.

Primary source: §3.1 Objects, values and types and §3.2 The standard type hierarchy of The Python Language Reference, 3.13. Every claim below is paraphrased from that text; the code blocks run real CPython (compiled to WebAssembly) in your browser.

    The three properties of an object

    The spec, compressed. Identity never changes once an object exists — think of it as the address (in CPython, id(x) literally is the memory address). Type determines which operations the object supports and which values it can have; it is also unchangeable. Value may change for mutable types (list, dict) and cannot for immutable ones (numbers, strings, tuples). Mutability is a property of the type.

    Two subtleties the reference spells out. First, an immutable container holding a mutable object: the tuple's value "changes" when the inner list changes, yet the tuple is still immutable — mutability refers only to the identities of the immediately contained objects. Second, names: a = 1; b = 1 may or may not make a and b the same object (int is immutable, so the implementation is free to reuse the object), whereas c = []; d = [] are guaranteed to be two distinct new lists, and e = f = [] binds two names to one list.

    Garbage collection, as the spec sees it

    Objects are never explicitly destroyed; when they become unreachable they may be collected. The reference deliberately leaves this to implementation quality — CPython uses reference counting plus optional delayed detection of cyclic garbage, and "other implementations act differently and CPython may change." Hence the rule: do not depend on immediate finalization; release external resources (files, sockets) explicitly with close(), or structurally with with / try…finally. Note too that debugging facilities, and a caught exception (its traceback holds frames), can keep objects alive longer than you expect. Lesson 13 opens the hood on how CPython actually does it.

    Equality, identity, hashing

    is compares identity; == asks the type (__eq__). The contract in §3.3.1: objects that compare equal must have the same hash, so a class that defines __eq__ without __hash__ has its hash set to None and becomes unhashable — otherwise dicts and sets would break. Hash randomization for str/bytes is on by default (see PYTHONHASHSEED), so hashes differ between runs. Dictionaries preserve insertion order (guaranteed since 3.7; CPython 3.6 did it as an implementation detail).
