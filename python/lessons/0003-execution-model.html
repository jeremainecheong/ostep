Language Reference §4 Execution model

Names, scopes, closures — and the exceptions that cross them

Python has no declarations, yet every name in a block is classified at compile time as local, global or free. That one design choice explains UnboundLocalError, why global and nonlocal exist, why class bodies are weird, and how closures capture variables. §4 is short; almost every line is load-bearing.

What you'll be able to do

    Blocks, binding, and the compile-time rule

    A block is a piece of code executed as a unit: a module, a function body, a class definition (also each interactive command, a script, -c argument, or the string passed to exec/eval). Names are introduced by binding operations: parameters, import, class and function definitions, assignment targets (including for headers, as in with/except/except*/patterns, capture patterns), assignment expressions, type statements and type-parameter lists. A del target counts as bound too.

    The rule. If a name is bound anywhere in a block, it is a local of that block (unless declared global/nonlocal). All uses of that name in the block then refer to the local — even uses that come before the binding. A name used but not bound is a free variable, resolved in the nearest enclosing scope. Locals are determined by scanning the whole block text, once, at compile time.

    Resolution: LEGB, walked by the compiler

    A scope is the region where a name is visible. Function-scope definitions extend into nested blocks unless a nested block rebinds the name. Resolution goes to the nearest enclosing scope; not found anywhere → NameError; a function-local referenced before it is bound → UnboundLocalError (a subclass of NameError). Names declared global resolve in the module namespace, then builtins; if absent from both, assignment creates a new global. nonlocal rebinds a variable of the nearest enclosing function scope, and it is a compile-time SyntaxError if no enclosing function scope has it.

    Class bodies are special

    A class definition is an executable statement whose namespace becomes the class's attribute dictionary. Names bound in the class block are visible only in the class block — not in methods, and not in comprehensions or generator expressions nested there (they are separate scopes). One exception in resolution: an unbound local in a class body is looked up in the global namespace, not the enclosing function. And one modern exception in visibility: annotation scopes can see the class namespace.

    Annotation scopes and lazy evaluation (PEP 695, 3.12+)

    Type-parameter lists (def f[T](...), class C[T]:, type A[T] = ...) and type statements introduce annotation scopes: mostly like function scopes, but they can see the enclosing class namespace, cannot contain yield/await/:=, and can't be rebound with nonlocal. The value of a type alias and the bounds/constraints/defaults of type variables are lazily evaluated — only when you access .__value__ or .__bound__ — which is what lets aliases refer to names defined later, including mutually recursive ones. (Ordinary annotations still evaluate eagerly at definition time in 3.13; the reference notes PEP 649 is expected to change that later.)

    Exceptions: the termination model

    An exception is raised where an error is detected and may be handled by the surrounding block or any block that (directly or indirectly) invoked it. Python uses the termination model: a handler learns what happened and continues at an outer level, but cannot repair the cause and resume the failing operation. Handlers are chosen by class: an except clause matches if it names the instance's class or a non-virtual base class. Unhandled exceptions terminate the program (or return to the REPL) with a traceback — except SystemExit. finally runs whether or not an exception occurred and does not handle it.
