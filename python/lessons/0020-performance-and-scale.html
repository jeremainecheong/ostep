Performance and scale: dtypes, columns, laziness, cores

The last lesson turns the internals of both libraries into practical rules. pandas' own scaling guide is four headings: load less data, use efficient dtypes, use chunking, use other libraries. Polars' advice (via the Modern Polars book) is nearly the same list plus one item pandas cannot offer — use the lazy API — because its engine is multithreaded and query-optimizing by design. The closing section connects this back to the GIL lesson: why Polars gets parallelism that pandas structurally can't.

Primary sources: pandas Scaling to large datasets and Enhancing performance; Polars Comparison with other tools, Multiprocessing, Streaming; Kevin Heavey's Modern Polars — Performance ("six fairly obvious performance rules").

    Where the speed comes from

    Columnar, typed memory. Arrow arrays (Polars) and NumPy blocks (pandas) both let inner loops run in compiled code over contiguous typed buffers — this is why "vectorize" is rule one for both. pandas object columns break this: each cell is a Python object with its own refcount (lesson 13), touched one at a time.
    Multithreading vs the GIL. Polars' engine is Rust; its threads never take the GIL because they don't touch Python objects, so a query uses all cores by default (POLARS_MAX_THREADS to cap). pandas is single-threaded: NumPy kernels release the GIL for some operations, but pandas itself runs one operation at a time — the guide's remedy is other libraries (Dask etc.). The 3.13 free-threaded build (lesson 14) does not change this: parallelism needs the library's own design.
    Query optimization. Only a lazy engine can reorder your work: projection/predicate/slice pushdown, common-subplan elimination, join ordering (lesson 17). Eager pandas executes exactly what you wrote, in order, materializing every intermediate.
    Missing values without dtype changes. Validity bitmaps mean an integer column stays integer with nulls; pandas' NumPy path upcasts to float64 (twice the memory of int32, and float semantics).
    Process-level parallelism caveat. If you combine Polars with multiprocessing, use the spawn start method, not fork: forking a multithreaded process (Polars' thread pool) is unsafe and can deadlock — the Polars guide quotes the standard-library warning.

    Choosing

    The Polars comparison page is candid: pandas is "widely-adopted and comprehensive" with a rich feature set and community, but single-threaded and prone to memory/performance trouble on medium-to-large data; Polars is optimized for multithreaded single-machine work with a stricter, more composable API that yields fewer schema bugs. Practical reading: pandas when you need its ecosystem (plotting, statsmodels, scikit-learn glue, countless tutorials) or small interactive work; Polars when data is large, pipelines are repeatable, or you want lazy optimization and predictable types; DuckDB/Spark when you're beyond one machine or want SQL. They interoperate cheaply through Arrow (pl.from_pandas, .to_pandas(), .to_arrow()), so the choice is per stage, not per project.
