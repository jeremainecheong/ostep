Group by, joins, and reshaping: the relational core

Three operations do most of the work in data analysis: split a table into groups and summarize them, combine two tables on keys, and move data between wide and long layouts. Both libraries implement all three; pandas names them after its index-centric heritage (groupby, merge/join, pivot/stack/melt), Polars after SQL and expressions (group_by().agg(), join(how=…), pivot/unpivot). The semantics — especially of joins and duplicates — are where the details matter.

Primary sources: pandas Group by: split-apply-combine, Merge, join, concatenate and compare, Reshaping and pivot tables; Polars Aggregation, Joins (quick-reference table), Concatenation, Pivot, Unpivot.

What you'll be able to do

    Split → apply → combine

    pandas' model: split the data into groups by some criteria; apply a function to each group independently; combine the results. The apply step is one of three kinds: aggregation (one summary per group: sum, size, …), transformation (group-wise computation returning an object indexed like the original: z-scores, fills), filtration (drop whole groups by a group-wise test). No splitting happens until needed — df.groupby("k") only validates the mapping. Defaults worth knowing: keys are sorted (sort=False keeps first-appearance order and can be faster); NA keys are dropped (dropna=False keeps them); the keys become the index of the result (as_index=False keeps columns); for categoricals, observed controls whether unseen categories appear.

    Polars: group_by(exprs) then agg(exprs), where each aggregating expression can be anything — pl.col("x").sum(), pl.col("x").filter(pl.col("y") > 0).mean(), pl.col("name").sort_by("score").last(), pl.len(), even a list of the group's values. Because expressions are independent, Polars evaluates them in parallel; there is no "apply to a Python group object" step unless you ask for map_groups. Transformation is over() (lesson 17); filtration is a filter with an over() expression. Keys stay ordinary columns; output order is not guaranteed unless maintain_order=True or you sort.

    Join explorer

    Two pandas specifics from the guide: when joining columns on columns the indexes of both frames are discarded; and in a many-to-many join a key that appears more than once on both sides produces the Cartesian product of the matching rows — so validate="one_to_one"/"one_to_many" exists to raise on unexpected duplicates. indicator=True adds a _merge column (left_only/right_only/both). DataFrame.join is merge on indexes. Polars: validate exists too, key columns from the right get a _right suffix unless coalesced, and you can join on expressions (left_on=pl.col("a").str.to_lowercase()).

    Concatenation and reshaping

    concat

    pandas pd.concat along axis=0 (rows) or 1 (columns) aligns on the other axis: join="outer" (union, default) or "inner"; ignore_index=True resets; keys= builds a MultiIndex. Polars pl.concat(how=…): "vertical" (same columns, longer), "horizontal" (non-overlapping columns, wider), "diagonal" (different columns; missing cells become null), plus _relaxed variants that coerce types; rechunk controls whether the result is one contiguous chunk.

    wide ↔ long

    pandas: pivot(index, columns, values) requires unique index/column pairs (duplicates → use pivot_table, which aggregates, default mean); stack/unstack move the innermost column/index level; melt(id_vars, value_vars) goes wide→long and ignores the index; explode turns list-likes into rows; crosstab, get_dummies. Polars: pivot(on, index, values, aggregate_function) is eager because its output schema depends on the data; a LazyFrame can pivot only if you declare the resulting columns up front with on_columns= (the guide: "we don't want you to shoot yourself in the foot" — the cost should be clear), otherwise collect first; unpivot(on, index) ≈ melt, producing variable/value; explode; to_dummies.
