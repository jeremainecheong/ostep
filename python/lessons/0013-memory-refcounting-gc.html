Memory: reference counts, the cycle collector, and how objects are laid out

CPython frees most objects the instant their last reference disappears. That is reference counting, and it is simple, prompt and deterministic — until two objects reference each other. A second collector finds those cycles, generationally, using thresholds you can inspect. Around these sit the allocator and the clever layouts of list and dict. This lesson is the mechanism behind lesson 1's "may be garbage-collected" and the prerequisite for understanding the GIL.

Primary sources: garbage_collector.md; PEP 683 (immortal objects, 3.12); PEP 442 (finalization); gc; Include/internal/pycore_runtime_init.h (3.13 thresholds), Objects/listobject.c (growth formula), Objects/dictobject.c (layout comments). All numbers below were read from the 3.13 sources.

What you'll be able to do

    Reference counting

    Every object starts with a header: ob_refcnt and ob_type (PyObject; variable-size objects add ob_size). Py_INCREF/Py_DECREF adjust the count whenever a reference is created or dropped — binding a name, storing in a container, passing an argument, a C local. When the count hits zero the object's tp_dealloc runs immediately, decrementing whatever it referenced, possibly cascading. Advantages: prompt, predictable, no pauses; costs: every reference operation writes memory (the "mutable state in immutable objects" PEP 683 complains about), and it cannot free cycles. Immortal objects (PEP 683, 3.12): None, True, False, small ints, interned strings and statically allocated types have their refcount set to a huge constant that INCREF/DECREF never change — that is why sys.getrefcount(None) prints an absurd number.

    Cycles and the collector

    The algorithm (garbage_collector.md): only container objects (those with tp_traverse) are tracked, in a doubly-linked list per generation. To collect: copy each object's refcount into gc_refs; for every tracked object call tp_traverse and subtract one from each referenced object's gc_refs. Whatever still has gc_refs > 0 is referenced from outside the set — a root; everything reachable from roots (via tp_traverse again) is alive; the rest is unreachable garbage. Then: handle weakrefs (clear them, call callbacks), call tp_finalize (__del__) exactly once per object (PEP 442 — resurrection is detected and re-checked), and finally call tp_clear on the remaining garbage to break the cycles so refcounting frees them.

    Find the garbage

    Objects: a and b reference each other; c references a; a variable in your code references c. Then del of that variable and… nothing is freed by refcounting alone.

    Generations and thresholds (3.13)

    The weak generational hypothesis: most objects die young. New containers start in generation 0; survivors move to 1, then 2. A collection of generation 0 runs when allocations − deallocations of tracked objects since the last collection exceeds threshold0; generation 1 is collected after generation 0 has been collected threshold1 times; generation 2 after threshold2 generation-1 collections — plus a rule that the oldest generation is only collected when the number of long-lived pending objects exceeds 25% of the long-lived total, to avoid quadratic behaviour. 3.13 defaults: (2000, 10, 10) (verified in pycore_runtime_init.h; earlier versions used 700). gc.freeze() moves everything to a permanent generation that is never scanned — useful before fork(). The free-threaded build (next lesson) does not use generations: each collection scans the whole heap, stop-the-world.

    gen 0threshold 2000 net allocations
    gen 1after 10 gen-0 collections
    gen 2after 10 gen-1 collections (+25% rule)

    Layouts that make Python fast

    list: over-allocation

    Objects/listobject.c: on append past capacity, new_allocated = (newsize + (newsize >> 3) + 6) & ~3 — about 12.5% extra, rounded to a multiple of 4 — giving the growth pattern 0, 4, 8, 16, 24, 32, 40, 52, 64, 76…; so appending is amortized O(1). The list itself is an array of PyObject* pointers: 8 bytes per slot, objects elsewhere.

    dict: compact and ordered

    Since 3.6, a dict is two arrays: a sparse dk_indices hash table whose entries are 1, 2, 4 or 8 bytes depending on table size (int8 up to 128 slots…), pointing into a dense dk_entries array of (hash, key, value) in insertion order — that is where ordering comes from for free. Minimum size 8; kept at most two-thirds full (USABLE_FRACTION); resized on the way up. Instances of the same class can share one keys object (split-table dicts: values in a per-instance array) — the layout LOAD_ATTR_INSTANCE_VALUE exploits.

    Allocation: small objects (≤ 512 bytes) go through pymalloc, CPython's arena/pool allocator for many same-size blocks, avoiding malloc overhead; larger ones use the system allocator. The free-threaded build replaces pymalloc with mimalloc, a thread-safe allocator whose heap structure also lets the GC find all objects without the linked lists. tracemalloc traces allocations; sys.getsizeof() reports an object's own size (not what it references).
