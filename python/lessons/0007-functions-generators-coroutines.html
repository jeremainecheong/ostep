Functions, generators, coroutines: one calling convention, three kinds of frame

A function call binds arguments to parameter slots by a fixed algorithm the reference spells out; a generator is a function whose frame suspends at yield and can be resumed, sent values, thrown exceptions, or closed; a coroutine is the same machinery with await instead of yield and an event loop instead of a for loop. Understanding the protocol underneath — __next__, send, throw, close, StopIteration.value, __await__ — makes async code stop looking magical.

Primary sources: §6.3.4 Calls, §6.2.9 Yield expressions (generator-iterator methods), §3.4 Coroutines, §8.7–8.8. Internals: InternalDocs/generators.md (frames embedded in generator objects).

What you'll be able to do

    Calls: the slot-filling algorithm

    §6.3.4: create one unfilled slot per formal parameter. Place the N positional arguments in the first N slots. For each keyword argument, find the slot with that name; if it is already filled → TypeError; otherwise fill it (even with None). Remaining unfilled slots take their default values — defaults are evaluated once, when the function is defined. Any slot still empty → TypeError. Extra positional arguments go to *args if present (else TypeError); extra keywords go to **kwargs if present (else TypeError). *iterable and **mapping at the call site are unpacked first. Parameters before / are positional-only; after a bare * or *args, keyword-only.

    Bind a call to def f(a, b=2, /, c=3, *args, d, e=5, **kw)

    Function objects

    A user-defined function object (§3.2) carries: __code__ (the compiled body), __globals__ (the module namespace where it was defined — the reference to global names), __defaults__/__kwdefaults__, __closure__ (cells for free variables), __dict__ (arbitrary attributes), __annotations__, __type_params__ (3.12+), __name__, __qualname__, __module__, __doc__. Lambdas are the same objects with a single expression body. Because __defaults__ is created once, a mutable default (def f(x, acc=[])) is shared across calls — the classic trap.

    Generators: suspended frames

    Any function containing yield becomes a generator function: calling it runs nothing and returns a generator iterator. Each __next__() resumes the frame until the next yield, whose operand is returned to the caller; the yield expression itself evaluates to whatever was sent (None for plain __next__). When the function returns, StopIteration is raised and the return value becomes StopIteration.value — which is exactly what yield from sub evaluates to when the sub-generator finishes. Since PEP 479, a StopIteration escaping the body is turned into RuntimeError. Calling any method while the generator is already executing → ValueError.

    Drive a generator by hand

    def gen():
    print("  started")
    received = yield 1          # first suspension point
    print("  got", received)
    try:
        yield 2
    except KeyError:
        print("  caught KeyError, yielding 3")
        yield 3
    return "done"

    close() precisely

    Raises GeneratorExit at the paused yield (same as throw(GeneratorExit)). If the body catches it and returns, that value is close()'s result (3.13); if it lets it propagate or was already closed, close() returns None; if it yields again → RuntimeError; other exceptions propagate. Also called by the generator's finalizer, so finally/with blocks inside generators do run on collection.

    Under the hood (InternalDocs)

    The generator object embeds a _PyInterpreterFrame: locals, the evaluation stack and the instruction pointer live inside the generator, so suspending is just returning from the eval loop with that frame preserved. RETURN_GENERATOR creates the object on the first call; SEND/YIELD_VALUE handle yield from and await. That's why generators are cheap: no thread, no stack copying.

    Coroutines and awaitables

    async def defines a coroutine function; calling it returns a coroutine object, an awaitable. await x requires x to be awaitable: a coroutine, or an object whose __await__() returns an iterator (that is how asyncio.Future plugs in). Driving works exactly like generators — send(None) to start, the underlying iterator raises StopIteration with the return value in .value — but coroutines do not support __next__/iteration directly, may not be awaited twice (RuntimeError), and must not raise bare StopIteration. async for uses __aiter__/__anext__ (awaitable, raising StopAsyncIteration); async with awaits __aenter__/__aexit__; async generators mix yield into async def. An event loop is just a scheduler that calls send() on many coroutine objects and parks the ones whose awaitable said "not yet".
