The eval loop: a stack machine that rewrites its own instructions

_PyEval_EvalFrameDefault in Python/ceval.c is a loop: fetch a code unit, dispatch on the opcode, run a case generated from Python/bytecodes.c. Since 3.11 those instructions watch the types they see and replace themselves with specialized variants (PEP 659) — the single biggest reason 3.11–3.13 are faster. 3.13 adds a second tier: hot loops are translated to micro-ops and, in JIT builds, to machine code by copy-and-patch (PEP 744).

Primary sources: interpreter.md (instruction format, inline caches, evaluation stack, specialization, families), frames.md, jit.md; PEP 659; PEP 744; What's New 3.13 (JIT section). Family names below are grep'd from the 3.13 Python/bytecodes.c.

What you'll be able to do

    Frames and the evaluation stack

    Each call pushes a _PyInterpreterFrame onto a per-thread data stack (allocated in chunks — not the C stack, and not a heap object). It holds the code object, the instruction pointer, the function, and localsplus: the local variables followed by the evaluation stack. A Python-visible PyFrameObject is created lazily, only if something asks (a traceback, sys._getframe(), a debugger), and copies the interpreter frame if it outlives it. Generators embed their frame in the generator object (lesson 7). The compiler precomputes the maximum stack depth (co_stacksize), and each instruction's stack effect is recorded in the opcode metadata (_PyOpcode_num_popped/_num_pushed).

    Dispatch

    The loop decodes opcode and oparg from the current code unit and jumps to the matching case. On compilers that support it, CPython uses computed gotos (a table of label addresses) instead of a switch, which helps the CPU's branch predictor; the cases themselves are generated from the instruction definitions DSL in Python/bytecodes.c into generated_cases.c.h. Jumps are relative: JUMP_FORWARD adds oparg to the instruction pointer, JUMP_BACKWARD subtracts it — and JUMP_BACKWARD is also where the interpreter checks for pending signals, asynchronous exceptions and, in the default build, whether to release the GIL (lesson 14).

    Specialization: the adaptive interpreter (PEP 659)

    The idea: a dynamic language VM must specialize on the types and values actually flowing through the program — usually associated with JITs, but valuable even in an interpreter. Each adaptive instruction counts its executions in its first inline-cache entry; when the counter reaches zero it calls _Py_Specialize_XXX (Python/specialize.c), which inspects the operands and, if a fast case applies, rewrites the instruction in co_code_adaptive with a specialized variant and fills the remaining cache entries (type versions, dict indices, function versions). The specialized instruction re-checks its assumptions each time with a cheap guard; on failure it de-optimizes back to the adaptive form and the counter restarts with exponential back-off. Speculative but safe; small regions, so no warm-up problem. Measured speedups: 10–60%, "up to 50%" overall.

    Why this matters for how you write code. Stable types at each call site specialize well; a site that alternates between ints and floats ("polymorphic") keeps de-optimizing. Attribute access on plain classes with a fixed set of attributes (shared-key dicts) hits LOAD_ATTR_INSTANCE_VALUE; __slots__ hits LOAD_ATTR_SLOT; overriding __getattribute__ forces the slow path. Module-level globals are fast via dict versions; builtins too — unless you shadow them.

    Tier 2 and the JIT (PEP 744, 3.13)

    Tier 1Specialized bytecode, the adaptive interpreter above. Optimizes one instruction at a time.
    Hot detectionWhen a JUMP_BACKWARD (loop) or RESUME counter says the code is hot, the optimizer records a trace: the instructions actually executed, translated into micro-ops ("uops") — smaller steps generated from the same DSL.
    Tier 2 IR + optimizerPasses over the uop trace: remove redundant guards and refcount traffic using known types, constant-propagate. An executor attached to the original instruction runs the trace; a guard failure takes a side exit back to Tier 1.
    Machine codeWith --enable-experimental-jit, the optimized trace is compiled by copy-and-patch: pre-built machine-code stencils for each uop (generated at build time with LLVM) are copied and their holes patched with constants and addresses. No runtime dependency; ~900 lines of build-time Python + ~500 lines of C. Off by default; PYTHON_JIT=0/1 toggles a JIT build.

    Why not just interpret uops? PEP 744: dispatch overhead between uops dominates; a straight-line compiled trace removes dispatch and decoding costs and lets values live in registers instead of heap frames. And why copy-and-patch rather than a classic backend? Editing bytecodes.c updates the JIT "for free" on every platform; low maintenance for a volunteer project. The 3.13 status: experimental, roughly performance-neutral, a foundation.
