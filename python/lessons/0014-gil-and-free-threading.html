The GIL: what it is, why it exists, and how 3.13 makes it optional

The global interpreter lock lets only one thread execute Python bytecode at a time. It exists because reference counting and the built-in containers were never designed for concurrent mutation; it is the reason CPU-bound threads don't speed up on multiple cores, and the reason C extensions are easy to write. 3.13 ships the first free-threaded build (PEP 703): the GIL becomes optional, at the price of a whole new refcounting scheme, per-object locks, a different allocator and — for now — a single-thread performance cost. This lesson covers both worlds with the actual numbers.

What you'll be able to do

    What the GIL is

    Glossary: "the mechanism used by the CPython interpreter to assure that only one thread executes Python bytecode at a time. This simplifies the CPython implementation by making the object model (including critical built-in types such as dict) implicitly safe against concurrent access… at the expense of much of the parallelism afforded by multi-processor machines." Extensions may release it around heavy work (compression, hashing) and the GIL is always released when doing I/O.

    Mechanically (ceval_gil.c): the GIL is a boolean locked guarded by a mutex and signalled with a condition variable. A thread that wants it waits up to the switch interval — DEFAULT_INTERVAL 5000 µs, i.e. 5 ms, readable and settable with sys.getswitchinterval()/setswitchinterval() — then sets gil_drop_request (folded into the eval_breaker flag the eval loop checks at JUMP_BACKWARD/RESUME). The holder notices, releases, and with forced switching waits until another thread has actually taken the GIL, so a releasing thread on a multi-core machine cannot immediately re-grab it and starve the others. Which waiter wins is the OS's decision. The interval is a target, not a guarantee: a single long-running C operation can hold the GIL as long as it likes. C code releases it explicitly with Py_BEGIN_ALLOW_THREADS/Py_END_ALLOW_THREADS (e.g. zlib, hashlib, every blocking I/O call).

    Two threads, one GIL — pick a workload

    Why the GIL exists: reference counting

    Every Py_INCREF is a read-modify-write of ob_refcnt. Two threads doing that concurrently on the same object lose updates (exactly the counter race of an OS course) — and a lost decrement leaks, a lost increment frees a live object and crashes. Making every refcount operation atomic slows the single-threaded case badly. The GIL solves this globally: one thread runs, so no atomics are needed anywhere, and dicts, lists and the allocator get thread-safety for free. That is also why removing it was hard for thirty years: every object, container and internal structure relied on it.

    PEP 703: making the GIL optional

    Biased reference countingTwo counts per object: ob_ref_local (owned by the creating thread, stored in ob_tid; non-atomic fast path) and ob_ref_shared (atomic, for other threads). The true count is their sum; deallocation happens when both are zero, after a merge.
    ImmortalizationObjects used by every thread — None, small ints, interned strings, and in 3.13 also module-level functions, code objects, modules, method descriptors and type objects (immortalized when a second thread starts) — get a fixed refcount, so no contention. Cost: more memory in programs creating many such objects; slated for 3.14 fixes.
    Deferred reference countingA limited form for functions, code, modules and types that are frequently accessed but shouldn't be immortal: their refcount is not tracked precisely by the interpreter; the tracing GC finds the missing references and only it can free them.
    Per-object locksA one-byte ob_mutex in each object; dict, list, set internals are protected by critical sections (Py_BEGIN_CRITICAL_SECTION) which are automatically suspended when the thread blocks, so nested locking cannot deadlock the way plain mutexes would.
    mimallocA thread-safe general allocator replaces pymalloc. Its heap structure lets the GC enumerate all objects without the per-generation linked lists, and helps dict/list readers avoid locks safely (memory isn't reused while a reader may still see it — QSBR).
    Stop-the-world GCCollection pauses all threads; the free-threaded collector is non-generational: every collection scans the whole heap. Extensions declare support with the Py_mod_gil slot; importing an unmarked extension re-enables the GIL (with a warning) unless overridden.

    3.13 status, in numbers

    • Separate executable python3.13t (build option --disable-gil); sys.version contains "experimental free-threading build"; sys._is_gil_enabled() tells you the current state.
    • Runtime toggle: PYTHON_GIL=0/1 or -X gil=0/1. Default in the free-threaded binary is GIL off — until an incompatible extension is imported.
    • Single-threaded overhead ≈ 40% on pyperformance in 3.13, mostly because the specializing adaptive interpreter (lesson 12) is disabled in the free-threaded build; the goal is ≤ 10%, with specialization re-enabled thread-safely in 3.14.
    • Thread-safety promise: built-in containers use internal locks and "behave similarly to the GIL", but the HOWTO calls this a description of the current implementation, not a guarantee — use threading.Lock. Sharing one iterator across threads is unsafe; frame objects must not cross threads.
    • Ecosystem tracking: py-free-threading.github.io/tracking and hugovk.github.io/free-threaded-wheels.
    What to do today. Threads are still the right tool for I/O-bound concurrency (the GIL is released while waiting) and for calling GIL-releasing native code (NumPy, hashing, compression). For CPU-bound pure Python: multiprocessing/concurrent.futures.ProcessPoolExecutor, or sub-interpreters (PEP 684 gave each interpreter its own GIL in 3.12; PEP 734's stdlib module lands later), or test the free-threaded build with proper locking. Write thread-safe code regardless — the GIL never made x += 1 atomic in Python.
