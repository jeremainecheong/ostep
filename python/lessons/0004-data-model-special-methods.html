Language Reference §3.3 Special method names

Special methods: how syntax becomes method calls

Operators, len(), iteration, with, truth tests, repr() — every piece of syntax in Python is defined by the data model as a call to a method with a double-underscore name. This is the protocol view of the language: implement the right dunders and your objects behave like built-ins. This lesson covers construction, representation, comparison, truth, containers, numbers and context managers; attributes and descriptors get their own lesson next.

Primary source: §3.3 Special method names — basic customization (3.3.1), container emulation (3.3.7), numeric types (3.3.8), with statement context managers (3.3.9), special method lookup (3.3.12).

What you'll be able to do

    The dispatch: a + b, exactly

    §3.3.8: x + y calls type(x).__add__(x, y). If that is missing or returns NotImplemented, Python calls the reflected method type(y).__radd__(y, x). If that too declines, TypeError. One twist: if type(y) is a subclass of type(x) and overrides the reflected method, y.__radd__ is tried first — so subclasses can override their ancestors' operations. In-place x += y tries __iadd__, then falls back to __add__/__radd__.

    Step through the algorithm

    Construction and destruction

    C(args) is type.__call__ doing two things: __new__(cls, *args) — a static method (special-cased, no decorator needed) that creates the instance, usually via super().__new__(cls) — then, only if __new__ returned an instance of cls, __init__(self, *args) to initialize it. __init__ must return None. __new__ exists chiefly so subclasses of immutable types (int, str, tuple) can customize creation — the value is fixed before __init__ runs — and metaclasses use it to customize class creation. __del__ is the finalizer: called when the instance is about to be destroyed, not guaranteed to run at interpreter exit, may resurrect the object (then it is not called again in CPython), and exceptions inside it are printed to stderr and otherwise ignored.

    Representation, comparison, truth

    repr / str / format

    __repr__: the "official", information-rich string, ideally a valid expression to recreate the object, else <...>; used by the debugger and as the fallback for __str__. __str__: the informal, printable string (print, format). __format__(spec) backs f-strings and format(); object.__format__ accepts only an empty spec. __bytes__ for bytes(x).

    Rich comparison

    x < y → x.__lt__(y), etc. Reflections: __lt__/__gt__, __le__/__ge__, __eq__/__eq__, __ne__/__ne__; no other relations are implied (define all six or use functools.total_ordering). object.__eq__ is identity, returning NotImplemented otherwise; __ne__ inverts __eq__. If both sides return NotImplemented, == falls back to is and != to is not; ordering operators raise. Right operand's subclass gets priority here too (virtual subclassing not considered).

    Truth

    bool(x): __bool__ if defined (must return a bool); else __len__ (false iff zero); else every instance is true. Also __hash__ (lesson 1's contract).

    Containers and iteration

    §3.3.7: __len__ (must return an int ≥ 0; also used for truth), __getitem__/__setitem__/__delitem__ (sequences should raise IndexError for out-of-range ints — that's how the old iteration protocol knows to stop — and TypeError for wrong key types; mappings raise KeyError), __missing__ (called by dict.__getitem__ on dict subclasses when the key is absent), __iter__ (returns an iterator; mappings iterate keys), __reversed__, __contains__ (for mappings, membership of keys). If __contains__ is missing, in falls back to iterating with __iter__, then to the old __getitem__ protocol. __length_hint__ is an optimization only. Sequences are encouraged to support slice objects in __getitem__ and mapping-style keys()/items()/get()… for mappings — collections.abc mixins fill these in.

    Callables and context managers

    x(args) → type(x).__call__(x, args). The with statement: __enter__()'s return value is bound to the as target; __exit__(exc_type, exc_value, traceback) receives the exception (or three Nones), and suppresses it by returning a true value; it must not re-raise the passed-in exception itself. contextlib.contextmanager builds both from one generator.

    Special method lookup bypasses the instance

    §3.3.12: implicit invocations of special methods are only guaranteed to work if defined on the type, not in the instance's __dict__. Rationale: methods like __hash__ and __repr__ exist on all objects including type objects; looking them up through the instance would confuse "the class's repr" with "the metaclass's repr" — type(1).__hash__() vs int.__hash__(). Implicit lookup also bypasses __getattribute__, for speed and to keep the interpreter's hands untied.
