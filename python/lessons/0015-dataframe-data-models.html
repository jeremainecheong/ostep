Two data models: labeled NumPy blocks vs Arrow columns

pandas and Polars both give you a "DataFrame", and the word hides two different designs. pandas is built on labeled axes and alignment — an index on every row, NumPy arrays underneath, NaN as the missing marker. Polars is built on Apache Arrow columns with a validity bitmap, no row index, strict dtypes, and expressions evaluated by a query engine. Knowing which model you are in explains most of the API differences that follow in lessons 16–20.

What you'll be able to do

    Side by side

    pandas labels + NumPy

    • Series: 1-D labeled array of any dtype; DataFrame: 2-D labeled, columns potentially of different types; both carry an Index (row labels) and DataFrame a columns Index.
    • Data alignment is intrinsic: arithmetic between two Series aligns on labels and produces the union of indexes with NaN where a label is missing.
    • Storage: NumPy arrays by default (columns of the same dtype consolidated into blocks); optional nullable extension arrays (Int64, boolean, string) and PyArrow-backed columns ("int64[pyarrow]", ArrowDtype).
    • Missing data: different sentinels per dtype — np.nan for NumPy float (which coerces int columns to float64 or object), NaT for datetimes, pd.NA for nullable/Arrow dtypes.
    • pandas 3.0: Copy-on-Write is the default and only mode; strings infer to a dedicated str dtype (PyArrow-backed when available) instead of object.

    Polars Arrow + expressions

    • Series: 1-D homogeneous; DataFrame: 2-D collection of uniquely named Series with a schema. No index: rows are addressed by integer position; the guide argues an index makes results less predictable, and any needed key is just a column.
    • Memory: the Apache Arrow columnar format, so zero-copy interchange with other Arrow tools; every column is a chunked Arrow array.
    • Missing data: always null, for every dtype, tracked by a validity bitmap costing n/8 bytes; null_count is O(1). NaN is a valid float value, not missing.
    • Strict, rich dtypes: sized ints (Int8…Int64, UInt…), Float32/64, Boolean, String, Categorical, Enum, Date/Datetime/Duration/Time, nested List, Array, Struct, Object.
    • Rust engine: parallel by default across cores; eager and lazy evaluation with query optimization (lesson 17).

    Missing data: the same column, two encodings

    Consider an integer column with one missing value. pandas (NumPy-backed) must change the dtype: the reindex/insert of a missing value coerces int64 to float64 and stores NaN in the data itself. Polars keeps the Int64 buffer untouched and flips one bit in a separate validity bitmap. pandas' nullable Int64 (capital I) and PyArrow-backed dtypes adopt the same "mask" idea, which is why the pandas docs recommend them for data with missing values.

    Copy-on-Write: pandas 3.0 adopts the immutable mindset

    Before 3.0, whether df["a"] was a view or a copy of df depended on the internal block layout — the source of the infamous SettingWithCopyWarning. The migration guide states the new rule: any DataFrame or Series derived from another in any way always behaves as a copy; a lazy copy is made only when one of them is actually modified. Consequences: chained assignment (df["a"][0] = 1, df["a"].replace(…, inplace=True)) never works — write df.loc[0, "a"] = 1 or df.replace({"a": {…}}); selecting a column returns a new Series each time; constructors copy NumPy input by default (copy=False to opt out); .to_numpy() may return a read-only view. Polars never had the problem: DataFrames are immutable values and every operation returns a new frame (sharing Arrow buffers underneath).
