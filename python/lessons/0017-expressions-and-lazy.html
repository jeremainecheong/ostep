Expressions, window functions, and the lazy query engine

Polars' expressions are more than a nicer syntax: because they describe computation without running it, Polars can build a query plan, optimize it (push filters into the file scan, read only needed columns, fold constants, reorder joins), check the schema before touching data, and execute in parallel or in streaming batches. pandas evaluates eagerly line by line; its eval/query and UDF advice are the closest analogues. This lesson makes the plan visible.

Primary sources: Polars Lazy API, Query plan, Optimizations (the table below is theirs), Schema, Streaming, Window functions, User-defined Python functions; pandas Enhancing performance and User-defined functions.

What you'll be able to do

    Eager vs lazy

    The guide's example. Eagerly: read a CSV, filter rows on sepal length, compute mean sepal width per species — every step executes immediately and materializes intermediate results, loading columns and rows that are then thrown away. Lazily (pl.scan_csv … .collect()): the planner applies predicate pushdown (filter while reading, so only matching rows are read) and projection pushdown (read only the needed columns). The guide's recommendation: prefer the lazy API unless you need intermediate results or are exploring. Note that many eager methods call the lazy engine internally and collect at once, so within one operation the optimizer still helps.

    Two more lazy benefits. Schema checking before execution: a LazyFrame knows its schema (collect_schema()), so calling .round() on a string column fails immediately when the query is built, not after minutes of I/O. Streaming: collect(engine="streaming") processes the query in batches so datasets larger than memory can be handled; operations without a streaming implementation fall back to the in-memory engine transparently. Also: sink_parquet/sink_csv stream results to disk without materializing them.
    

    


    Window functions: aggregate without collapsing
    

    expr.over("group") computes the expression per group but returns a result of the original length, e.g. rank within a group, group mean broadcast to each row, or cumulative sums per key. It is the expression form of pandas groupby(...).transform(...). The mapping_strategy parameter controls the shape: "group_to_rows" (default, values mapped back to their rows), "explode" (groups concatenated, faster, order changes), "join" (each row gets the whole group result as a list).
    

    


    User-defined functions: the escape hatch, and its cost
    

    pandas
    UDFs run per element/row/group in Python. The guide's warning: pandas must infer the result type, inference can be wrong, and unlike vectorized operations UDFs give up NumPy's speed. Prefer built-in vectorized methods; if you must, Series.map/apply, DataFrame.apply(axis=1) is the slowest. pandas.eval()/DataFrame.query() use numexpr to evaluate arithmetic/boolean expressions on large frames without temporaries; Numba (engine="numba" in some methods) or Cython compile hot loops.
    Polars
    map_elements(f) calls Python once per value — slow (call overhead) and Polars cannot infer the return type until it sees values, so pass return_dtype. map_batches(f) hands the whole Series (or each group's series) to f once — so NumPy/Numba-vectorized functions stay fast. Polars warns when a map_elements call could have been an expression. Everything else in the expression API runs in Rust, in parallel, without the GIL.
