From source to bytecode: the compiler pipeline and the code object

Before CPython executes anything it compiles your source to bytecode — instructions for a stack-based virtual machine, packed into a code object together with constants, names, line-number tables and an exception table. The pipeline is tokenizer → PEG parser → AST → symbol table → control-flow graph → optimizer → assembler. This lesson follows a function through it and reads the result with dis, on real 3.13 bytecode in your browser.

Primary sources: InternalDocs/compiler.md, code_objects.md, exception_handling.md; dis; PEP 617 (PEG parser, 3.9), PEP 626 (line numbers), PEP 657 (fine-grained error locations). The runners execute in Pyodide 0.28, i.e. CPython 3.13 compiled to WebAssembly — the bytecode you see is genuine 3.13 output.

    The code object

    compile() (or a function definition) produces a code object — immutable, containing no references to mutable objects, which is why .pyc files can simply marshal them. Fields you will meet (§3.2 of the reference, code_objects.md): co_code (the bytecode bytes — a read-only view; the interpreter actually runs co_code_adaptive, a private mutable copy that specialization rewrites, next lesson), co_consts, co_names (globals/attributes), co_varnames (locals and parameters), co_cellvars/co_freevars (closures), co_argcount/co_posonlyargcount/co_kwonlyargcount, co_stacksize (maximum evaluation-stack depth, computed by the compiler), co_flags (generator, coroutine, varargs…), co_linetable (compact positions; iterate co_positions() for line/column ranges, PEP 657), co_exceptiontable, co_qualname, co_filename. When a code object is created, _PyCode_Quicken() initializes the inline caches of adaptive instructions.

    Reading bytecode

    Instruction format (interpreter.md): each code unit is 16 bits — an 8-bit opcode and an 8-bit oparg. Larger arguments are built with up to three EXTENDED_ARG prefixes (each contributes 8 more bits). Some instructions are followed by inline cache entries (2-byte units, shown by dis as CACHE when show_caches=True) used by specialization. Jump offsets are relative and counted in code units. 256 opcodes fit, and 3.13 uses them for a stack machine: LOAD_FAST pushes a local, BINARY_OP pops two and pushes one, CALL n pops the callable + self/NULL + n args, RETURN_VALUE pops the result.

    Anatomy of LOAD_ATTR 3 with its caches

    opcode = LOAD_ATTRoparg = 3 (index into co_names, shifted)CACHE counterCACHE versionCACHE …CACHE …
    One code unit of instruction followed by cache units; the whole family (LOAD_ATTR, LOAD_ATTR_INSTANCE_VALUE, LOAD_ATTR_SLOT, LOAD_ATTR_MODULE…) shares the same cache size, and the first cache entry is always the specialization counter.

    Zero-cost exceptions (3.11+)

    There is no SETUP_FINALLY anymore. The compiler emits an exception table (co_exceptiontable): for each protected range of instructions, where to jump, the stack depth to restore, and whether to push the "lasti" (for re-raise). Entering a try costs nothing; only when an exception is raised does the interpreter search the table. dis.dis() prints it as ExceptionTable: at the end.

    What the optimizer does

    On the CFG (Python/flowgraph.c): constant folding (1 + 2 → 3, "a" "b" → "ab"), turning constant list/set literals in in tests into tuples/frozensets, jump threading and dead-code elimination, removing unreachable blocks after return, superinstructions like LOAD_FAST_LOAD_FAST. compile(..., optimize=1) removes asserts and sets __debug__ False; optimize=2 also strips docstrings.
