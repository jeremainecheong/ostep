Three file systems, three ideas: locality, crash consistency, and never overwriting

vsfs works but treats the disk like memory. FFS treats the disk like a disk. Then the problem every file system must face — the power goes out halfway through an update — solved first by checking the whole disk (fsck), then by write-ahead logging (journaling). Finally LFS turns every write into a sequential one and asks: what if the log is the file system?

Primary sources: Ch 41, Ch 42, Ch 43. Homework: ffs.py, fsck.py, lfs.py. Original papers: McKusick et al. (FFS, 1984), Hagmann (journaling in Cedar), Rosenblum & Ousterhout (LFS, 1992).

What you'll be able to do

    FFS: disk awareness (chapter 41)

    Crux: how to organize on-disk data to improve performance. The old UNIX FS put all inodes at the start and data after: a file's inode and data were a long seek apart, free lists fragmented so files ended up scattered (the book: delivering only 2% of disk bandwidth), and 512-byte blocks were too small. What structures and allocation policies make a file system "disk aware"?

    Policies: keep related things together

    • Directories: put a new directory in the group with few allocated directories and many free inodes (balance).
    • Files: put a file's data blocks in the same group as its inode, and put files in the same directory in the same group. Reading /a/b and /a/c stays in one cylinder group; the book's traces show ~7% of accesses are to the same file, ~40% within the same directory or one level up — namespace locality is real.

    The large-file exception

    One big file would fill its group and push its neighbours away. FFS instead spreads it: the first 12 (direct) blocks in the inode's group, then each indirect block's worth in another group. The cost is a seek per chunk — but if chunks are large, seek cost is amortized: at 10 ms positioning and 40 MB/s, a 409.6 KB chunk keeps the disk half busy; 3.6 MB gets you 90%. (FFS chose chunk placement by indirect-block boundaries; modern systems compute it.)

    Other FFS gifts: 4 KB blocks with 512-byte sub-blocks for small files (copy up when a file reaches 4 KB — and libc buffers writes to avoid the dance); parameterization of the disk (layout sector skipping so sequential reads don't miss a rotation, until track buffers made it moot); long file names; symbolic links; atomic rename. The lesson the book distills: treat the disk like it's a disk.

    Crash consistency (chapter 42)

    Crux: how to update the disk despite crashes. A crash or power loss can land between any two writes; the disk is only partially updated. How do we keep the on-disk image in a reasonable state?

    Solution 1: the file system checker (fsck)

    Let inconsistencies happen; fix them at boot, before mounting. fsck checks the superblock (sanity; use a copy if bad), free blocks (rebuild bitmaps from the inodes' pointers — trust the inodes), inode state (valid types), inode links (recount by scanning directories; orphans go to lost+found), duplicates (two inodes claiming one block: clear one or copy it), bad blocks (pointers outside the disk), and directories (., .., referenced inodes exist, no directory linked twice). Two flaws: it can't tell that the third scenario above is a bug — it only restores metadata consistency, the file happily points at garbage — and it is too slow: scanning a whole volume to fix three blocks, the book's analogy, is dropping your keys in your bedroom and searching the entire house.

    Solution 2: journaling (write-ahead logging)

    Before touching the real structures, write a note in a journal saying what you're about to do. If you crash mid-update, replay the note; recovery is O(log size), not O(disk). Step through both protocols (ext3 has both modes):

    • Why the commit is a separate write. The disk may reorder the five journal blocks; if TxE lands before Db and you crash, replay writes garbage over Db's slot (possibly the superblock!). So: write everything except TxE, wait, then write the single-sector TxE (a 512-byte write is atomic). Or include a checksum of the transaction in TxB/TxE (ext4) and do it in one go.
    • Batching: buffer many updates into one global transaction (5 s in ext3) to avoid writing the same inode block again and again. The journal is a circular log; a journal superblock marks the oldest and newest live transactions; a free step releases space after checkpointing.
    • Metadata journaling halves write traffic (user data is written once, not twice) but must order things: write data to its final location first, so a pointer never points at garbage ("write the pointed-to object before the object that points to it" — also the rule behind LFS and soft updates). A tricky case remains: delete a directory, reuse its block for file data, then replay a journaled directory write over the new data — hence revoke records.
    Other approaches. Soft updates order every write carefully (complex, needs FS-specific knowledge). Copy-on-write (ZFS, btrfs, LFS below) never overwrites in place — flip a root pointer atomically instead. Backpointer-based consistency puts a back pointer in every block and checks it on read. Optimistic crash consistency issues more writes concurrently and uses checksums to detect the rare inconsistency. Strong guarantees for user data (not just metadata) are still, in the book's words, "a work in progress".

    Log-structured file systems (chapter 43)

    Crux: how to make all writes sequential writes. Memory is growing (reads hit the cache), the gap between sequential and random disk I/O is widening, and existing FSes do many small writes (five writes to create a file). For reads you can't choose where to go; for writes you always can.

    LFS buffers every update — data blocks, inodes, directory blocks — in an in-memory segment (a few MB) and writes the whole segment sequentially to a fresh place on disk, never overwriting. Build one:

    Segments accumulate in memory and hit disk as one big sequential write. D = data, I = inode, imap = a piece of the inode map.

    Finding inodes: the inode map

    In FFS inode k is at a fixed address; in LFS it's wherever it was last written. The imap maps inode number → latest disk address, and pieces of it are written into the log right after the inodes they cover. To find the imap: the checkpoint region (CR) at a fixed address holds pointers to the latest imap pieces, updated only every ~30 s. Reading file k: CR → imap → inode → block (the CR and imap are cached in memory, so it's FFS cost after that). Directories work the same way, and the imap solves the recursive update problem: an inode moving doesn't force its parent directory to be rewritten, because the directory stores the inode number, which the imap resolves.

    Garbage collection

    Overwrites leave old versions in the log (a versioning FS would keep them; LFS reclaims them). The cleaner reads M partially-dead segments, writes their live blocks into N < M new segments, and frees the old ones. Liveness: each segment starts with a segment summary block recording (inode number, offset) for every block; a block is live iff the imap → inode → offset lookup still points at it (a version number shortcut avoids reads). Policy: clean cold segments soon (their live blocks are stable), hot ones later (more of them will die). Cleaning cost was LFS's great controversy.

    Crash recovery: two CRs updated alternately with timestamps at head and tail, so a torn CR write is detected and the other used. Then roll forward from the last checkpoint through the segments written since. Write-anywhere/copy-on-write lives on in NetApp's WAFL (which turns old versions into snapshots — turn flaws into virtues), ZFS, btrfs — and in flash SSDs' translation layers, next lesson, where large writes are essential.
