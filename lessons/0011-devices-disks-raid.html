Talking to devices, the physics of a disk, and making many disks one

Persistence begins with hardware. A device is a few registers and a protocol; interrupts and DMA make talking to it cheap. A hard disk is a spinning platter whose costs are seek, rotate, transfer — so sequential access is everything. RAID turns several such disks into one that is bigger, faster, or safer, and the arithmetic tells you which.

    I/O devices (chapter 36)

    Crux: how to integrate I/O into systems. What are the general mechanisms, and how do we make them efficient?

    A canonical device exposes an interface — status, command and data registers — and hides internals (a microcontroller, memory, ASICs; a modern RAID card runs firmware of hundreds of thousands of lines). The canonical protocol: poll status until not busy; write data (programmed I/O, PIO — the CPU moves each word); write the command; poll until done.

    From polling to interrupts to DMA

    Interrupts aren't always better. For a fast device, spinning is cheaper than the switch-out-and-back; a flood of interrupts can livelock a server that only handles interrupts and never runs the application. Hybrids: poll briefly then block; coalesce several completions into one interrupt.

    Two ways to reach registers

    Explicit I/O instructions (x86 in/out, privileged) name a port. Memory-mapped I/O maps registers to addresses; ordinary loads and stores are routed to the device. Both are in use.

    Device drivers

    Abstraction keeps the rest of the OS device-neutral: file system → generic block layer → device driver → hardware. Cost: specialized capabilities (e.g. SCSI's rich error reporting) get lost behind generic interfaces. Drivers are over 70% of Linux kernel code, often written by amateurs — hence a disproportionate share of crashes.

    // xv6 IDE driver, the shape of it: wait for ready, issue, sleep; the interrupt handler finishes the job
static void ide_start_request(struct buf *b) {
    ide_wait_ready();
    outb(0x3f6, 0);                                     // generate interrupt
    outb(0x1f2, 1);                                     // how many sectors?
    outb(0x1f3, b->sector & 0xff); ...                  // LBA bytes
    outb(0x1f7, b->flags & B_DIRTY ? IDE_CMD_WRITE : IDE_CMD_READ);
    if (b->flags & B_DIRTY) outsl(0x1f0, b->data, 512/4);   // PIO transfer
}
void ide_intr() { if (!(b->flags & B_DIRTY) && ide_wait_ready() >= 0) insl(0x1f0, b->data, 512/4);

    Hard disk drives (chapter 37)

    Crux: how to store and access data on disk. What's the interface, how is data laid out, and how does scheduling help?

    Interface: an array of 512-byte sectors, 0..n−1; a single sector write is atomic, multi-sector writes may torn on power loss. Unwritten contract: nearby sectors are fast; sequential is far faster than random. Geometry: platters with two surfaces, spinning at 7,200–15,000 RPM (10K RPM ≈ 6 ms per rotation); concentric tracks read by a head on an arm. Every access pays:

    TI/O = Tseek + Trotation + Ttransfer     RI/O = Sizetransfer / TI/O

    Seeks have phases (accelerate, coast, decelerate, settle — settling alone is 0.5–2 ms); rotation averages half a revolution; transfer is fast. Drives add track skew so a sequential read that crosses tracks doesn't miss a whole rotation, zones with more sectors on outer tracks, and a track buffer cache (8–16 MB) with write-back ("immediate reporting") or write-through semantics.

    Disk scheduling

    Because the disk's costs are known, the OS (or the drive) approximates SJF. SSTF (shortest seek time first) — starves far requests; SCAN (elevator: sweep across tracks, queue requests behind the sweep; C-SCAN sweeps one way, fairer to the outer tracks; F-SCAN freezes the queue per sweep); SPTF (shortest positioning time, accounting for rotation — "it depends", so done inside the drive). Modern OSes pick a few requests and let the drive's internal scheduler finish the job; they also do I/O merging and sometimes wait briefly (anticipatory, non-work-conserving) for a better request.

    RAID (chapter 38)

    Crux: how to make a large, fast, reliable disk from several small, slow, unreliable ones — transparently, so existing software just sees a bigger disk?

    A RAID is a computer (microcontroller, DRAM, sometimes non-volatile memory) running software that maps logical blocks to physical disks. Fault model: fail-stop (a disk works or is clearly dead). Evaluate by capacity, reliability (how many failures survive), and performance: single-request latency, and throughput for sequential (S MB/s per disk) vs random (R MB/s per disk) workloads. With the book's drive (7 ms seek, 3 ms rotate, 50 MB/s): S ≈ 47.6 MB/s, R ≈ 0.98 MB/s.

    Reproduces Figure 38.8 with numbers. T = time for one request to one disk. Try N = 2 vs 16 and watch RAID-5's random-write factor of 4 stay put.
    • RAID-0 striping: blocks round-robin across disks; chunk size trades intra-file parallelism (small) against positioning time (large; 64 KB is typical). Best performance, no redundancy.
    • RAID-1 mirroring: two copies (RAID-10 stripes over mirrors; RAID-01 mirrors stripes). Reads go to either copy; writes go to both (in parallel, but wait for the slower). A crash between the two copies is the consistent-update problem; fix with a write-ahead log, often in battery-backed NVRAM.
    • RAID-4 parity: one parity disk, P = XOR of the stripe. Any single lost block is reconstructed by XOR-ing the rest. Full-stripe writes are cheap; a small write needs the old data and old parity (subtractive parity: P_new = (C_old ⊕ C_new) ⊕ P_old) — 2 reads + 2 writes, and every write hits the one parity disk: random writes cap at R/2.
    • RAID-5: rotate parity across disks; random reads use all N and random writes reach (N/4)·R. Has replaced RAID-4 except where writes are always full-stripe. RAID-6 tolerates two failures; hot spares and rebuild are the other issues.
