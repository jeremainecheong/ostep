OSTEP chapters 29–31 · Lock-based Concurrent Data Structures · Condition Variables · Semaphores

Locking real data, waiting for conditions, and the semaphore that does both

Locks give mutual exclusion; they don't let a thread wait for something to happen. Condition variables do, and the producer/consumer problem shows every way to get them wrong. Then Dijkstra's semaphore: one integer that can act as a lock, an ordering primitive, or a counter of resources.

Primary sources: Ch 29, Ch 30, Ch 31. Code: threads-cv, threads-sema. For more puzzles the book recommends Downey's free Little Book of Semaphores.

What you'll be able to do

    Lock-based data structures (chapter 29)

    Crux: how to add locks to data structures so they are correct and allow many threads to use them at once (they scale)?

    Counters: precise vs approximate

    A single lock around counter++ is correct but scales terribly — the book measured one thread ~0.03 s for a million updates, and much worse with more threads on more CPUs. Approximate counter: one local counter (and lock) per CPU, plus a global; every S local increments, transfer the local value to the global. Bigger S → more scalable, less accurate; the book's plot shows near-perfect scaling with S = 1024.

    Threshold S = 5: a local counter that reaches 5 flushes into the global and resets.

    Lists, queues, hash tables

    • Linked list: one lock; keep lock/unlock around the whole insert but arrange the code so there's a single exit path (allocate outside the lock). Hand-over-hand locking (one lock per node, grab next before releasing previous) allows concurrency in theory but the per-node cost makes it slower in practice.
    • Queue (Michael & Scott): a head lock and a tail lock, with a dummy node separating them, so enqueue and dequeue proceed concurrently.
    • Hash table: a lock per bucket → scales beautifully (the book's chart: near-flat time vs inserts, versus a linearly-rising single-locked list).

    Knuth's law, the chapter's tip: start with one big lock (correct first), measure, and refine only if it's actually slow. Linux began with a single big kernel lock.

    Be wary of control flow around locks. Every early return inside a critical section is a chance to forget the unlock. Restructure so the lock is released in one place.

    Condition variables (chapter 30)

    Crux: how to wait for a condition. Spinning on a flag wastes CPU and can even be incorrect. A condition variable is an explicit queue threads join when a condition isn't true; another thread that changes the state wakes one (signal) or all (broadcast).
    // join(): parent waits for child. Three parts: a lock, a CV, and a state variable (done).
int done = 0; pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER; pthread_cond_t c = PTHREAD_COND_INITIALIZER;
void thr_exit() { Pthread_mutex_lock(&m); done = 1; Pthread_cond_signal(&c); Pthread_mutex_unlock(&m); }
void thr_join() { Pthread_mutex_lock(&m); while (done == 0) Pthread_cond_wait(&c, &m); Pthread_mutex_unlock(&m); }

    wait(cond, mutex) atomically releases the mutex and sleeps; on wakeup it re-acquires the mutex before returning. Drop the state variable and a child that exits first signals nobody, so the parent sleeps forever. Drop the lock and the parent can check done, be interrupted before waiting, miss the signal, and sleep forever. Rule: hold the lock when signalling and when waiting.

    The producer/consumer (bounded buffer) problem — find the bugs

    Producers put items in a buffer; consumers take them out (a shell pipe, a web server's request queue). Step through the three versions the book examines. The buffer has one slot; P is a producer, C1 and C2 consumers.

    • Mesa semantics (every real system): a signal is a hint that state changed; by the time the woken thread runs, another thread may have changed it back. So always re-check in a while. (Hoare semantics, in which the woken thread runs immediately, is harder to build.) A while also handles spurious wakeups.
    • One CV for two conditions lets a consumer wake a consumer; then everyone sleeps. Two CVs (empty, fill) direct signals to the right kind of thread. Then generalize to a ring buffer with count, fill_ptr, use_ptr.
    // the final, correct solution (single lock, two CVs, while loops)
void *producer(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        while (count == MAX) Pthread_cond_wait(&empty, &mutex);
        put(i);
        Pthread_cond_signal(&fill);
        Pthread_mutex_unlock(&mutex);
    }
}
void *consumer(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        while (count == 0) Pthread_cond_wait(&fill, &mutex);
        int tmp = get();
        Pthread_cond_signal(&empty);
        Pthread_mutex_unlock(&mutex);
        printf("%d\n", tmp);
    }
}
    Covering conditions. A memory allocator where threads wait for "enough" free bytes: a free(50) may wake a thread wanting 100 instead of one wanting 10 — so use pthread_cond_broadcast() and let each waiter re-check. Costs some needless wakeups; Lampson & Redell used it in Pilot. If your program only works with broadcast, you probably have a bug — unless it's this case.

    Semaphores (chapter 31)

    Crux: how to use semaphores instead of locks and CVs? What's a binary semaphore? Can you build one from the other?
    #include <semaphore.h>
sem_t s; sem_init(&s, 0, 1);          // value 1; second arg 0 = shared among threads of this process
int sem_wait(sem_t *s) { /* decrement; if value now negative, wait */ }      // Dijkstra's P()
int sem_post(sem_t *s) { /* increment; if a thread is waiting, wake one */ } // Dijkstra's V()
// invariant: when negative, the value equals the number of waiting threads

    Binary semaphore = lock

    Initial value 1. First wait makes it 0 and proceeds; a second thread makes it −1 and sleeps; post makes it 0 and wakes the sleeper.

    Semaphore for ordering = CV-like

    Initial value 0. Parent waits; child posts when done. Works whichever runs first: if the child finishes first the value is 1 and the parent's wait returns immediately. Rule of thumb for the initial value: how many resources can be handed out right away?

    Bounded buffer with semaphores — try it

    empty = 3full = 0mutex = 1
    MAX = 3. Watch counts go negative: that's how many threads are asleep. The book's first attempt put the mutex outside the empty/full waits — a producer then sleeps holding the mutex and the consumer that would free a slot can't get in: deadlock. Scope the lock tightly.

    Two classics

    Reader-writer lock

    Many readers may hold it at once; a writer needs exclusivity. Implementation: a lock semaphore protects readers; the first reader in acquires writelock, the last reader out releases it; writers just take writelock. Flaw: readers can starve writers. Extra bookkeeping often makes these slower than a plain lock — Hill's law: simple and dumb can be better.

    Dining philosophers (Dijkstra)

    Five philosophers, five forks, each needs both neighbours' forks to eat. Naive "left then right" deadlocks if all grab left at once. Fix: break the dependency — one philosopher grabs right first.

    Thread throttling: a semaphore initialized to the number of threads allowed in a memory-hungry region — admission control against thrashing. And implementing a semaphore ("Zemaphore") from a lock and a CV is easy: wait does while (value <= 0) cond_wait; value--; post does value++; cond_signal (this variant never goes negative). Building CVs from semaphores, however, is surprisingly tricky — the book's warning about generalization: "Don't generalize; generalizations are generally wrong" (Lampson).
