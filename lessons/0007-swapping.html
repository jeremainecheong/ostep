Beyond physical memory: swapping, and deciding what to evict

The last piece of the memory illusion: address spaces bigger than RAM. A present bit and a page-fault handler let the OS park pages on disk transparently. Then the policy question that dominated a decade of research: when memory is full, which page goes? The answer is "approximately LRU", and understanding why takes a few plots.

Primary sources: Ch 21, Ch 22, Ch 23. Homework: paging-policy.py. The classic paper behind ch 23 is Levy & Lipman on VAX/VMS (short, worth reading).

What you'll be able to do

    Mechanisms (chapter 21)

    Crux: how to go beyond physical memory. Use a larger, slower device (disk/SSD) to transparently provide the illusion of a large virtual address space. Why? Convenience: programmers needn't manage memory overlays by hand, and many large processes can coexist.
    • Swap space: a disk region the OS reads/writes in page-sized units, remembering a disk address for each swapped page. (Code pages can be dropped and re-read from the executable on disk instead.)
    • Present bit in the PTE: 1 = in memory; 0 = on disk. An access to a non-present page is a page fault.
    • Page-fault handler (always OS software, even with a hardware-managed TLB): find the disk address in the PTE, issue the disk read, block the process, and when it completes update the PTE (present = 1, PFN) and retry the instruction — which may now TLB-miss, then hit.
    • Replacement: if memory is full, evict a page first (write it out if dirty). In practice a background swap daemon keeps free frames between a low watermark and a high watermark, evicting in clusters for disk efficiency.

    Page-fault control flow, hardware and software

    Why not let hardware handle page faults? Disk I/O is slow (milliseconds) and the OS must block the process and run something else anyway; the extra software overhead is negligible. So hardware just traps.

    Policies (chapter 22)

    Crux: how to decide which page to evict. Memory is a cache for virtual pages; minimize misses. Average memory access time:

    AMAT = TM + (PMiss × TD)

    With memory ≈ 100 ns and disk ≈ 10 ms, a 90% hit rate gives ~1 ms per access — 10,000× slower than memory. Even 99.9% is ~10 µs. The disk cost dominates unless misses are very rare.

    Simulator: the book's reference stream, cache of 3 pages

    • Optimal: evict the page used furthest in the future. Not buildable (needs the future), but the yardstick: "80% vs OPT's 82%" is meaningful, "80%" alone is not. On the stream above: 6 hits, 5 misses; 3 of the misses are compulsory (first touch, "cold-start") so hit rate excluding them is 85.7%.
    • FIFO: evict the oldest. Simple, blind to popularity: 4/11 hits here. Suffers Belady's anomaly — a bigger cache can get worse (the book's stream 1,2,3,4,1,2,5,1,2,3,4,5 with 3 vs 4 frames). LRU has the stack property (a cache of N+1 contains the cache of N) so it never does.
    • Random: sometimes as good as OPT, sometimes awful; no pathological cases.
    • LRU (and LFU): use history — recency (or frequency) predicts the future via locality. Matches OPT on the stream above.

    • No locality: nothing helps; hit rate = cache size / 100 for every policy except OPT.
    • 80-20: LRU beats FIFO/random because it holds the hot 20% — the gain is modest, but each miss is so expensive that it matters.
    • Looping sequential: LRU and FIFO score zero with 49 frames for a 50-page loop — the worst case. Random has no such cliff. This motivates scan-resistant algorithms (ARC, Linux's 2Q).

    Implementing LRU: approximate it

    Crux: how to implement an LRU replacement policy without updating a data structure on every memory access? Perfect LRU is too expensive; approximate it with the hardware use bit (reference bit), set by hardware on any access to the page (first built in the Atlas one-level store).

    The clock algorithm: pages on a circular list with a clock hand. On replacement, look at the page under the hand: if its use bit is 1, clear it and advance; if 0, evict it. Try Clock in the simulator above. Prefer evicting clean pages (dirty ones must be written back first) by also inspecting the dirty bit. Other policies: demand paging vs prefetching (bring in page P+1 when P faults), clustering of writes. And thrashing: when demand exceeds memory, early systems used admission control (run fewer processes); Linux runs an out-of-memory killer. Or, as the book admits, buy more memory — though fast SSDs have revived replacement research.

    Complete systems: VAX/VMS and Linux (chapter 23)

    VAX/VMS (1970s, still instructive)

    • 32-bit address space, tiny 512-byte pages (→ big linear tables). Fix: split into P0 (code + heap) and P1 (stack) with a base/bounds pair each, and put the page tables themselves in kernel virtual memory so they can be swapped.
    • Page 0 is invalid — that's why NULL-pointer dereferences crash instead of silently reading memory.
    • Kernel mapped into every address space (protected by mode bits) so kernel code can touch user buffers easily.
    • Segmented FIFO: each process has a resident-set-size limit and a per-process FIFO; evicted pages go to global clean-page and dirty-page second-chance lists, from which a re-fault can reclaim them cheaply. Big lists ≈ LRU. Plus write clustering.
    • Laziness: demand zeroing (map a zero page only when touched) and copy-on-write (share pages read-only, copy on first write — makes fork() cheap).

    Linux (32-bit x86 view)

    • User portion 0–3 GB, kernel from 0xC0000000. Kernel logical addresses (via kmalloc) map contiguously to physical memory (logical − 0xC0000000), can't be swapped, and give physically contiguous buffers for DMA; kernel virtual (vmalloc) need not be contiguous. x86-64 uses four-level (now up to five-level) tables with the top 16 bits unused.
    • Huge pages (2 MB, some systems 1 GB): far more TLB coverage, shorter table walks; first via mmap/shmget flags, now transparent huge pages automatically. Cost: internal fragmentation, slower zeroing.
    • Page cache unifies file, anonymous and memory-mapped pages; dirty pages flushed by background pdflush threads. Replacement is a modified 2Q: an inactive and an active list (active ≈ ⅔), first reference goes inactive, a second promotes — scan-resistant, so a big sequential read can't flush the working set.
    • Security hardening: NX bit against stack-injected code; ASLR (randomize stack/heap/code) against return-oriented programming; kernel page-table isolation (KPTI) after Meltdown/Spectre — unmap most of the kernel from user page tables, at some context-switch cost.
