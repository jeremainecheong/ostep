Files across a network: building on parts that fail

In a data centre something is always broken, so the question flips: how do you build a system that works when its components don't? Communication is the heart of it; RPC makes it look like a function call. Then two distributed file systems that made opposite choices — NFS bet on statelessness, AFS on whole-file caching and server-issued promises.

Primary sources: Ch 48, Ch 49, Ch 50. Papers: Sandberg et al. (NFS, 1985), Howard et al. (AFS scale and performance, 1988), Birrell & Nelson (RPC). Try gRPC or Thrift to feel RPC yourself.

What you'll be able to do

    Distributed systems (chapter 48)

    Crux: how to build systems that work when components fail. Machines fail; that need not mean the system fails. Also in play: performance (few messages, fast handling) and security (authentication, privacy).

    Everything is built on messages over an unreliable network: packets are dropped by full buffers, corrupted by bit flips, misrouted. UDP gives you unreliable datagrams with a checksum. To get reliability, the sender waits for an acknowledgment and retries on timeout; but if only the ack was lost the receiver sees the message twice, so add sequence counters so the receiver can discard duplicates yet re-ack them. That's the core of TCP (plus exponential back-off on timeouts so a congested network isn't flooded). Which layer should guarantee what is the end-to-end argument: reliability the application needs must be checked by the application anyway.

    Remote procedure call makes this look like a call: a stub generator turns an interface into client stubs (marshal arguments into a buffer, send, wait, unmarshal the reply) and a server stub (unmarshal, call the real function, send the result). The run-time library handles naming, transport (usually built on UDP with its own acks/timeouts, since TCP's are redundant), timeouts and retries, byte ordering (Sun's XDR), and long-running calls (periodic acks to say "still working"). What doesn't translate: pointers (must be serialized), and the synchronous, blocking nature (some packages add async RPC). An older alternative, distributed shared memory, faded: failure handling and performance both suffer when a page fault may be a network round trip.

    NFS (chapter 49)

    Crux: how to build a distributed file system. Clients run applications that call open/read/write; a client-side file system turns them into messages to a file server, which stores the data. Goals: transparent sharing, central administration, security — and, above all for NFS, simple and fast crash recovery.
    Crux: how to define a stateless file protocol. The server keeps no per-client state, so it can crash and reboot and clients just retry. But POSIX has open()… The answer is the file handle — volume identifier + inode number + generation number (bumped when an inode is reused, so an old handle fails) — sent with every request instead of a descriptor. Client-side file system tracks the mapping from descriptors to handles and current offsets.

    open("/home/remzi/foo.txt") becomes three LOOKUPs (one per component) from the root handle obtained at mount; each read() a READ with an explicit offset; no OPEN or CLOSE messages exist. The client sets a timer; on timeout it retries. That is safe because the operations are idempotent — doing them twice equals doing them once (READ, WRITE with offset, LOOKUP; MKDIR is the awkward exception). Lost request, lost reply, or a server crash in between all look the same to the client and get the same fix: retry.

    Client caching and the consistency problem

    Caching blocks and buffering writes at the client cuts traffic, but with many clients: (1) update visibility — C1's buffered write isn't on the server yet; (2) stale cache — C2 cached the old version. NFS's engineering answers: flush-on-close (all dirty blocks are sent when a file is closed) and, before using a cached block, GETATTR to check the server's modification time — throttled by an attribute cache (~3 s) because the flood of GETATTRs was itself a problem. Result: behaviour that sometimes surprises (a fresh write may be invisible to another client for a few seconds).

    Two clients, one file

    Server-side: the server must commit each WRITE to stable storage before replying, or a crash loses data the client believes is safe (the book's example: three writes a/b/c, server crashes with b in memory, client never retries b, file ends up a/x/c). That made writes slow; NetApp's early business was battery-backed memory to acknowledge writes quickly. Sun also introduced the VFS/vnode interface so NFS and local file systems coexist in one kernel. NFS's basic security was weak (client-asserted user IDs); Kerberos-based authentication came later.

    AFS (chapter 50)

    Crux: how to design a scalable file protocol. Carnegie Mellon's goal was one server for as many clients as possible. AFSv1 already cached whole files on the client's local disk (open fetches the file; reads and writes are local; close stores it back) — but measurement showed servers saturating at about 20 clients: too much time walking pathnames, and too many TestAuth messages (clients asking "is my copy still valid?" on every open).

    AFSv2 fixes

    • Callbacks: when a client fetches a file the server promises to tell it if the file changes. Subsequent opens need no server contact — the client trusts its cache until the callback breaks. Polling becomes interrupts.
    • FIDs (volume id, file id, uniquifier) and client-side directory caching: the client walks the path itself, fetching directories (with callbacks) once.
    • Servers now handle ~50 clients; the common case — open a cached file, read it — needs no messages at all.

    Consistency and failure

    • Updates become visible on close: the server breaks callbacks on every other client with a copy; their next open refetches. Between processes on one machine, standard UNIX semantics apply. Two clients writing simultaneously: last writer (closer) wins — the whole file, never a mix. (NFS can end up with a block-level mixture.)
    • Crash recovery is harder than NFS: a rebooted client must treat its cache as suspect (it may have missed callbacks); a rebooted server has lost all callback state and must tell every client (or clients detect it via heartbeats) to revalidate.

    Performance (the book's Figure 50.4, in units of Lnet > Ldisk > Lmem): for most workloads the two are equal — small and medium files are cached in memory on both. AFS wins on the sequential re-read of a large file that fits on local disk but not in memory (Ldisk vs NFS's Lnet). AFS loses badly when you read a single block of a large file (it fetches all NL blocks: NL× slower), and pays roughly 2× on overwriting or partially writing a large file (fetch the whole file, then store it whole). AFS also added a global namespace (the same path on every machine), security with authenticated users, per-directory ACLs, and volumes for administration. The book's verdict: NFS became the open standard and won the market; NFSv4 has quietly grown server state and an open message — AFS's ideas live on.
