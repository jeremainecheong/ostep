OSTEP chapter 6 · Mechanism: Limited Direct Execution

Run the program directly — but keep control

The fastest way to run a program is to just run it on the CPU. The problem is what "just run it" gives up: the ability to stop it, and to stop it from doing dangerous things. Hardware and OS split the work. This is the mechanism under every scheduler.

What you'll be able to do

    Crux: how to efficiently virtualize the CPU with control. Efficiency says: run the program directly on the CPU. Control says: don't let it do anything it wants, and be able to take the CPU back. Both need hardware support.

    Problem 1: restricted operations

    If a process runs directly on the CPU, what stops it from reading any disk block or writing any memory? The answer is two processor modes and a controlled doorway between them.

    ModeWhat runsWhat it can do
    user modeapplicationsordinary computation only; an I/O instruction raises an exception and the OS likely kills the process
    kernel modethe OSeverything: issue I/O, change memory mappings, program devices

    A process asks for a privileged operation via a system call: it puts the system-call number in a register, executes a trap instruction, and the hardware jumps into the kernel and raises the privilege. When done, the OS issues return-from-trap, which lowers privilege and resumes the process where it left off.

    Who decides where the trap goes? Not the process — that would be a security hole. At boot, running in kernel mode, the OS fills the trap table with handler addresses and tells the hardware where it is (a privileged instruction). Afterward the hardware remembers until reboot. The syscall number is a form of protection too: user code names a service, never an address.
    What the hardware saves. On x86 the trap pushes the PC, flags and a few registers onto the process's kernel stack; return-from-trap pops them. That is how the OS gets back exactly where the program left off.

    Problem 2: switching between processes

    If the process is running, the OS isn't. How does the OS get the CPU back?

    Cooperative: wait for a system call

    Old approach (early Macintosh, Xerox Alto): trust processes to give up the CPU by making system calls, including an explicit yield(). Illegal operations (divide by zero, bad memory access) also trap into the OS. Flaw: a process in an infinite loop never traps. Your only recourse is to reboot.

    Non-cooperative: the timer interrupt

    Program a timer to raise an interrupt every few milliseconds. The running process is halted and a pre-configured handler runs — the OS is back in charge and may switch. The OS starts the timer at boot (privileged) and can turn interrupts off (also privileged). The hardware saves enough state that return-from-trap can resume the interrupted process.

    The context switch, precisely

    Two saves happen, and students mix them up. (1) On the trap/interrupt, the hardware implicitly saves the user registers of the running process onto its kernel stack. (2) If the OS decides to switch, the OS explicitly saves the kernel registers of A into A's process structure and restores B's from B's, then switches to B's kernel stack. When the handler finally returns-from-trap, it pops B's user registers — so B, not A, resumes.

    # xv6 context switch (Figure 6.4). void swtch(struct context *old, struct context *new);
.globl swtch
swtch:
  # Save old registers
  movl 4(%esp), %eax    # put old ptr into eax
  popl 0(%eax)          # save the old IP
  movl %esp, 4(%eax)    # and stack
  movl %ebx, 8(%eax)    # and other registers
  movl %ecx, 12(%eax)
  movl %edx, 16(%eax)
  movl %esi, 20(%eax)
  movl %edi, 24(%eax)
  movl %ebp, 28(%eax)

  # Load new registers
  movl 4(%esp), %eax    # put new ptr into eax
  movl 28(%eax), %ebp   # restore other registers
  movl 24(%eax), %edi
  movl 20(%eax), %esi
  movl 16(%eax), %edx
  movl 12(%eax), %ecx
  movl 8(%eax), %ebx
  movl 4(%eax), %esp    # stack is switched here
  pushl 0(%eax)         # return addr put in place
  ret                   # finally return into new ctxt

    Worried about concurrency?

    What if an interrupt arrives while the OS is handling another one? Two standard answers: disable interrupts while handling one (briefly — too long and you lose interrupts), and use locking around internal data structures so many activities in the kernel can proceed at once. Part 2 of the book is about this.

    How long does this take? The book cites lmbench: in 1996 a syscall took ~4 µs and a context switch ~6 µs on a 200 MHz P6; modern systems are sub-microsecond. But not everything tracks CPU speed — many OS operations are memory-bound, and memory bandwidth improved much less than CPUs (Ousterhout).
    Baby-proofing the CPU. The book's image for LDE: lock the cabinets (trap handlers set up at boot), start the timer, then let the baby (process) roam in a restricted mode, secure that the dangerous things are locked away.
