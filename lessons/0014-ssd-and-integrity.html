Flash SSDs: a log-structured device — and how storage lies to you

Flash can't overwrite a page; it must erase a whole block first, and every erase wears it out. So inside every SSD is a small log-structured file system called the flash translation layer. Then the failures RAID's fail-stop model ignores: sectors that quietly go bad, and blocks that return the wrong data with a smile. Checksums are how a file system stops trusting its disk.

Primary sources: Ch 44, Ch 45. Papers the book leans on: Agrawal et al. (SSD design space), the "unwritten contract" of SSDs (He et al.), Bairavasundaram et al. on latent sector errors and corruption in 1.5 million drives.

    Flash: bits, pages, blocks (chapter 44)

    Crux: how to build a flash-based SSD. How to handle the expensive erase, and how to build a device that lasts when repeated overwrites wear it out?

    A flash cell traps charge in a transistor: SLC stores 1 bit, MLC 2, TLC 3 (more bits per cell → cheaper, slower, shorter-lived). Cells form pages (1–8 KB... the unit you read or program) inside erase blocks (128–256 KB, up to 2 MB; the unit you erase) inside banks/planes. Three operations:

    Reliability: each block survives a limited number of program/erase cycles (rated ~10,000 for MLC, ~100,000 for SLC; in practice more) — wear out. And programming a page can flip bits in neighbours (program disturbance), so FTLs program pages within a block in order, low to high.

    The flash translation layer

    The FTL turns reads and writes on logical blocks into reads, programs and erases on physical pages, while pursuing performance (parallelism across chips; low write amplification = bytes written to flash ÷ bytes the client wrote) and reliability (wear leveling, disturbance avoidance). A direct-mapped FTL (logical page N always lives in physical page N) is a disaster: every write reads the whole block, erases it, and reprograms everything — write amplification equal to the block/page ratio, and hot logical pages burn out their block. So real FTLs are log-structured:

    Three blocks of four pages (E = erased, V = valid, struck = invalid/old). Writes append to the next free page; the mapping table records where each logical block lives. Overwrite a block and its old page becomes garbage.
    • Garbage collection: pick a block with dead pages, read its live pages, write them to the end of the log, erase the block. Costs reads, writes and an erase — the write amplification you pay for logging. Devices overprovision capacity and clean in the background. The trim command tells the FTL a logical range is deleted so it needn't preserve it.
    • Mapping table size: a page-level map costs 4 bytes per 4 KB page — 1 GB of DRAM for a 1 TB SSD. Block-level mapping (like big virtual-memory pages) shrinks it but makes small writes copy whole blocks. Hybrid FTLs keep a few page-mapped log blocks and many block-mapped data blocks, merging with switch (best: a log block filled in order simply becomes a data block), partial, or full merges. Modern devices cache the hot part of a page-level map instead.
    • Wear leveling: because the log spreads writes naturally, most blocks age evenly; but blocks full of long-lived cold data never get erased, so the FTL periodically migrates that data to even out wear (more write amplification).

    Three lessons: SSDs' random I/O is tens to hundreds of MB/s where the hard drive manages 2; sequential is still better than random even on flash (the unwritten contract); and random writes beat random reads because the log makes them sequential internally. The remaining gap is cost: the book quotes roughly 60 cents per GB for flash versus about 5 cents for disk, so archival stays on disk while performance-critical data moves to flash.

    Data integrity (chapter 45)

    Crux: how to ensure data integrity given failures more subtle than fail-stop — with low space and time overhead?

    Two partial-failure modes from Bairavasundaram et al.'s three-year study of 1.5 M drives. Latent sector errors (LSEs): a sector is unreadable (head crash, cosmic rays); the drive's own error-correcting codes detect it and return an error. Block corruption: the drive returns wrong data with no error — a buggy firmware write, a faulty bus, a bit flip. Cheap drives: 9.40% had an LSE and 0.50% corruption; enterprise drives: 1.40% and 0.05%. Both grow with age, cluster in space and time, and are found mostly by scrubbing.

    LSEs are easy

    Because they are detected, just use your redundancy: read the mirror copy, or reconstruct from parity. But a RAID-4/5 rebuild after one whole-disk failure now risks hitting an LSE on another disk — one reason RAID-DP (two parity disks, NetApp) exists.

    Corruption needs detection: the checksum

    A small function of the data (4–8 bytes) stored alongside it; on read, recompute and compare. Mismatch → use another copy, or report an error. Stronger checksums cost more compute:

    • XOR of all words: cheap; misses two bits flipped in the same position.
    • Addition (2's-complement sum): fast; misses shifted data.
    • Fletcher: two running sums s1 += d, s2 += s1 (mod 255); catches all single-bit, double-bit and most burst errors.
    • CRC: treat the data as a polynomial, divide by an agreed value, keep the remainder; the standard in networking.

    Layout and the two harder faults

    • Layout: drives with 520-byte sectors put the 8-byte checksum with each 512-byte sector; otherwise pack a sector's worth of checksums ahead of every n data sectors (cheaper for reads, an extra write for small updates).
    • Misdirected writes: the controller writes the right data to the wrong disk or sector; the checksum matches its data, so it passes. Fix: add a physical identifier (disk number + sector offset) to the stored checksum block and check it on read.
    • Lost writes: the device reports success but never wrote; old data with an old, valid checksum remains. Fixes: write verify (read after write — doubles write cost), or store checksums elsewhere too — ZFS keeps every block's checksum in its parent inode/indirect block, so a lost write to either the data or the checksum is caught unless both are lost.
    • Scrubbing: periodically read the whole disk and verify checksums (nightly or weekly) so cold data doesn't rot unnoticed.
    • Overheads: space is tiny (8 B per 4 KB ≈ 0.19%); time is the CPU cost of computing (combine with the data copy) and, for some layouts, extra I/O. Well-designed systems make integrity nearly free.
