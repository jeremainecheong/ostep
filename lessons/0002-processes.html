The process: a running program, and the API that makes one

The first big abstraction. A process is what the OS turns a dead program on disk into: memory, registers, and open files, plus a state machine the OS drives. UNIX creates one with the strangest pair of calls you'll ever use: fork() and exec().

Primary sources: Chapter 4 and Chapter 5. Code for chapter 5 (p1.c–p4.c) is in ostep-code/cpu-api; type it in and run it. For depth, the book points to Stevens & Rago, Advanced Programming in the UNIX Environment.

What you'll be able to do

    Crux: how to provide the illusion of many CPUs? There are only a few physical CPUs. By running one process, stopping it, running another, and so on — time sharing — the OS makes it look like there are endless virtual CPUs. The cost is performance: each runs slower when the CPU is shared. Doing this needs low-level mechanisms (the context switch) and high-level policies (the scheduler).

    What a process is: its machine state

    To describe a process at any instant you need three things. Everything the OS saves and restores when switching lives in one of these.

    Creating a process, step by step

    Eager vs lazy. Early systems loaded all code and data up front (eagerly). Modern OSes load pieces only when needed (lazily) — that requires paging and swapping, which come in lessons 6–7.

    Process states — click the events

    In the simplified view a process is Running, Ready (could run, but the OS chose not to right now), or Blocked (waiting on something, typically I/O). Drive the machine yourself; illegal transitions are refused.

    What the OS keeps: the process list and PCB

    The OS tracks every process in a process list; each entry is a process control block (PCB). Here is the real one from xv6 — small enough to read in full. The context field is where registers go when the process is stopped; restoring them resumes it (the context switch, next lesson).

    // xv6: the registers saved and restored to stop and restart a process
struct context { int eip; int esp; int ebx; int ecx; int edx; int esi; int edi; int ebp; };

enum proc_state { UNUSED, EMBRYO, SLEEPING, RUNNABLE, RUNNING, ZOMBIE };

struct proc {
  char *mem;                 // Start of process memory
  uint sz;                   // Size of process memory
  char *kstack;              // Bottom of kernel stack for this process
  enum proc_state state;     // Process state
  int pid;                   // Process ID
  struct proc *parent;       // Parent process
  void *chan;                // If !zero, sleeping on chan
  int killed;                // If !zero, has been killed
  struct file *ofile[NOFILE];// Open files
  struct inode *cwd;         // Current directory
  struct context context;    // Switch here to run process
  struct trapframe *tf;      // Trap frame for the current interrupt
};

    The process API: fork, wait, exec

    Crux: how to create and control processes? What interfaces should the OS present, and how should they be designed for power, ease of use, and performance?

    Why such a strange API? Because of the shell

    The separation of fork() from exec() is the point. The shell forks, and in the gap before exec it can rewire the child's environment — close stdout, open a file so it lands in fd 1, then exec wc. wc never knows. Pipes work the same way with pipe(): one process's output fd connected to another's input fd. Lampson's law, quoted by the book: get it right — neither abstraction nor simplicity substitutes for getting it right.

    Control and users

    • Signals: kill() sends one. Control-C sends SIGINT (interrupt, usually terminates); Control-Z sends SIGTSTP (stop/pause; resume later with fg). A process can catch signals with signal().
    • Users: the OS lets many users in and ensures each can only control their own processes. The superuser (root) can control any — the book's advice is to run as a regular user and tread carefully as root.
    • Tools: ps, top, kill, killall. The book suggests always having a CPU meter visible.
