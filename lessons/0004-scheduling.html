Scheduling: who runs next, and by what measure

The context switch is the mechanism; scheduling is the policy. Two families of policies pull in opposite directions — finish short jobs early, or give everyone a quick turn — and the multi-level feedback queue gets the best of both by watching what jobs actually do.

Primary sources: Ch 7, Ch 8, Ch 9, Ch 10. Homework simulators: scheduler.py, mlfq.py, lottery.py, multi.py in ostep-homework.

What you'll be able to do

    Assumptions and metrics (chapter 7)

    The book starts with a deliberately unrealistic workload and relaxes it one assumption at a time: (1) every job runs the same length, (2) all arrive at the same time, (3) each runs to completion once started, (4) jobs only use the CPU, (5) run-times are known. Two metrics matter:

    Turnaround time (performance)

    Tturnaround = Tcompletion − Tarrival

    How long from arrival to finish. Minimized by running short things first.

    Response time (interactivity)

    Tresponse = Tfirstrun − Tarrival

    How long until it first gets the CPU. Minimized by giving everyone a turn quickly.

    Simulator: FIFO, SJF, STCF, RR

    The trade-off is inherent. SJF/STCF optimize turnaround and are terrible for response; RR optimizes response and is among the worst for turnaround (it stretches every job). The book: "both are bad where the other is good." The RR quantum must be a multiple of the timer period; too short and context-switch cost dominates — amortize it with a longer slice.

    Incorporating I/O

    Treat each CPU burst between I/Os as its own job. When A issues I/O and blocks, STCF runs B in the gap; when A's I/O completes, A (now with a short remaining burst) preempts. This overlap keeps the CPU busy while the disk works.

    MLFQ: scheduling without knowing job lengths (chapter 8)

    Crux: how to schedule without perfect knowledge? Minimize response time for interactive jobs and turnaround for everyone, with no a-priori knowledge of job length. Answer: learn from history.

    Several queues, each a priority level. A job's priority is set by observed behaviour: if it keeps giving up the CPU (interactive) it stays high; if it burns whole time slices (CPU-bound) it sinks. The book refines the rules three times; the final set is:

    1. If Priority(A) > Priority(B), A runs (B doesn't).
    2. If Priority(A) = Priority(B), A and B run in round-robin using that queue's time slice.
    3. When a job enters the system, it is placed at the highest priority.
    4. Once a job uses up its time allotment at a level (regardless of how many times it gave up the CPU), its priority is reduced.
    5. After some period S, move all jobs to the topmost queue.

    Step through why each refinement was needed:

    Tuning. How many queues, how long a slice per queue, how often to boost — these are the "voo-doo constants" Ousterhout warned about. Solaris's MLFQ (the Time-Sharing class) uses 60 queues with slices from ~20 ms (high priority) to a few hundred ms, boosting about every second. Some systems let admins change defaults or let users give advice (nice). BSD UNIX, Solaris and Windows NT and later all use an MLFQ variant as base scheduler.

    Proportional share: lottery, stride, CFS (chapter 9)

    Crux: how to share the CPU proportionally? Instead of optimizing turnaround or response, guarantee each job a percentage of CPU time.

    Lottery scheduling

    Tickets represent share. Hold a lottery each slice: with A = 75 tickets, B = 25, A should win about 75% of the time. Randomness is light on state and handles corner cases gracefully, but only approaches the target over time (the book measures an unfairness metric U that approaches 1 as jobs get longer). Mechanisms: ticket currency (users hand out their own tickets), transfer (client → server), inflation (trusted processes raise their own count).

    Stride scheduling (deterministic)

    Each job has a stride inversely proportional to its tickets (book: 10000/tickets → A 100, B 200, C 40) and a pass counter. Always run the lowest pass, then add its stride. Exact proportions, but it needs global state: a new job's pass must be set sensibly or it monopolizes the CPU — lottery has no such issue.

    Linux CFS, the fair scheduler you actually use

    Each process accumulates vruntime; pick the smallest. The slice comes from sched_latency (e.g. 48 ms) divided among runnable processes, floored by min_granularity (e.g. 6 ms) so slices don't get absurdly small. nice values (−20..+19) map to weights; the slice is proportional to weight and vruntime advances slower for heavier processes:

    time_slice_k = weight_k / Σ weight_i × sched_latency
vruntime_i  += weight_0 / weight_i × runtime_i      // weight_0 = 1024 (nice 0)

static const int prio_to_weight[40] = {
 /* -20 */ 88761, 71755, 56483, 46273, 36291,  /* -15 */ 29154, 23254, 18705, 14949, 11916,
 /* -10 */  9548,  7620,  6100,  4904,  3906,  /*  -5 */  3121,  2501,  1991,  1586,  1277,
 /*   0 */  1024,   820,   655,   526,   423,  /*   5 */   335,   272,   215,   172,   137,
 /*  10 */   110,    87,    70,    56,    45,  /*  15 */    36,    29,    23,    18,    15 };

    Runnable processes live in a red-black tree keyed by vruntime (O(log n) insert, O(1) min). A process waking after a long sleep gets its vruntime set to the tree's minimum so it doesn't starve everyone else. Weaknesses of fair-share schedulers: I/O-heavy jobs can miss their share, and someone must assign tickets/nice values — general-purpose schedulers like MLFQ handle that automatically. Proportional share shines in clouds and VMs ("give this VM one quarter of the CPU").

    Multiprocessor scheduling (chapter 10)

    Why it's different: caches

    Each CPU has its own cache. Cache coherence (via bus snooping) keeps copies consistent so correctness is fine, but performance depends on cache affinity: a job that keeps running on the same CPU finds its state warm. And kernel data shared across CPUs needs locks, which limit scaling.

    Two designs

    SQMS — one queue for all CPUs. Simple, balances load naturally; but the shared lock doesn't scale and jobs bounce between CPUs (poor affinity) unless you add affinity hacks.

    MQMS — one queue per CPU. Scales, affinity for free; but load imbalance needs migration, e.g. work stealing (an idle queue peeks at a busier one occasionally — not too often, or the peeking itself costs).

    Linux has had three: the O(1) scheduler (priority, MLFQ-like), CFS (proportional), and BFS (single queue, proportional). No consensus: "small code changes can lead to large behavioral differences."
