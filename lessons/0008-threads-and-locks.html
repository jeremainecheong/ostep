Threads, the race they create, and the lock that tames it

Concurrency starts here. A thread shares its address space with other threads, so a single counter++ becomes a three-instruction race the scheduler can lose for you. The fix is a lock — but building a correct, fair, fast one needs help from the hardware and the OS.

Primary sources: Ch 26, Ch 27, Ch 28. Code: threads-intro, threads-locks. Homework: x86.py lets you step interleavings by hand. Read man -k pthread for the full API.

What you'll be able to do

    Threads (chapter 26)

    A thread is like a process but shares the address space with its siblings. Each has its own PC, registers, and stack (thread-local storage), so a context switch between threads saves registers into a thread control block but leaves the page table alone. Why threads? Parallelism on multiple CPUs, and avoiding blocking — while one thread waits on I/O another runs, sharing data more naturally than separate processes would.

    Crux: how to support synchronization. Instructions execute one at a time but the scheduler interleaves threads arbitrarily. What hardware primitives and OS support let us build correct concurrent programs?

    Vocabulary you'll use for the rest of the book: a race condition (data race) is when the result depends on timing; the outcome is indeterminate; the code touching shared state is a critical section; what we want is mutual exclusion — one thread inside at a time — so the section runs atomically, "all or nothing". The book's point about why OS class: the kernel was the first concurrent program; interrupts can arrive between any two instructions, so every kernel structure (page tables, process lists, file-system bitmaps) is a critical section.

    The thread API (chapter 27)

    #include <pthread.h>
int pthread_create(pthread_t *thread, const pthread_attr_t *attr, void *(*start_routine)(void*), void *arg);
int pthread_join(pthread_t thread, void **value_ptr);      // wait for completion; retrieve return value

pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;         // or pthread_mutex_init(&lock, NULL)
int rc = pthread_mutex_lock(&lock);   assert(rc == 0);    // the book wraps calls to check return codes
x = x + 1;                                                // critical section
pthread_mutex_unlock(&lock);
// also pthread_mutex_trylock() (fail instead of wait), pthread_mutex_timedlock()

pthread_cond_t cond = PTHREAD_COND_INITIALIZER;
pthread_mutex_lock(&lock);
while (ready == 0) pthread_cond_wait(&cond, &lock);       // releases lock while sleeping, re-acquires on wake
pthread_mutex_unlock(&lock);
// signaler: lock; ready = 1; pthread_cond_signal(&cond); unlock.   Compile with: gcc -o main main.c -Wall -pthread
    The chapter's guidelines. Keep it simple. Minimize thread interactions. Initialize locks and CVs. Check return codes. Be careful passing pointers to stack variables into a thread — the stack frame may be gone (never return a pointer to a thread's stack). Each thread has its own stack. Always signal with condition variables, not flags. Use the man pages.

    Locks (chapter 28)

    Crux: how to build a lock. Efficient mutual exclusion at low cost. What hardware support? What OS support?

    A lock is a variable holding free or held (plus, perhaps, the owner and a queue). lock() acquires it or waits; unlock() frees it and lets a waiter in. The programmer chooses granularity: one coarse lock or many fine ones. Evaluate every design on three axes:

    ApproachCorrect (mutual exclusion)?Fair (no starvation)?Performance
    Disable interruptsyes, on one CPU–Trusts apps (they could loop forever); useless on multiprocessors; loses interrupts; slow instructions. Only for the OS itself.
    Loads/stores on a flagno — both threads can read 0 before either writes 1–spin-waits
    Test-and-set spin lockyesnoTerrible on one CPU (a preempted holder makes everyone spin a whole slice); fine on multiple CPUs if critical sections are short.
    Ticket lock (fetch-and-add)yesyes (FIFO)still spins
    Yield instead of spinyesnoSaves the wasted slice but wastes context switches; with 100 threads, 99 yield in turn.
    Queue + park/unpark (Solaris) / futex (Linux)yesyesSleep instead of spin; the real thing.

    Too much spinning: bring in the OS

    Crux: how to avoid spinning without wasting CPU? Hardware alone can't; we need OS support.
    • Just yield: while (TestAndSet(&flag,1)==1) yield(); gives up the CPU instead of a slice. Better, but with many threads it's still a lot of switching and starvation is possible.
    • Queues + park()/unpark() (Solaris): a small guard spin lock protects the lock's flag and queue; a would-be acquirer enqueues itself and calls park() to sleep; unlock hands the lock directly to the next queued thread via unpark(). The wakeup/waiting race (unpark arrives just before park) is closed by setpark(): "I'm about to park; if someone unparks me first, return immediately."
    • Linux futex: per-address kernel queue; futex_wait(addr, expected) sleeps only if *addr == expected, futex_wake(addr) wakes one. The high bit of the lock word encodes held/free, the rest counts waiters, so the uncontended path is a single atomic op in user space.
    • Two-phase locks: spin briefly (the lock may be about to free up), then sleep. A hybrid — the book's recurring pattern.
    Priority inversion (the Mars Pathfinder story): a low-priority thread holding a spin lock, a high-priority thread spinning for it, and a medium-priority thread starving the low one. Fixes: priority inheritance, or don't mix spin locks with priorities.
