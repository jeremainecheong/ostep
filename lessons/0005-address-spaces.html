Address spaces: the second illusion, and how hardware translates it

Every pointer you have ever printed was a lie — a virtual address. The OS gives each process a private, large, contiguous address space starting at 0, then uses hardware to redirect every load and store to wherever the bytes really are. This lesson builds that hardware up from a single pair of registers.

Primary sources: Ch 13, Ch 14, Ch 15, Ch 16. Homework: relocation.py, segmentation.py. For C memory, the book sends you to K&R and Stevens; use valgrind on everything you write.

What you'll be able to do

    The abstraction: an address space (chapter 13)

    Early machines ran one program that used all memory. Time sharing meant several processes resident at once, and saving whole memory images to disk on every switch was far too slow — so processes stayed in memory, which made protection the issue. The abstraction that solved it:

    Crux: how to virtualize memory. Build this private, potentially large address space for many processes at once on top of one physical memory. Three goals: transparency (the program doesn't know), efficiency (time and space — needs hardware help), protection (isolation from other processes and the OS).
    Every address you see is virtual. Print main's address, a malloc result, and a stack variable's address (the book's va.c): all virtual, all an illusion. Only the OS and hardware know the physical truth.

    Interlude: the memory API (chapter 14)

    Two kinds of memory in C. Stack (automatic): the compiler allocates and frees it when a function is entered and exits. Heap: you ask with malloc(size) and must give back with free(ptr). malloc and free are library calls; underneath, the library grows the heap with the brk/sbrk system calls, or gets anonymous memory via mmap.

    double *d = (double *) malloc(sizeof(double));   // use sizeof, not a number
int *x = malloc(10 * sizeof(int));               // array of 10 ints
char *dst = (char *) malloc(strlen(src) + 1);    // +1 for the terminating '\0'
free(x);                                         // no size argument: the library remembers
// also: calloc() zeroes memory; realloc() grows a region and copies

    Mechanism: address translation (chapter 15)

    Crux: how to efficiently and flexibly virtualize memory, while keeping control over which locations a process may touch. The generic technique is hardware-based address translation: on every memory reference the hardware turns the virtual address into a physical one. The OS manages memory and sets up the hardware; the book calls this dynamic relocation, or base and bounds.

    Two registers per CPU, part of the memory management unit (MMU): base and bounds. For every access: physical = virtual + base, after checking virtual < bounds. Both registers are privileged; the OS sets them when it schedules a process and saves/restores them on a context switch.

    Try it: the book's example (process loaded at physical 32 KB, 16 KB address space)

    Book values: the instruction at virtual 128 lands at physical 32896; a load from virtual 15 KB goes to 47 KB; anything ≥ 16 KB faults. Some hardware stores bounds as the end physical address instead — same idea.

    What each side must do

    Hardware

    • Privileged mode (two modes).
    • Base/bounds registers in the MMU.
    • Translate + check on every access.
    • Privileged instructions to update base/bounds and to register exception handlers.
    • Raise exceptions on out-of-bounds or privileged-instruction misuse.

    Operating system

    • At process creation: find room via a free list of physical slots, set the registers.
    • At termination: reclaim memory onto the free list.
    • At context switch: save/restore base and bounds in the PCB. (While a process is descheduled the OS may even move it: copy, update base.)
    • Install exception handlers at boot; typically kill the offending process.

    The problem: the process's 16 KB is placed as one block, so the free space between heap and stack sits in physical memory doing nothing — internal fragmentation. That motivates the next step.

    Segmentation (chapter 16)

    Crux: how to support a large address space with a lot of possibly-empty space between stack and heap? A 32-bit (4 GB) address space would demand 4 GB resident even if the program uses megabytes.

    Generalize: one base/bounds pair per logical segment — code, heap, stack. Each segment sits independently in physical memory; the gap is never allocated. The book's segment table:

    SegmentBaseSize (max 4K)Grows positive?Protection
    Code 0032K2K1Read-Execute
    Heap 0134K3K1Read-Write
    Stack 1128K2K0Read-Write

    Which segment? The explicit approach uses the top bits of the virtual address (here the top 2 of 14 bits; 11 = stack, and 10 is wasted). The implicit approach infers it from how the address was formed (PC → code, stack pointer → stack, otherwise heap). The stack grows negative, so its offset is computed differently — try it.

    Segmentation translator (14-bit VA, explicit top-2-bit segment)

    // Segment  = (VirtualAddress & SEG_MASK) >> SEG_SHIFT
// Offset   = VirtualAddress & OFFSET_MASK
// if (Offset >= Bounds[Segment]) RaiseException(PROTECTION_FAULT)
// else PhysAddr = Base[Segment] + Offset;  Register = AccessMemory(PhysAddr)

    Sharing: with protection bits, a read-execute code segment can be mapped into several processes at once. Fine-grained segmentation (Multics, Burroughs B5000) used many segments and a segment table; coarse-grained uses a few. OS duties grow: save/restore segment registers on switch, handle segment-growth requests (sbrk), and manage variable-sized free space — which brings external fragmentation: free memory chopped into odd-sized holes. Compaction fixes it but is expensive; smart allocators (next lesson) only mitigate it. And a large sparsely-used heap still must be entirely resident. Hence: paging.
