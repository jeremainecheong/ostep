Security: policies, identities, access, cryptography — and one more layer of virtualization

Every mechanism in this book — modes, page tables, file permissions — is also a security mechanism. These chapters make that explicit: what we protect, who a process is, how the OS decides yes or no, and what cryptography can do once data leaves the OS's custody. The appendix closes the loop: virtualize the whole machine, and the OS becomes the program being fooled.

Primary sources: Ch 53, Ch 54, Ch 55, Ch 56, Ch 57, Appendix B. Classic papers: Saltzer & Schroeder (1975); Bugnion et al., Disco (1997).

What you'll be able to do

    Goals and principles (chapter 53)

    Crux: how to secure OS resources. With many interacting processes on one machine, ensure each can access exactly the resources it should, in exactly the ways we intend. What primitives from the OS, what mechanisms from hardware?

    What are we protecting? Everything — the OS controls all hardware, so a compromised OS is a limitlessly compromised machine. Goals come in three classic flavours: confidentiality (secrets stay secret), integrity (data and components aren't improperly changed; authenticity is a cousin), availability (services stay usable). Each system turns these into specific policies, and, as everywhere in the book, the OS separates policy from mechanism. The chapter's design principles, from Saltzer and Schroeder — flip each:

    The OS's own basics: virtualization of processes and memory is protection; system calls are the mediated entry; and the OS must know who is asking — the next chapter.

    Authentication (chapter 54)

    Crux: how to securely identify processes. Each process must carry the right identity (a principal — usually a user id), new processes must get the right one, and nothing malicious may change it.

    Processes inherit identity from their parent, so the chain starts at boot with a system process whose job is to log users in: it authenticates a human and starts a shell owned by that user. Controlled exceptions change identity: setuid programs run with their owner's id (how sudo and passwd work). Three ways a human proves identity:

    What you know

    Passwords. Never store them; store a cryptographic hash (SHA-3 is the book's example). Add a per-user salt so identical passwords hash differently and precomputed dictionary attacks fail. Limit guesses; the hash makes online guessing slow, the salt makes offline guessing expensive.

    What you have

    A smart card, a phone, a hardware token — proof of possession, often via a one-time code. Weakness: it can be lost or stolen.

    What you are

    Biometrics: fingerprints, face, voice. Matching is probabilistic, so tune between false positives (admitting the wrong person) and false negatives (rejecting the right one); and remote biometrics prove only that some bits arrived.

    Combine them: multi-factor authentication (password + a code texted to your phone). Non-human principals (servers, daemons) authenticate with keys and certificates — chapter 57.

    Access control (chapter 55)

    Crux: how to determine if an access request should be granted. Given a process, a user, an object and a moment, decide yes or no — and be able to encode the policies we want.

    The decider is a reference monitor that ideally achieves complete mediation. Conceptually, access is a matrix of subjects × objects; the two implementations slice it differently. Click a cell:

    Rows = subjects, columns = objects. An ACL stores a column with each object ("who may touch this file"); a capability list stores a row with each subject ("what this process may touch").

    Access control lists

    Per object. UNIX's 9 permission bits are a condensed ACL: owner / group / other × read / write / execute; the OS looks up the requester and checks the file's bits. Good for "who can access this file?", for revocation (edit the list), and it's what users see. Costly to answer "what can this user access?", and identities must be meaningful across machines (a Wisconsin ACL means nothing to a Berkeley user id).

    Capabilities

    Per subject: an unforgeable token whose possession grants access, like a ticket or a key. The OS keeps them (a process must not fabricate one) — a UNIX file descriptor is a capability: checked at open(), then presented on every read(). Cheap to check, easy to delegate, natural for least privilege; hard to revoke or to audit who can reach an object. Most systems use ACLs at the user level and capabilities inside the kernel.

    Discretionary access control lets owners set permissions; mandatory access control imposes system-wide rules owners can't override (classified-data systems). Helpers: role-based access control (grant permissions to roles like administrator, assign users to roles) and type enforcement (label subjects and objects with types and write rules between types). The chapter's warning: failures rarely come from broken mechanisms; they come from badly designed policies.

    Cryptography (chapter 56)

    Crux: how to protect information outside the OS's domain — on a stolen disk, on the network — so others can neither use nor alter it? What technologies, how to use them properly, and what can't they do?

    Symmetric ciphers

    One shared secret key encrypts and decrypts (AES). Fast; the problem is key distribution.

    Public-key (asymmetric)

    A key pair: encrypt with the public key → only the private key decrypts (secrecy); encrypt with the private → anyone with the public key can verify who sent it (authentication, signatures). RSA. Slow, so used to exchange symmetric keys.

    Cryptographic hashes

    No key, not reversible: a fixed-size fingerprint (SHA-3; SHA-1 is broken). Any change to the input changes the hash unpredictably; used for passwords, integrity checks, signatures.

    Alice → Bob with two keys

    Cracking: ciphers are public; security lives entirely in the key. Brute force scales with key length (exponentially), so use standard algorithms with long keys — and never invent your own cipher. OS uses: data in transit (next chapter) and at-rest encryption — full-disk encryption in hardware or software, decrypting as blocks enter the OS, protecting against a stolen laptop but not a running attacker (the key is in memory). Also cryptographic capabilities: tokens the system signs or MACs so users may hold them yet can't forge them — how distributed systems hand out access. Keep keys in as few places, for as short a time, as possible.

    Hash it yourself (SHA-256, in-browser)

    Change one character: the whole digest changes. Add a salt: the same password gives a different stored value per user, defeating precomputed tables.

    Distributed system security (chapter 57)

    Crux: how to protect distributed system operations. The network is insecure; make sure it introduces no new problems: messages encrypted and authenticated, service available only to intended users.
    • Public keys across machines: how do you know a public key is really Microsoft's? Certificates (X.509): a trusted certificate authority signs the binding of name to public key; you trust the CA's key (pre-installed in your browser), so you can verify anyone it vouches for. Self-made certificates prove nothing.
    • Passwords across machines: only ever over an already-encrypted, authenticated channel — the server's identity must be established first, or you hand your password to an impostor.
    • SSL/TLS: encrypted sockets. Use TLS; SSL itself is broken and only acceptable for ancient devices that support nothing else (and even early TLS versions had flaws). The handshake negotiates algorithms, verifies the server's certificate, and agrees a symmetric session key, typically via Diffie-Hellman — which must itself be authenticated, or a man-in-the-middle can run one exchange with each side.
    • Higher-level tools: HTTPS (HTTP over TLS), SSH (remote login and tunnels), and enterprise systems such as Kerberos for authenticating users to many services. Build on these; building your own cryptography almost always fails.

    Appendix B: virtual machine monitors

    Crux: how to virtualize the machine underneath the OS, transparently. The OS becomes the "application"; the VMM (hypervisor) does to it what the OS does to processes. Revived by Stanford's Disco (Rosenblum et al., → VMware) for server consolidation, testing, and running multiple OSes at once.

    Virtualizing the CPU: trap-and-emulate

    Run the guest OS in user mode (or a de-privileged "supervisor" mode as on MIPS). When it executes a privileged instruction it traps to the VMM, which emulates it (e.g. installing a trap table means the VMM records where the OS's handlers are; a guest system call traps to the VMM, which jumps to the OS's handler; the OS's return-from-trap traps again and the VMM returns to the user). A snag: some instructions (early x86's popf) behave differently in user mode without trapping — hence binary translation (VMware) and, later, hardware virtualization support.

    Virtualizing memory: shadow page tables

    virtual address
    (process view)
    physical address
    (OS thinks it owns)
    machine address
    (the real DRAM)

    Two translations per access is too slow, so the VMM keeps a shadow page table mapping virtual → machine directly, rebuilt whenever the OS changes its page table (which traps). Disco, on MIPS with a software TLB, instead intercepted the OS's TLB-miss handler and installed virtual→machine entries; it cached translations in a software "second-level TLB" and had to flush the TLB on every OS switch (no ASIDs to spare).

    The information gap: the VMM doesn't know what the OS is doing — an idle loop looks like real work; demand-zeroing a page the VMM just zeroed wastes time. Para-virtualization (Xen) modifies the guest OS slightly to cooperate. The appendix's closing thought: the same ideas — limited direct execution, address translation, laziness — apply one level down, and the VMM is just "another OS" in disguise.
