Files, directories, and a file system simple enough to hold in your head

    Files and directories (chapter 39)

    Crux: how to manage a persistent device. What are the APIs? What matters in the implementation?

    A file is a linear array of bytes with a low-level name, its inode number. A directory is a list of (human name, inode number) pairs — itself a file with an inode number — always containing . and ... Together they form a tree from /; the pathname is the human-readable name. File extensions are convention, not law.

    Three tables behind a descriptor

    A file descriptor is a per-process integer indexing a per-process array; each entry points to an entry in the system-wide open file table (the current offset, read/write mode, a reference count, the underlying inode). Most entries are private, but fork() and dup() share them:

    Per-process descriptor tables

    parent: fd 3 → entry A
    child (after fork): fd 3 → entry A
    parent: fd 4 = dup(3) → entry A

    Open file table (system-wide)

    entry A: offset = 10, mode = read, refcnt = 3, inode → #12

    Inode table

    inode #12: size, blocks, permissions…
    Because parent and child share entry A, when the child reads and advances the offset the parent's next read continues from there. Shells use exactly this to redirect a pipeline's output.

    File system implementation: vsfs (chapter 40)

    Crux: how to implement a simple file system. What structures go on disk, what do they track, and how are they accessed?

    The book's two questions for any file system: its data structures (arrays of blocks? trees?) and its access methods (what does open/read/write do to those structures?). A mental model beats memorizing code.

    On-disk layout: click any block

    S superblocki / d bitmapsI inode tableD data
    64 blocks of 4 KB. Block 0: superblock. 1–2: inode and data bitmaps. 3–7: inode table (5 blocks × 16 inodes of 256 bytes = 80 inodes). 8–63: 56 data blocks.

    The inode: how a file's blocks are found

    Inode i lives at inodeStartAddr + i × sizeof(inode); the disk reads the sector containing it (inode 32 → byte 20 KB → sector 40 with 512-byte sectors). It holds type, size, block count, permissions, owner, times, and — the interesting part — pointers to data blocks. vsfs uses the ext2/ext3 scheme: 12 direct pointers, one indirect (a block of pointers), one double indirect, one triple indirect. It's an imbalanced tree biased toward small files — because, as the measurements the book cites show, most files are small (~2 KB), most bytes are in big files, and directories are tiny.

    Alternatives: extents (pointer + length; compact but less flexible — ext4, XFS), linked lists with a table of next-pointers (the FAT file system), and directories as hash tables or B-trees (XFS) instead of the simple list vsfs uses.

    Directories, free space

    A directory's data block is a list of entries: (inum, reclen, strlen, name) — reclen lets a deleted entry (inum 0) be reused. Free space: the inode and data bitmaps (block 1 and 2); on create, scan for a free inode; on write, find free data blocks — ext2/3 tries to find a run of free blocks for contiguity (pre-allocation).

    Access paths: what actually hits the disk

    Reading /foo/bar (three blocks) with an empty cache: traversal starts at the root inode (well-known number 2) and alternates inode → directory data → inode… Each read() touches bar's inode (to find the block), the data block, and writes the inode (access time).     Crux: how to reduce file system I/O costs. Even open is dozens of I/Os on a deep path. Answer: caching. Early systems set aside a fixed 10% of memory (a static partition); modern ones use a unified page cache shared with virtual memory (dynamic partitioning). Writes are buffered in memory for 5–30 s so they can be batched, scheduled, or elided entirely (a file created and deleted before the flush never touches disk) — at the risk of losing data on a crash. Databases and careful apps use fsync(), direct I/O, or raw disk to opt out.
