Paging: fixed-size pieces, a table to map them, and a cache to make it fast

Variable-sized allocation fragments memory; the allocator chapter shows how hard that is to manage. Paging sidesteps it by chopping everything into fixed-size pages, at the price of a translation table for every process — big and slow unless the hardware caches it (the TLB) and the OS structures it cleverly (multi-level tables).

Primary sources: Ch 17, Ch 18, Ch 19, Ch 20. Homework: malloc.py, paging-linear-translate.py, tlb.c (measure your own TLB), paging-multilevel-translate.py. Chapter 17 draws on Wilson et al.'s allocator survey.

What you'll be able to do

    Free-space management (chapter 17)

    Crux: how to manage free space when requests are variable-sized (user-level malloc, or the OS with segments)? Which strategies minimize fragmentation, at what time/space cost?

    Mechanisms every allocator has: splitting a free chunk to satisfy a smaller request, coalescing adjacent free chunks on free(), and a header just before each allocated block that records its size (that's how free(ptr) knows how much to release) plus a magic number for sanity checks. The free list itself is embedded inside the free space. Try the classic fit policies:

    Heap of 100 units. Initially: free 10 · used 5 · free 30 · used 5 · free 20 · used 5 · free 25. Click a used block to free it (adjacent free chunks coalesce).
    typedef struct { int size; int magic; } header_t;   // lives just before the pointer malloc returns
void free(void *ptr) {
    header_t *hptr = (header_t *) ptr - 1;
    assert(hptr->magic == 1234567);
    // total freed = hptr->size + sizeof(header_t)
}
    • Best fit: smallest chunk that fits (exhaustive search, leaves tiny slivers). Worst fit: largest chunk (also exhaustive; performs badly). First fit: first that fits (fast; junk at the head of the list unless address-ordered). Next fit: first fit resuming where the last search ended.
    • Segregated lists for popular sizes — the slab allocator (Bonwick, Solaris) keeps pre-initialized kernel objects in per-type caches. Binary buddy: split power-of-two blocks recursively; coalescing is trivial (a buddy's address differs in one bit) but internal fragmentation results. Real allocators (glibc) also use trees and balanced structures for speed and scale.

    Paging (chapter 18)

    Crux: how to virtualize memory with pages so as to avoid segmentation's problems, with minimal space and time overhead?

    Split the address space into fixed-size pages and physical memory into page frames. Any page can go in any frame, so there's no external fragmentation and sparse address spaces are cheap. A per-process page table maps virtual page number (VPN) → physical frame number (PFN). The book's tiny example: a 64-byte address space with four 16-byte pages in a 128-byte physical memory with eight frames.

    Translate a 6-bit address (2-bit VPN, 4-bit offset)

    VPN→ PFN
    03
    17

    VPN     = (VirtualAddress & VPN_MASK) >> SHIFT      // top bits
PTEAddr = PTBR + (VPN * sizeof(PTE))                // page-table base register + index
PTE     = AccessMemory(PTEAddr)                     // an extra memory reference
if (PTE.Valid == False)            RaiseException(SEGMENTATION_FAULT)
else if (CanAccess(PTE.ProtectBits) == False) RaiseException(PROTECTION_FAULT)
else { offset = VirtualAddress & OFFSET_MASK;
       PhysAddr = (PTE.PFN << SHIFT) | offset;  Register = AccessMemory(PhysAddr) }

    Two problems paging creates

    Too big

    32-bit address space, 4 KB pages → 20-bit VPN → 220 ≈ 1 M entries × 4 bytes = 4 MB per process, for a linear table. With 100 processes that is 400 MB of page tables. So they live in OS memory, not in the MMU — and later, can even be swapped.

    Too slow

    Every load/store now needs a second memory access to fetch the PTE. Trace the book's array-init loop: each iteration has 4 instruction fetches, 1 explicit store, and 5 page-table lookups — 10 memory accesses instead of 5.

    What's in a PTE

    A valid bit (unmapped pages of the sparse space are invalid — touching them traps, probably killing the process); protection bits (read/write/execute); a present bit (in memory or on disk); a dirty bit (modified since brought in); a reference/accessed bit (used recently — key for replacement). The x86 PTE packs P, R/W, U/S (user or supervisor), PWT/PCD/PAT (caching), A, D and the 20-bit PFN into 32 bits; x86 has no separate valid bit, it uses P for both.

    TLBs: faster translations (chapter 19)

    Crux: how to speed up address translation and avoid the extra memory reference? Add a translation-lookaside buffer to the MMU: a small, fully-associative hardware cache of recent VPN→PFN mappings. (A better name: address-translation cache.)
    VPN = (VirtualAddress & VPN_MASK) >> SHIFT
(Success, TlbEntry) = TLB_Lookup(VPN)
if (Success == True)                                // TLB hit
    if (CanAccess(TlbEntry.ProtectBits)) { PhysAddr = (TlbEntry.PFN << SHIFT) | Offset; AccessMemory(PhysAddr) }
    else RaiseException(PROTECTION_FAULT)
else                                                // TLB miss: walk the page table, install, retry
    PTE = AccessMemory(PTBR + VPN * sizeof(PTE))
    if (!PTE.Valid) RaiseException(SEGMENTATION_FAULT)
    else { TLB_Insert(VPN, PTE.PFN, PTE.ProtectBits); RetryInstruction() }

    Ten 4-byte ints starting at virtual address 100, 16-byte pages (so a[0] sits at offset 4 of VPN 6). Step through sum += a[i].

    The 70% here comes from spatial locality (neighbouring elements share a page). Running the loop again immediately would hit 100% — temporal locality. Bigger pages raise TLB coverage; that's why databases use large pages. Programs whose working set exceeds TLB coverage slow down sharply.

    Who handles the miss?

    Hardware-managed (CISC, x86): the hardware knows the page-table format, walks it via the PTBR, fills the TLB, retries. Software-managed (RISC: MIPS, SPARC): the hardware raises an exception; a trap handler in the OS looks up the translation, installs it with a privileged instruction, and returns — to the same instruction, not the next one. The OS handler itself must never TLB-miss (keep it in unmapped or permanently-mapped memory). Flexibility: the OS can use any table structure it likes.

    Context switches

    Translations are per-process; after a switch they are wrong. Options: flush the TLB on every switch (set all valid bits to 0; cost: misses after every switch), or add an address space identifier (ASID) to each entry so entries of different processes coexist; the OS sets a privileged ASID register on switch. Two processes sharing a code page can have entries with different VPNs, same PFN.

    Replacement on a full TLB: LRU or random (random avoids pathological loops of n+1 pages in an n-entry TLB). A real MIPS R4000 entry: 19-bit VPN, 24-bit PFN, 8-bit ASID, plus global (ignore ASID), coherence, dirty and valid bits — 64 bits total. TLBs typically hold 32–128 entries; a few are wired for the OS.

    Smaller tables (chapter 20)

    Crux: how to make page tables smaller? Linear arrays waste memory (4 MB per process, mostly for invalid entries). What structures fix that, and what inefficiencies do they add?
    • Bigger pages (16 KB → 1 MB table) — but internal fragmentation inside each page. Modern systems offer multiple page sizes for special cases.
    • Hybrid paging+segments: one page table per segment, bounded by the segment size. Still fragments; and a sparse heap needs a big table.
    • Multi-level page tables: chop the page table into page-sized pieces; don't allocate pieces that are entirely invalid; a page directory says where each piece is (or that it's invalid). Space-efficient for sparse spaces, page-sized pieces are easy to place, but a TLB miss now costs two (or more) memory loads: a time-space trade-off, and more complexity.
    • Inverted page table: one entry per physical frame; a hash table makes lookup practical (PowerPC).
    • And tables themselves can be swapped to disk (VAX/VMS) — next lesson.

    Two-level translation: the book's 16 KB space with 64-byte pages

    14-bit address: 8-bit VPN + 6-bit offset. Each PTE is 4 bytes, so a 64-byte page holds 16 PTEs → the VPN splits into a 4-bit page-directory index and a 4-bit page-table index. Code lives in VPNs 0–1, heap in 4–5, stack in 254–255; everything else is unmapped, so only two of sixteen page-table pages exist.

    PDEAddr = PageDirBase + (PDIndex * sizeof(PDE))        // load 1
PDE = AccessMemory(PDEAddr); if (!PDE.Valid) fault
PTEAddr = (PDE.PFN << SHIFT) + (PTIndex * sizeof(PTE))  // load 2
PTE = AccessMemory(PTEAddr); if (!PTE.Valid) fault
PhysAddr = (PTE.PFN << SHIFT) | Offset                  // load 3: the actual data
