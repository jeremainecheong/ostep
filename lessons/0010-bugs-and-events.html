The bugs concurrency actually produces — and the alternative that avoids threads

A study of real code found that most concurrency bugs aren't deadlocks at all, and that nearly every non-deadlock bug is one of two patterns. Deadlock itself has four necessary conditions, each a lever. Then a different answer to the whole problem: don't use threads; write an event loop.

Primary sources: Ch 32, Ch 33. The bug study is Lu et al., "Learning from Mistakes" (ASPLOS '08), which the book calls excellent and readable. Event-based servers: Pai et al. (Flash), Welsh et al. (SEDA), Ousterhout's "Why Threads Are a Bad Idea".

What you'll be able to do

    What kinds of bugs exist? (chapter 32)

    Crux: how to handle common concurrency bugs. They come in a few patterns; knowing them is the first step to writing robust code.

    Lu et al. studied 105 concurrency bugs in MySQL, Apache, Mozilla and OpenOffice: 74 non-deadlock, 31 deadlock. Of the non-deadlock bugs, 97% were one of two kinds.

    Atomicity violation (from MySQL)

    Thread 1::
if (thd->proc_info) {
    ...
    fputs(thd->proc_info, ...);   // T2 may have NULLed it here
}
Thread 2::
thd->proc_info = NULL;

    "The desired serializability among multiple memory accesses is violated": the check and the use were meant to be atomic. Fix: a lock around both accesses in both threads (proc_info_lock).

    Order violation (from Mozilla)

    Thread 1::  mThread = PR_CreateThread(mMain, ...);
Thread 2::  void mMain(...) { mState = mThread->State; }  // mThread may still be NULL

    "The desired order between two memory accesses is flipped": T2 assumed T1 had already run. Fix: enforce ordering with a condition variable (or semaphore) — a state variable mtInit, a lock, and while (mtInit == 0) wait.

    Deadlock

    Crux: how to deal with deadlock. Prevent, avoid, or detect and recover? Is it a real problem? (Yes: 31 of 105.)

    Why do deadlocks happen in big systems? Complex dependencies (the VM system calls the file system to page in; the file system calls the VM for a buffer) and encapsulation (Java's Vector.AddAll(v1, v2) locks both — two threads calling it with the arguments swapped deadlock, and neither caller can see why). Four conditions must all hold. Click one to see the prevention technique that removes it.

    Click a condition.
    Trylock and livelock. pthread_mutex_trylock(L2) lets a thread release L1 and retry instead of waiting — but two threads can retry in lockstep forever (livelock). Add a random delay. Also beware: if code between the acquisitions allocated memory, "back off" must undo it too.
    Lock-free with compare-and-swap. do { old = *v; } while (CAS(v, old, old + amount) == 0); — no lock, so no deadlock; a list insert does the same by retrying CAS(&head, n->next, n). Powerful but hard to generalize (the book: building a general wait-free structure is an entire field).

    Beyond prevention

    • Avoidance via scheduling: if you know which locks each thread may take, never run two threads that could conflict at the same time (Dijkstra's Banker's Algorithm). Conservative, costs concurrency; fine for embedded systems.
    • Detect and recover: let it happen occasionally, detect a cycle in the resource graph, restart. Databases do this; and, per Tom West's law, "not everything worth doing is worth doing well" — a once-a-year freeze may just be rebooted.
    • The chapter's best advice: a lock ordering discipline prevents deadlock before it happens. Its long-term hope: models like MapReduce that avoid locks entirely.

    Event-based concurrency (chapter 33)

    Crux: how to build concurrent servers without threads, keeping control over scheduling and avoiding the bugs above? Node.js and many GUI toolkits do exactly this.
    while (1) {
    events = getEvents();
    for (e in events) processEvent(e);       // the event handler; it must never block
}
int select(int nfds, fd_set *readfds, fd_set *writefds, fd_set *errorfds, struct timeval *timeout);
// checks descriptors 0..nfds-1 for readiness; timeout NULL = block, 0 = poll and return at once
// each iteration: FD_ZERO, FD_SET each socket, select(), then FD_ISSET to find the ready ones
    • Why simpler: no locks. One thread, one handler at a time, so no interleaving inside a handler — the concurrency bugs above simply cannot happen. The application, not the OS, decides what runs next.
    • Problem: blocking calls. A handler that calls read() on a file blocks the whole server. The rule: no blocking calls in handlers. Solution: asynchronous I/O — aio_read(struct aiocb*) returns immediately; poll with aio_error() or get a UNIX signal on completion. (Early systems lacked async disk I/O, so Flash used a hybrid: events for the network, worker threads for disk.)
    • Problem: state management. With threads, local variables survive across a blocking call; with events, the handler that issues the I/O is not the one that finishes it — manual stack management. Record what's needed (e.g., the socket descriptor) in a continuation indexed by the request and look it up when the completion event arrives.
    • Still hard: multiple CPUs bring back locking across event handlers; paging can block a handler implicitly; APIs change from blocking to non-blocking over time and force restructuring; async network and disk I/O don't always integrate neatly.

    The book's verdict: neither model has won; both will persist.
